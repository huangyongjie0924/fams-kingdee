> **一句话结论**：把云之家待办当作「**轮到你处理了**」的定向提醒，而不是流水账。**一张单对一个人最多一条待办**（`sourceId` = 单据 ID），内容随流程推进刷新；上一环节办完即关闭，下一环节的人收到新待办；「打回」（驳回 / 退回）让被打回方的待办**重新变回未办**。

## 0. 与既有需求的对齐声明（必读）

`docs/维修流程模块需求分析.md` **P1-3** 已定义过通知需求，原文：

> As 员工/维修工, I want 关键节点收到云之家消息, so that 我不用反复登录查看
> ① **受理、派工、完工、退回、超时**五个节点推送；② 消息含单号、资产名称、当前状态、可点击进入详情；③ **推送失败不阻塞主流程**。

**结论：已与既有需求对齐，本文档是它的细化与扩展，不是另起一套。** 逐条对照如下：

| P1-3 原文 | 本文档的处理 | 关系 |
|---|---|---|
| 受理节点推送 | §2 事件 2：受理 → 通知**报修人** | 沿用 |
| 派工节点推送 | §2 事件 3：派工 → 通知**被指派维修工** | 沿用 |
| 完工节点推送 | §2 事件 6：报完工 → 通知**报修人** | 沿用 |
| 退回节点推送 | §2 事件 8：退回 → 通知**被指派维修工** | 沿用 |
| **超时**节点推送 | **不在本文档范围** | 归 **P1-5** 超时提醒，独立需求，另行定义 |
| 消息含单号、资产名称 | §3 文案模板全部含 `{单号}` + `{资产名称}` | 沿用 |
| 可点击进入详情 | §3.6 要求「待办可跳转到该单详情页」（URL 由架构师定） | 沿用（技术细节归架构师） |
| 推送失败不阻塞主流程 | §4 验收标准 AC-8 | 沿用 |

**两处需说明的差异（非冲突，是细化）：**

1. P1-3 表述为「**员工 / 维修工** 收到消息」，未区分"谁在哪个节点收"。本文档细化为 **「按'轮到你处理'定向通知」**——只通知该动作的责任人，不做角色广播（唯一例外：**提交报修 → 全体资产管理员**，见 §1）。理由见 §1 与 §2.4。
2. P1-3 把整块能力放在 **P1**。本次用户明确提出「发起维修后要能通知到接收人」，因此本文档把**闭环必需的节点提升为 P0**（提交、派工、报完工、驳回、退回、撤单），把**纯进展告知类节点保留为 P1**（受理、接单）。P0/P1 划分见 §2 表格「优先级」列。

**未发现与既有需求相矛盾之处。**

## 1. 「接受人」歧义澄清

用户原话：**「发起维修后能通知到接受人」**。

问题：流程里 `pending`（刚提交）时**还没有任何指派人**——真正确定「谁来接这单」是 `dispatch`（派工）那一刻。所以「接受人」在时间轴上指向两个不同的人。产品判断如下：

### 1.1 提交报修时，通知谁？

**结论：通知全体资产管理员**（`sys_user.role = 'asset_manager'`，`admin` 兜底）。

| 候选 | 判断 | 理由 |
|---|---|---|
| 全体资产管理员 | ✅ **采用** | 新单必须有人「认领」。若提交后无人知晓，单子就烂在 `pending` 里——这正是 P0-3「报修不靠人喊、不丢单」要消灭的痛点 |
| 资产管理员**角色**（只发一条角色级待办） | ❌ | 云之家待办是**按人**推送的（`openId`），没有"发给一个角色"的通道；角色必须展开成人 |
| 指定受理人 | ❌ | `pending` 阶段还没有受理人；且"谁值班"是排班问题，不该由员工报修时决定 |
| 不通知，只等派工 | ❌ | 违反 P0-3：单子没人看见就等于丢单。派工的前提是"先有人受理" |

**数量控制**：管理员人数有限（资产管理员岗，通常个位数），且**同一张单对每个管理员各发一条**（各自 `sourceId` = 单据 ID，互不覆盖）。这不会造成"一张单刷屏"。

### 1.2 派工时，通知谁？

**结论：通知被指派的维修工**（`RepairOrder.AssigneeEmpID` → 该员工的云之家 `openId`）。

**若派给外部维保供应商（`vendor_id > 0`，`assignee_emp_id = 0`）：不发送云之家待办。**
理由：外部供应商**没有本系统账号、也不在云之家组织内**，不存在 `openId`，技术上不可能收到。产品侧降级方案见 §5.2。

### 1.3 用户本意若是「提交即通知」，能否覆盖？

**能，且这正是本设计。** 用户说的「发起维修 → 通知接受人」，在本设计里就是：
- **提交那一刻** → 通知**全体资产管理员**（承接"发起即有人管"）；
- **派工那一刻** → 通知**被指派维修工**（承接"确定谁来修"）。

两个时刻都覆盖，不存在遗漏。

### 1.4 一张单最多几条待办？

**每张单，对每个相关的人各一条，互不覆盖。** 依据：待办唯一键为 `openId + appId + sourceId`，`sourceId` 取**单据 ID**，因此：

- 同一张单 → 不同的人 → 各一条（不覆盖）；
- 不同单据 → 同一个人 → 各一条（不覆盖）；
- **同一张单 → 同一个人 → 只有一条**（会被后续事件刷新内容，见 §2.4）。

产品语义上这是**合理的**：一个人对一张单只该有一条"当前待办"，它随流程更新；不需要为同一张单保留多条历史待办（历史由 `doc_status_log` 时间线承担，员工进单据详情即可看全）。

## 2. 触发矩阵（核心交付物）

### 2.1 读表说明

- **「通知谁」** = 该事件发生后**需要处理的人**（待办责任人），并注明从哪个字段取人。
- **「待办动作」** = 对**该接收人**那条待办做什么：`新建` / `标已读` / `标已办` / `删除` / `不通知`。
- **待办标题** = 云之家待办列表里显示的短标题；**`content`** = 手机通知栏正文（只显示它，必须自带信息）；**`itemtitle`** = 待办项标题（单据维度）。
- **优先级**：P0 = 闭环必需；P1 = 进展告知增强（可后补）。

### 2.2 需要通知的事件

| # | 事件（动作码 + 状态跃迁） | 通知谁（角色 + 定位字段） | 待办动作 | 待办标题 | 待办内容 `content` | 待办项标题 `itemtitle` | 优先级 |
|---|---|---|---|---|---|---|---|
| 1 | `submit` 提交报修：`''` → `pending` | **全体资产管理员**（`sys_user.role='asset_manager'`，`admin` 兜底；逐人取云之家 `openId`） | **新建**（每人一条，`sourceId`=单据 ID） | 新报修待受理 | `{报修人}报修「{资产名称}」，问题：{故障描述}` | `{单号} {资产名称}` | **P0** |
| 2 | `accept` 受理：`pending` → `accepted` | 报修人（`RepairOrder.ReporterEmpID`） | **新建**（若已存在则刷新 `content`，置为「已读」） | 报修已受理 | `你的报修「{资产名称}」已被受理，等待派工` | `{单号} {资产名称}` | P1 |
| 3 | `dispatch` 派工（内部维修工）：`accepted` → `dispatched` | 被指派维修工（`RepairOrder.AssigneeEmpID`） | **新建**；同时把**管理员**那条**标已办** | 维修派工待接单 | `指派你维修「{资产名称}」，问题：{故障描述}` | `{单号} {资产名称}` | **P0** |
| 4 | `dispatch` 派工（外部供应商，`vendor_id>0`） | —（无人可通知） | **不通知**（见 §5.2） | — | — | — | P0 |
| 5 | `take` 接单：`dispatched` → `repairing` | 报修人（`ReporterEmpID`） | **刷新**已有待办 `content`，置「已读」 | 维修进行中 | `你的报修「{资产名称}」已由{维修工}接单，维修中` | `{单号} {资产名称}` | P1 |
| 6 | `finish` 报完工：`repairing` → `confirming` | 报修人（`ReporterEmpID`） | **新建 / 刷新为「未办」**；同时把**维修工**那条**标已办** | 维修待确认 | `你的「{资产名称}」已报完工，请确认维修结果` | `{单号} {资产名称}` | **P0** |
| 7 | `confirm` 确认完工：`confirming` → `done` | 报修人（自己）、被指派维修工、全体资产管理员 | **全部标已办**（结案，无人再需动作） | —（不新建） | — | — | **P0** |
| 8 | `return` 退回：`confirming` → `repairing` | 被指派维修工（`AssigneeEmpID`） | **重新新建 / 置回「未办」**（打回）；报修人那条**标已办** | 维修被退回待返工 | `「{资产名称}」被报修人退回：{退回原因}，请重新处理` | `{单号} {资产名称}` | **P0** |
| 9 | `reject` 驳回：`pending` → `rejected` | 报修人（`ReporterEmpID`） | **新建**（告知 + 待其决定是否重报）；管理员那条**标已办** | 报修被驳回 | `你的报修「{资产名称}」被驳回：{驳回原因}` | `{单号} {资产名称}` | **P0** |
| 10 | `cancel` 报修人撤单：`pending` → `cancelled` | 全体资产管理员（提交时收到的那批人） | **标已办**（撤单后管理员无需再处理） | —（不新建） | — | — | **P0** |
| 11 | `cancel` 管理员取消：`accepted` / `dispatched` → `cancelled` | 报修人 + 被指派维修工 | 报修人：**刷新 `content`**；维修工：**标已办** | 报修已取消 | `你的报修「{资产名称}」已被管理员取消` | `{单号} {资产名称}` | **P0** |

**统计：要通知的事件 10 条**（编号 1、2、3、5、6、7、8、9、10、11；其中 4 为派工的外部供应商分支，属"不通知"）。

### 2.3 明确「不通知」的事件及理由

| # | 事件 | 为什么不通知 |
|---|---|---|
| 12 | `submit` 提交报修（**报修人自己**） | 是他自己刚做的动作，通知自己是"回声"，徒增打扰（违反设计宗旨「不打扰」）。他的待办从「受理」开始建立 |
| 13 | `accept` 受理（**管理员自己**） | 管理员受理后下一步还是他派工，任务未结束，**不标已办、不重复发**；待办保持未办、`content` 静默刷新即可 |
| 14 | `take` 接单（**维修工自己**） | 维修工自己点的接单，只需把自己那条待办**标已读**，不新建 |
| 15 | `finish` 报完工（**维修工自己**） | 同上，把自己那条**标已办**即可 |
| 16 | `confirm` 确认完工（**报修人自己**） | 自己动作，仅关闭自己那条待办 |
| 17 | `dispatch` 派工给**外部供应商** | 供应商无本系统账号、不在云之家组织内，不可能收到（见 §5.2） |
| 18 | **超时未受理 / 未完工** | 属 **P1-5** 超时提醒，独立需求；本文档不含，划清边界 |
| 19 | `approving` 待审批 / `scrapping` 报废评估 | P1/P2 预留码，**P0 不产生**这两个跃迁 |

**统计：不通知的事件 8 条**（编号 12–19）。

### 2.4 三条必须讲清的产品语义

**(1) 为什么同一张单对同一个人"只有一条待办"却不会丢信息？**
因为待办**不是流水账，是"当前该你做什么"**。同一张单在报修人侧从「已受理」→「维修中」→「待确认」，只是同一条待办的 `content` 在刷新、状态在变（已读 → 未办 → 已办）。**完整历史**由单据详情页的 `doc_status_log` 时间线承担（架构建议 §2.2），两者职责不重叠。这符合设计宗旨原则 5「每个人都看得见与自己有关的事」——**看历史去详情页，看"轮到我做什么"看待办**。

**(2) 打回（驳回 / 退回）必须让待办从「已办」回到「未办」。**
- **退回**（`confirming → repairing`）：维修工原本在报完工时已被标「已办」，现在单子回到他手上，**必须重新置为「未办」**——否则他会漏掉这张被退回的单。技术上因 `sourceId` 相同、会覆盖旧记录，**恰好实现"重新变回未办"**，产品语义与实现天然一致。
- **驳回**（`pending → rejected`）：报修人被驳回后需要决定「改一改再报 / 算了」。给他**新建**一条「已驳回」待办（同样 `sourceId` = 单据 ID），让他**在待办里看得到**。若要他重新提交，是**新建另一张单**（新 `sourceId`），不覆盖本条。

**(3) 报修人自己做的动作，要不要通知自己？——不通知。**
报修人确认完工、撤单、退回，都是**他自己的动作**。给他再发一条"你刚做了某事"的待办，是纯粹的噪音（违反设计宗旨「服务员工、不打扰」）。处理方式：
- **撤单** → 关闭（标已办）他自己那条；
- **确认完工** → 关闭（标已办）他自己那条；
- **退回** → 他自己那条**标已办**（他的动作已完成），**同时**给维修工**新建/置回未办**（§2.2 事件 8）。

## 3. 文案规范

### 3.1 三段文案的分工

| 字段 | 显示位置 | 长度上限 | 职责 |
|---|---|---|---|
| 待办标题 | 待办列表短标题 | **≤ 10 个中文字** | 一眼看出"要我干什么"（动作导向） |
| `content` | **手机顶部通知栏 / 待办摘要**（**只显示它**） | **≤ 40 个中文字** | **必须自带全部关键信息**，脱离系统也能看懂 |
| `itemtitle` | 待办项标题（单据维度） | **≤ 24 个中文字** | 单据定位：单号 + 资产名 |

> **硬规则**：`content` **禁止**出现「您有一条新待办」「请查看系统」这类空话。它必须在通知栏里就把「谁的、哪台设备、什么问题、要我做什么」说清——因为员工多数**不会点进去**，只看通知栏。

### 3.2 文案模板（可直接使用，`{}` 为变量占位）

| 场景 | 待办标题 | `content` | `itemtitle` |
|---|---|---|---|
| 提交报修 → 管理员 | 新报修待受理 | `{报修人}报修「{资产名称}」，问题：{故障描述}` | `{单号} {资产名称}` |
| 受理 → 报修人 | 报修已受理 | `你的报修「{资产名称}」已被受理，等待派工` | `{单号} {资产名称}` |
| 派工 → 维修工 | 维修派工待接单 | `指派你维修「{资产名称}」，问题：{故障描述}` | `{单号} {资产名称}` |
| 接单 → 报修人 | 维修进行中 | `你的报修「{资产名称}」已由{维修工}接单，维修中` | `{单号} {资产名称}` |
| 报完工 → 报修人 | 维修待确认 | `你的「{资产名称}」已报完工，请确认维修结果` | `{单号} {资产名称}` |
| 退回 → 维修工 | 维修被退回待返工 | `「{资产名称}」被报修人退回：{退回原因}，请重新处理` | `{单号} {资产名称}` |
| 驳回 → 报修人 | 报修被驳回 | `你的报修「{资产名称}」被驳回：{驳回原因}` | `{单号} {资产名称}` |
| 管理员取消 → 报修人 | 报修已取消 | `你的报修「{资产名称}」已被管理员取消` | `{单号} {资产名称}` |

### 3.3 紧急程度 `urgency` 要不要体现在文案里？

**结论：只在 `high` 时体现，`low` / `normal` 不体现。**

- **理由**：`urgency` 是报修人给的**主观**分级。若每条都标「【一般】」，通知栏会被无信息量的标签占满（违反「不打扰」）；而**真正紧急**的设备停机必须让管理员在通知栏第一眼看到。
- **落地规则**：`urgency = high` → `content` **前缀加** `【紧急】`；`low` / `normal` → 不加任何前缀。
- 例：`【紧急】张三报修「3号注塑机」，问题：异响停机`。
- `low` / `normal` 的区分仍保留在**单据详情页**展示（`RepairUrgencyLabels`），只是不进通知栏。

### 3.4 长度上限与截断规则

| 变量 | 上限 | 截断规则 |
|---|---|---|
| `{故障描述}`（`fault_desc`，库上限 500 字） | **20 字** | 超 20 字取前 20 字 + `…` |
| `{资产名称}`（`asset_name`） | **16 字** | 超 16 字取前 16 字 + `…` |
| `{报修人}` / `{维修工}`（姓名） | 不截断 | 姓名一般 2–4 字 |
| `{驳回原因}` / `{退回原因}` | **20 字** | 超 20 字取前 20 字 + `…` |
| `{单号}` | 不截断 | 固定格式 `WX<8位日期><4位序号>`（如 `WX202609200001`） |

**截断顺序（重要）**：**先对每个变量各自截断，再拼接模板**。禁止"先拼好整句再整体截断"——那样会把模板后半段（如「请确认维修结果」）截掉，导致语义残缺。

**`content` 总长兜底**：拼接后若仍 > 40 字（极端：长资产名 + 长故障描述 + `【紧急】`），按 **`{故障描述}` → `{资产名称}`** 的顺序继续缩短，**保证「动作要求」句（如「请确认维修结果」）永远不被截掉**。

### 3.5 语气

- 全中文，**说人话**，不官腔：用「你的报修」「已报完工」这类员工日常说法，不用「贵单」「已受理完毕，请知悉」。
- 对报修人：第二人称「你」（与 FAMS 现有界面一致）。
- 对管理员 / 维修工：直接说动作（「指派你维修…」「…请重新处理」），不用敬语。

### 3.6 跳转要求（文案之外，但产品必须提）

每条待办**可点击跳转到该维修单详情页**（对齐 P1-3「可点击进入详情」）。跳转 URL 属技术方案，由架构师定义；产品侧只要求：**点开后落在该单详情**，而不是落在列表或首页。

## 4. 验收标准（Given / When / Then）

| # | 验收标准 |
|---|---|
| **AC-1** | **Given** 员工 A 提交了一张报修单（资产「3号注塑机」，问题「异响停机」）<br/>**When** 提交成功<br/>**Then** 全体资产管理员（每个 `role='asset_manager'` 的账号）在云之家各收到 1 条待办，`content` 含「A」「3号注塑机」「异响停机」，且**不含**"您有一条新待办"之类的空话；员工 A **不**收到待办 |
| **AC-2** | **Given** 管理员 B 已受理并派工给维修工 C<br/>**When** 派工成功<br/>**Then** 维修工 C 收到待办「维修派工待接单」，`content` 含资产名称与故障描述；同时管理员 B 那条「新报修待受理」**转为已办** |
| **AC-3** | **Given** 维修工 C 已接单（单据处于「维修中」）<br/>**When** C 在系统中点「接单」<br/>**Then** C 自己那条待办**转为已读**，**不新建**新待办（不给自己发回声） |
| **AC-4** | **Given** 维修工 C 报完工，单据进入「待确认」<br/>**When** 报完工成功<br/>**Then** 报修人 A 收到待办「维修待确认」，`content` 含「请确认维修结果」；维修工 C 那条待办**转为已办** |
| **AC-5** | **Given** 报修人 A 确认完工，单据进入「已完工」<br/>**When** 确认成功<br/>**Then** 报修人 A、维修工 C、相关管理员**三方待办全部转为已办**，不再有待办挂在任何人的待办列表里 |
| **AC-6** | **Given** 报修人 A 对「待确认」的单点「退回」（填原因「仍异响」）<br/>**When** 退回成功<br/>**Then** 单据回到「维修中」；维修工 C **重新收到未办待办**，`content` 含退回原因；A 自己那条待办转为已办 |
| **AC-7** | **Given** 管理员 B 驳回一张待受理单（填原因「重复报修」）<br/>**When** 驳回成功<br/>**Then** 单据进入「已驳回」；报修人 A 收到待办，`content` 含驳回原因；管理员 B 那条待办**转为已办** |
| **AC-8** | **Given** 云之家服务不可用（超时 / 返回错误 / `openId` 解析失败）<br/>**When** 员工提交报修、管理员派工、维修工报完工等任一动作<br/>**Then** **维修单流程全部正常完成**（状态正确跃迁、数据正确落库、FAMS 内「我的报修 / 维修管理」正常显示）；通知失败**只记日志**，不弹错、不回滚、不阻塞任何人 |
| **AC-9** | **Given** 维修工 C **未绑定云之家**（无 `openId`）<br/>**When** 管理员把单派给 C<br/>**Then** 派工**成功**（流程不阻断）；C 在 FAMS 内正常看到该单；管理员侧能**看出 C 收不到通知**（见 §5.1） |

> 覆盖检查：AC-1 提交后管理员收到 ✅｜AC-2 派工后维修工收到 ✅｜AC-3 接单后待办转已读 ✅｜AC-4 完工后报修人收到 ✅｜AC-5 确认后待办转已办 ✅｜AC-7 驳回后待办回到待处理 ✅｜AC-8 云之家不可用不影响流程 ✅｜AC-9 无 openId 降级 ✅

## 5. 边界与例外

### 5.1 维修工没有云之家账号 / 未同步到 `openId`

**现状**：员工多为云之家 SSO 自动建号（`api/sso.go`），理论上都有 `openId`；但**维修工可能被手工配账号**、或工号未与云之家对齐，导致取不到 `openId`。

**产品上的降级原则：通知是"锦上添花"，流程是"底线"。**

| 场景 | 处理 |
|---|---|
| 派工时该维修工**取不到 `openId`** | ① **派工照常成功**，绝不阻断（对齐 P1-3「推送失败不阻塞主流程」）；② 该维修工在 FAMS 内**照常看到**派给自己的单（待办只是"提醒"，不是"数据入口"）；③ 该条通知**静默跳过并记日志** |
| 管理员**是否需要看到**「此人无法接收通知」 | **需要**。建议：在**派工时的维修工选择下拉**里，对未绑定云之家的员工加灰字标注「未绑定云之家 · 无法收到待办提醒」。理由：管理员据此可以改用**电话 / 口头**补一句，避免"以为通知了、其实没通知"的盲区 |
| 是否需要为维修工自动补建云之家绑定 | **不需要**（超范围）。绑定关系由云之家组织同步决定，不在本模块职责内 |

### 5.2 外部维保供应商无账号

**结论：不做云之家通知，仅 FAMS 内展示。**

| 项 | 处理 |
|---|---|
| 云之家待办 | **不发**（供应商无账号、不在组织内，技术上不可达） |
| FAMS 内展示 | 维修单详情 / 列表正常显示 `vendor_name`，状态照常流转（`dispatched` → 由管理员或维修工推进） |
| 替代提醒手段 | **建议由管理员线下通知**（电话 / 微信），系统**不做**自动外发。理由：本模块「领域固化、不做工作流引擎」，为供应商单独做一套外发通道属过度设计 |
| 未来 | 供应商自助协同入口是 **P2-4**（需受控访问），届时再评估 |

### 5.3 一单派给多人

**确认：当前模型只支持单个 `AssigneeEmpID`（单指派），因此只通知一人，不存在"多人通知"。**

| 项 | 结论 |
|---|---|
| 现状 | `RepairOrder.AssigneeEmpID` 为单值（`model/repair.go`），产品上**不做多人派工** |
| 是否支持"派工 + 抄送" | **不做**。抄送会引入"谁负责"的歧义，与 P0-4「列表只显示指派给自己的单」冲突 |
| 若将来需要多人协作 | 属**模型变更**（需多指派表 + 责任归属规则），本产品定义**不涉及**；提出前须先明确"谁点报完工、谁算工作量" |

### 5.4 其他边界

| 项 | 结论 |
|---|---|
| 同一张单被反复打回 | 待办**只有最新一条**（`sourceId` 覆盖），不累积。用户可接受——历史在单据时间线里 |
| 单据进入终态后 | 所有相关待办**全部转已办**，不留悬挂待办 |
| 员工一天报修 10 张单 | 收到 10 条**独立**待办（`sourceId` 不同，不覆盖），这是正确的——确实是 10 件待办的事 |
| 通知与 FAMS 内数据的**一致性** | 待办只是提醒；**状态真相以 FAMS 单据为准**。待办内容过期（如已被别人处理）时，点进去看到的是**最新真实状态**，不误导 |
