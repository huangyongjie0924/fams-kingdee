## 1. 前置检查（上线前逐项确认）

### 1.1 配置项

| 配置键 | 环境变量 | 必填 | 说明 |
|---|---|---|---|
| `flowcenter_enabled` | `YZJ_FLOWCENTER_ENABLED` | 是（切换时置 true） | 总开关，**默认 false** |
| `flowcenter_type_id` | `YZJ_FLOWCENTER_TYPE_ID` | 是 | 模板标识，**我们自己定义的任意值**（本项目取 `WXSQD` =「维修申请单」）。**发过待办后不可改，init 之前可自由改**。✅ **无需向云之家注册 / 报备 / 申请**，见 §2 步骤 2 的澄清与设计文档 §8.1 |
| `flowcenter_type_name` | `YZJ_FLOWCENTER_TYPE_NAME` | 是 | 模板名，如「维修工单」 |
| `flowcenter_app_name` | `YZJ_FLOWCENTER_APP_NAME` | 是 | 模板分类名，一般填轻应用名 |
| `eid` | `YZJ_EID` | 是 | 流程中心走 **team 级**令牌，缺 eid 直接报 `11000400` |
| `sender_id` | — | **是（易漏）** | 见下方说明 |
| `flowcenter_web_url` / `_mobile_url` | `YZJ_FLOWCENTER_*` | 否 | P0 不做统一发起，留空 |
| `flowcenter_sign_key` | `YZJ_FLOWCENTER_SIGN_KEY` | 否 | P0 不做快捷同意，留空 |

### 1.2 ⚠️ `sender_id` 必须有值（**运行期硬前置，2026-09-23 实测确认**）

`sender_id` 在两个地方都是必填：

| 时机 | 用途 | 为空会怎样 |
|---|---|---|
| 建模板（`init`） | `creator` | `cmd/yzjflowinit` 取不到 `-creator` 且 `sender_id` 为空 ⇒ **退出码 1，模板建不出来** |
| 运行期（`send`） | `creator` | **云之家直接拒绝**：`{"errorCode":1101030,"error":"creator不能为空","success":false}` |

> ⚠️ **实测更正（2026-09-23，探针 `cmd/zzflowprobe -step 6`）**：
> 本节原先写「运行期 `creator` 为空时只记告警日志、**仍照常发送**」——**该说法已被推翻**。
> 空 `creator` 会被云之家**明确拒绝**（`1101030`）。代码里「为空时仍照常发送」的注释与告警
> 日志因此也不准确：实际是**发送失败**，会走 3 次退避重试后落库 `state=failed`。
>
> - **好消息**：这是**响亮失败**（`success:false` + 明确错误信息），不是静默失败。
> - **坏消息**：`MissingFlowCenterConfig()` **不检查 `sender_id`**（`config/config.go:410`），
>   所以「开关打开 + `sender_id` 为空」**不会被启动防御拦下**，只会在**每条通知发出时**失败。
>   ⇒ **上线前必须人工确认 `sender_id` 非空**（见 §1.3 勾选项）。

**`sender_id` 该填谁**：一个**稳定的真实 云之家 openId**（`creator` 语义 = 流程发起人）。

- ❌ 不要用「报修人 openId」动态充当：生产实测 openId 回填率只有 101/130（77.7%），
  剩下 22% 会直接发不出去；P0 用固定账号更稳。
- ⚠️ 配了 `sender_id` 会**顺带影响 im-todo 通道**：`senderId` 从「不传」变为「传」
  （`integration/yunzhijia/todo.go:39` 是 `omitempty`）。该字段官方标「选填」、风险低，
  但要知道自己顺带动了既有通道。

### 1.3 一次性确认（不可逆项）

- [ ] **`sender_id` 已配置为非空真实 openId**（运行期**硬前置**：实测空值被云之家拒绝 `1101030 creator不能为空`；而启动防御**不检查**此项，漏配只会在发通知时才暴露）。见 §1.2。
- [ ] `flowcenter_type_id` 的取值已定稿。它是**我们自己定义的任意值**（不是从云之家查的，示例：`FQSK` / `QJSQ`），约束来自 send 接口「同一流程每次发送待办都用相同 typeId」⇒ **发过待办后不能改，init 之前可自由改**。
- [ ] 另：官方「必读」第 1 条约束的是 **AppId**（原文「上线后请勿再修改集成参数，尤其是 AppId」）—— 这一条才是**真正不可逆**的，`app_id` 已实测为 `500000084`，不要动。
- [ ] **已确认无任何云之家侧的外部前置动作**：金蝶技术支持 2026-09-23 答复「不需要在云之家注册，typeId 是由第三方系统开发人员通过这个接口传进来」。`init` 本身就是创建动作 ⇒ 上线只依赖我们自己跑一次 `cmd/yzjflowinit`。详见设计文档 §8.1。
- [ ] **「统一流程中心」模块已开通**（用户 2026-09-23 确认「该模块已开通在使用」），且 team 级授权已实测可用（零副作用探针：`scope=team` + `eid=26527676` 取 token 返回 `success:true`；伪造 eid 反例返回 `11003020 eid 出错` ⇒ 探针有区分力）。
- [ ] AppId 与「第三方应用ID」一致，且与现有 im-todo 用的是同一个（已实测确认）。
- [ ] 已知晓 `init` 的 `field` 是**累加**语义——对同一 `typeId` 重复初始化会**追加**字段而非覆盖。P0 不注册任何自定义字段（`Field` 留空），若将来要加，清单必须一次定好。

## 2. 部署顺序

### 步骤 1：部署新版本（迁移自动执行）

无需手工执行任何 SQL。`store.New()` 启动时自动迁移，会：

- 给 `repair_notify_task` 加 `channel VARCHAR(16) NOT NULL DEFAULT 'im-todo'`、`biz_id VARCHAR(128) NOT NULL DEFAULT ''`；
- 建 `idx_notify_channel_state (channel, state)` 索引；
- **存量行自动回填 `channel='im-todo'`**（由列默认值完成）——这正是要的语义：切换前发出的都是旧通道待办。

迁移走 `addColumnIfMissing` / `createIndexIfMissing`，**幂等可重跑**。

> 已验证：共享开发库（`asset@10.0.0.120`）执行后 `SHOW COLUMNS` 出现两列，存量 7 行全部回填 `channel='im-todo'`，索引已建。

**此步不改变任何运行行为**（开关仍为 false，新待办继续走 im-todo）。

### 步骤 2：初始化流程中心模板（手工执行一次）

```bash
cd /opt/asset-mgr   # 或实际部署目录
YZJ_APP_ID=xxx YZJ_SECRET=yyy YZJ_EID=26527676 \
  ./yzjflowinit -config config.yaml -creator <发起人openId>
```

若 `sender_id` 已配置，可省略 `-creator`。

**为什么必须手工执行、且不要放进启动流程**：`init` **可以重复调用**——官方原文「重复调用该接口将会对现有模板进行更新」，所以它**不是「只能跑一次」**；但**只有 `field` 参数是累加语义**（多次初始化会追加字段而非覆盖），放进启动流程会随每次重启持续污染云之家侧模板。另外 `typeId` 一旦发过待办就不能再改（init 之前可自由改）。这是「需人工确认、不适合自动化」的动作。

> ⚠️ 注意：`init` 的 `webUrl` / `mobileUrl` 本项目**留空** ⇒ 模板在**两端「发起界面」都不可见**。
> 这是**预期**（维修单只能从 FAMS 发起，不该出现在智能审批的发起列表）。
> 别误判成「模板没建成功」——`buid` 不填 ⇒ 模板属根组织，**「模板管理界面」（后台）仍可见**，
> 即下面第 2 步的验证点依旧成立。详见设计文档 §8.2。

**此步同样不改变运行行为**，只是把模板**建到**云之家。

> ✅ **不需要任何云之家侧的申请 / 报备 / 审批**。金蝶技术支持 2026-09-23 明确答复：
> 「不需要在云之家注册，typeId 是由第三方系统开发人员通过这个接口传进来，具体传什么让他们自己定义。」
> `init` 接口**本身就是创建动作**（按 `appId`+`appName` 建分类、按 `typeName` 建模板），
> 所以「注册」= 我们自己跑一次本步骤。
>
> ⚠️ 但「无需注册」≠「无需 init」——官方「集成过程」第 1 条：
> 「业务系统首次接入统一流程中心前**一定要先执行初始化**」。详见设计文档 §8.1。

### 步骤 3：打开开关

```yaml
yunzhijia:
  flowcenter_enabled: true
```

或环境变量 `YZJ_FLOWCENTER_ENABLED=true`。重启服务。

**效果**：**新**待办走流程中心；**旧**待办（`channel='im-todo'`）继续走 im-todo。两种集成方式并存是官方「必读」第 2 条的硬约束——切换前已发出的待办仍在用户手机里，必须能继续被正确办结。

### 步骤 4：观察存量消化

存量待办（生产仅 6 条：active 5 + dealt 1）处理完后，im-todo 代码路径自然闲置。**保留不删**，作为回退通道。

## 3. 验证点

| 步骤 | 怎么确认成功 |
|---|---|
| 1 迁移 | `SHOW COLUMNS FROM repair_notify_task;` 能看到 `channel` / `biz_id`；`SHOW INDEX FROM repair_notify_task;` 有 `idx_notify_channel_state`；存量行 `channel` 均为 `im-todo` |
| 2 模板 | 工具退出码 0，输出「流程中心模板初始化成功」；云之家「智能审批」后台能看到该模板 |
| 3 开关 | 启动日志出现「流程中心已启用」；**且**没有「配置错误：… 已自动关闭统一流程中心」——后者说明必填项缺失、功能被自动降级 |
| 3 端到端 | 走一张**测试单**：提交报修 → 派工 → 接单 → 报完工 → 确认，逐节点检查「流程中心 → 我的待办」里**那条待办的标题（节点名）**是否随流转更新、以及最终是否消失 |

**端到端要重点看的事**：

> ⚠️ **先读这条，否则一定会误判**（2026-09-23 实测更正，探针 `cmd/zzflowprobe`）：
> 「流程中心 → 我的待办」**按 `flowId` 聚合 —— 一个流程实例只有一条待办**，
> 标题/正文 = 最近一次 `send` 的内容。实测：同一实例连发 3 次、跨 2 个不同 `activityId`，
> 界面**始终只有 1 条**，后发的顶替先发的。
>
> 而 `FlowID = 维修单 ID`（`api/notify_flowcenter.go:143`），所以
> **一个维修单在该员工待办列表里永远只占一行**。
>
> ⇒ **验证必须看「标题里的节点名」，不能数条数**；也不存在「同一单两条并存」的情况。
> 详见设计文档 §11「新发现①」。

1. **接单时**：维修工那条待办是**原地更新**——标题从「待接单」变为「维修中」。
   ⚠️ 本节原先写「『待接单』应显示为已办（留痕），而不是消失」，**该期望已作废**：
   在 `flowId` 聚合语义下，「待接单」与「维修中」不可能同时各占一张卡片。
   代码侧「不删已办结节点」的逻辑（`shouldDeleteForReactivate`，`api/notify_flowcenter.go:333`）
   仍应保留，但**其收益不在「我的待办」视图**——历史留痕需去云之家的
   「已办 / 我处理过的」视图确认（⏳ 未实测）。
2. **确认完工后**：该待办应从「我的待办」**消失**
   （✅ 已实测：`instance/finish` 后待办消失），且流程在云之家侧变为「已完成」，不留进行中的僵尸流程。

## 4. 回滚

**回滚操作**：把 `flowcenter_enabled` 置回 `false`，重启。

**为什么回滚是安全的**：办结 / 删除已有待办时，代码看的是**那条记录自己的 `channel`**，不是全局开关。所以回滚后：

- 新待办 → 走 im-todo ✓
- 已用流程中心发出、仍挂在用户手上的待办 → 仍用流程中心接口正确办结 ✓

这正是加 `channel` 列的目的。**不会出现「回滚后一半待办永远办不掉」的情况。**

不需要回滚数据库：新增的列与索引对旧代码无影响。

## 5. 排障速查

| 现象 | 最可能的原因 |
|---|---|
| 启动日志「已自动关闭统一流程中心」 | 必填项缺失，日志里会列出具体缺哪几项（`base_url` / `eid` / `app_id` / `flowcenter_type_id` / `_type_name` / `_app_name`） |
| 接口返回 `11000400 参数错误` | `eid` 未配置或未生效（team 级令牌必须带 eid） |
| 接口返回 `10000401 认证失败` | 用错令牌级别——流程中心必须用 team 级，im-todo 用 app 级 |
| 接口返回 `1101030 参数不能为空` | 令牌级别对，但业务参数缺失。**若 error 文案是「creator不能为空」⇒ `sender_id` 没配**（见 §1.2，启动防御拦不住这一项） |
| 接口返回 `1301003 流程不存在或已删除` | 对一个云之家侧不存在的 `flowId` 调了 `instance/delete` / `finish`。最常见于「该单待办全由 im-todo 发出、之后开关才打开」（已有 `hasFlowCenterTask` 守卫会跳过，见「已实现的兼容守卫」） |
| 待办发不出、日志「skip emp=N 无云之家 openId」 | 该员工未绑定 openId。启动日志会打印覆盖率，为 0 时另有明确告警 |
| 待办一直在用户手上办不掉 | 检查该条记录的 `channel` 与 `biz_id`：`biz_id` 为空说明流程中心待办未成功发出；`channel` 与实际发出的通道不一致会导致用错接口 |
| 每张单确认完工时都报结案失败 | 该单待办全由 im-todo 发出（其 `flowId` 在云之家不存在）。已有守卫会跳过，若仍报错请检查守卫是否生效 |

### 已知限制（P0 接受）

办结调用（`todo/done`）失败时，记录状态置 `failed`，随后重新通知会覆盖其 `biz_id`，导致该节点在云之家侧无法再被办结。属外部接口失败的异常路径，有 3 次有界重试 + `last_error` 落库 + 失败日志。彻底解决需给唯一键加节点维度，改动面大，待有真实数据后评估。

### 测试默认不连生产库（安全阀）

**为什么需要它**：生产机 `10.0.0.120` 上只有生产库（`asset`），没有独立测试库；而 `store.New()` 启动时会**自动执行表结构迁移（DDL）**。这意味着「随手跑一次集成测试」就等于「连生产库并执行 DDL」。为避免误伤生产库，集成测试加了一道安全阀：**DSN 指向的库名不像测试库时，测试直接 `Skip`，绝不连库。**

**判定规则**（纯函数，位于 `config/dsn.go`，`store` / `api` 两个包共用）：

- `config.ParseDSNDatabaseName(dsn)`：从 `user:pass@tcp(host:port)/dbname?params` 中**精确**取出 `dbname`。用 `LastIndex("@")` 定位，密码里含 `@` 也不受影响；解析不出返回空串。
- `config.IsTestDatabaseName(name)`：库名（不区分大小写）**含 `test`** 才算测试库。

> ⚠️ 绝不能退化成 `strings.Contains(dsn, "test")` 这种粗糙匹配——密码里出现 `test`（如 `user:teST123@tcp(...)/asset`）会把生产库误判成测试库，**正好在最危险的时候给出「安全」的错觉**。`config/dsn_test.go` 专门钉死了这条用例。

**默认行为**（不设任何环境变量时）：读 `config.yaml` 的 DSN → 解析库名 → 不是测试库就 `Skip`。所以在本机/生产机上直接 `go test ./...`，所有需要数据库的集成测试都会显示为 `SKIP`，**不会碰到生产库**。

**如何真正跑集成测试**：显式指向一个**独立的测试库**（不要指向生产库）：

```bash
# 方式一：环境变量优先（推荐；会打印目标库名，便于确认没连错）
ASSET_MGR_TEST_DSN='user:pass@tcp(10.0.0.120:3306)/asset_test?charset=utf8mb4' \
  go test -p 1 -count=1 ./...

# 方式二：把 config.yaml 的 DSN 临时指向测试库（库名需含 test）
```

**注意**：

- 集成测试必须用 `-p 1`（串行）。跨包并行会互相污染共享库的基线数据，导致断言抖动。
- 若设了 `ASSET_MGR_TEST_DSN`，运行时会 `t.Logf` 打出解析出的库名——**上生产前请核对这一行**，确认指向的是测试库而非生产库。
