## 1. 背景与目标

### 1.1 为什么改

现有维修单待办走云之家 **待办通知**（im-todo）。用户实测反馈：

> 「消息只能通知用户，用户已读后容易忘。」

待办通知是**消息语义**——用户点开看过，这条消息就从视野里消失了。维修工没接单、受理人没派工，系统不会再提醒第二次。

### 1.2 改成什么

云之家 **统一流程中心**（cloudflow）是**审批语义**：

| 维度 | 统一流程中心 | 待办通知（现状） |
|---|---|---|
| 待办归属 | 挂在「流程中心 → 我的待办」，**处理完才消失** | 消息列表，点开即消费 |
| 视图 | 待办 / 已办 / 我发起的 / 抄送我的 / 流程监控 | 单条消息 |
| 搜索 | 多维搜索 | 仅标题 |
| 分类 | 按多重业务维度筛选 | 仅按 appId |
| 附加信息 | 自定义字段（最多 50 个，前 3 个直接显示） | 仅基础信息 |
| 超时提醒 | 支持 `ttl` / `ttlType` | 不支持 |
| 统一监控 | 管理员可看所有流程卡在哪 | 不支持 |

**核心变化：触发点完全不变，变的是待办在云之家的「身份」。**

### 1.3 目标

- 维修单各状态流转产生的待办，在云之家以**审批任务**形式存在，不因「已读」消失
- 保持现有触发矩阵（10 行）与文案规则不变
- 与现有 im-todo **并存**，可灰度、可回退

## 2. 与现有待办通知的关系：并存，不是替换

官方文档「必读」第 2 条明确要求：

> 业务系统**必须兼容** 云之家待办集成和统一流程中心集成的数据。……业务系统需要确保此时仍能正常处理切换流程中心以前已经产生的待办数据。建议业务系统记录每条待办数据对应的集成方式（云之家待办还是统一流程中心）以及对应的 appId，在处理待办时根据待办对应的集成方式进行相应处理。

**不兼容的后果**：切换前已发出的旧待办还在用户手里，系统若一律按流程中心的方式去标记已办，这些旧待办**在云之家永远转不成已办**。

### 生产库存量（已实测）

```sql
-- 10.0.0.120/asset
SELECT state, COUNT(*) FROM repair_notify_task GROUP BY state;
-- active 5 / dealt 1 / deleted 1
```

**需要兼容的存量仅 6 条**（active + dealt）。兼容改造压力极小，但**必须做**——否则这 6 条会变成僵尸待办。

## 3. 接口与授权（已实测）

### 3.1 授权级别

| 探测 | 结果 | 结论 |
|---|---|---|
| `scope=app` 调流程中心 | `10000401 认证失败` | 级别不够 |
| `scope=team` 调流程中心 | **`1101030 参数不能为空`** | ✅ 接口**已开通** |
| `scope=app` 调 im-todo | 正常 | — |
| `scope=team` 调 im-todo | `10000401 认证失败` | 两者互不通用 |
| `scope=team` 不带 `eid` | `11000400 参数错误` | team token **必须带 eid** |

**「参数不能为空」是业务层入参校验**——请求已经进入流程中心内部，说明功能已开通，**无需额外采购**。

### 3.2 双 token

`app` 与 `team` 是两个独立凭据，互不通用。客户端目前只缓存一个 token，需扩为两套。

**具体实现（已核对行号）：**

| 项 | 位置 | 说明 |
|---|---|---|
| `Scope:"app"` 硬编码 | `integration/yunzhijia/client.go:177` | 需参数化 |
| 单 token 缓存字段 | `client.go:34/36/37/40`（`mu`/`token`/`tokenExpiry`/`refreshToken`） | 命中判断在 `client.go:141` |

| accessToken 拼接 | `client.go:234-244` 的 `tokenPath`（第 243 行拼 query） | 内部写死调 `GetAppToken`，需加 scope 变体 |

**改法（推荐）：**
1. 新增 `appMu` / `teamToken` / `teamTokenExpiry` 三件套（照抄 jsapi 模式，**不动现有 im-todo 路径**）
2. `fetchAppToken` 改为 `fetchToken(ctx, scope string)`，请求体 `Scope: scope`
3. 新增 `GetTeamToken(ctx)`；team 分支**必须带 `eid`**
4. `tokenPath` 加 scope 变体（如 `tokenPathScope`），**保留原方法**供 im-todo 调用
5. `Client` 加 `eid string` 字段，**保留 `NewClient` 签名不变**

> ⚠️ **切勿复用 `c.token`/`c.tokenExpiry` 存两种 token**：两者寿命不同，并发会互相覆盖（该客户端曾因 token 缓存踩过 K11 的坑）。
>
> `eid` 来源：config 的 `yunzhijia.EID`（`cmd/yzjsync/main.go:65` 已有用法）。

## 4. 数据模型映射

| 流程中心 | 本项目取值 | 说明 |
|---|---|---|
| `flowId` | `repair-{repair_id}` | 沿用现有 `sourceId` 格式，便于反查 |
| `activityId` | `purpose` 原文 | 英文动作码，如 `intake` / `dispatch` / `take` |
| `activityName` | 节点中文名 | 由 `flowActivityName(purpose)` 映射，如「待受理」「待接单」「维修中」 |
| `bizId` | `{sourceId}-{empID}-{purpose}` | 如 `repair-1409-127-dispatch` |
| `approver` | `employee.open_id` | 现有解析逻辑复用 |
| `creator` | `sender_id`（配置） | 为空时记告警日志并照常发送（待实测） |
| `serialNo` | `repair_order.code` | 如 `WX202609211409` |
| `title` | 现有文案标题 | 如「维修派工待接单」 |
| `urgency` | 固定 `3` | P0 不按单据紧急度映射（`flowUrgency` 常量） |

> **`bizId` 为什么含 `purpose`**：同一维修工在同一张单上可能先后持有不同节点的任务（见 §5 的 take 方案 A）。仅用 `sourceId-empID` 会让两个节点任务撞成一条。

### ⚠️ 关键：本地记录里的 `biz_id` 始终代表「当前活跃节点」

这一条是踩过坑才定下来的，改动前务必读完。

**约束**：`repair_notify_task` 的唯一键是 `(repair_id, emp_id, source_id)`，而 `source_id`（= `notifySourceID()` 的返回值）是**单号级** `repair-{id}`、**不含节点**。所以**同一维修工在同一张单上只有一条记录**——这一点无法靠「不同节点天然是不同记录」来回避（那是错误假设）。

**解法**：让这条记录里的 `biz_id` 始终指向**当前活跃节点**的审批任务。已办结的节点不再需要它的 `bizId`，所以一条记录够用：

| 时点 | 记录状态 |
|---|---|
| 派工 | `biz_id=…-dispatch`, `state=active` |
| 接单 · 第一步 | `done(…-dispatch)` → `state=dealt`（**不删**，保留流程留痕） |
| 接单 · 第二步 | upsert 把 `biz_id` 换成 `…-take`，`state` 回到 `active` |
| 报完工 | `dealOp` 查到记录，`biz_id` 已是 `…-take` → `done(…-take)` ✓ |

**由此推出两条硬约束**：

1. **flowcenter 通道下，`dealt` 的记录不得在「重新激活」时被删除**（`shouldDeleteBeforeReactivate`）。删了就等于抹掉已办结节点的留痕，A 方案的核心优点随之消失。
2. **`UpsertNotifyTask` 必须更新 `biz_id` 与 `channel`**，否则「接单 · 第二步」换不掉 `biz_id`，报完工时会去办结一个已经不存在的老节点 → 静默失效。
   - 但用「**非空才覆盖**」`IF(VALUES(x)='', x, VALUES(x))`：本表有**两个写入者**，失败路径（`recordFailure`/`markFailed`）只传业务字段、通道为空，无条件覆盖会把已记下的通道抹成空串，导致 flowcenter 待办被误判成 im-todo。

## 5. 触发矩阵 → 节点映射

沿用 `api/notify_plan.go` 的 9 个 case，逐一映射：

| # | 触发 | 现有动作 | 流程中心动作 | 节点 |
|---|---|---|---|---|
| 1 | submit 报修 | 受理人 create | `todo/send` → 资产管理员 | `intake` 待受理 |
| 2 | accept 受理 | 不发通知 | **不发新节点**（受理人待办保持） | — |
| 3 | reject 驳回 | 受理人 deal + 报修人 create | 办结「待受理」→ 发「已驳回」给报修人 | `rejected` 已驳回 |
| 4 | dispatch 派工 | 受理人 deal + 维修工 create | 办结「待受理」→ 发「待接单」给维修工 | `repair` 待接单 |
| 5 | take 接单 | 维修工 **read** | **见下方语义缺口** | `repairing` 维修中 |
| 6 | finish 报完工 | 维修工 deal + 报修人 create | 办结「维修中」→ 发「待确认」给报修人 | `confirm` 待确认 |
| 7 | confirm 确认 | 三方 deal + 结案 | 办结「待确认」+ **`instance/finish`** | — |
| 8 | return 退回 | 报修人 deal + 维修工 create | 办结「待确认」→ 发「待返工」给维修工 | `rework` 待返工 |
| 9 | cancel 取消 | 删该 sourceId 全部 + 报修人 create | **`instance/delete`** + 发「已取消」给报修人 | `cancelled` 已取消 |

### ⚠️ 语义缺口：`opRead` 在流程中心没有对应接口 —— 已定案用方案 A

现有 `opRead`（接单后把维修工待办**只置已读、本地保持未办**）在流程中心**无对应能力**——流程中心只有「标记已办」（`todo/done`）和「抄送已读」（`carboncopy/read`，那是抄送语义，不能用）。

若直接映射成「标记已办」，等于**接单即办结**：维修工在维修期间手上没有任何待办，忘了报完工就无人提醒（这正是原方案 §3.2 要避免的漏洞）。

**✅ 2026-09-23 用户拍板：采用方案 A。**

| 方案 | 做法 | 结论 |
|---|---|---|
| **A ✅ 已采用** | 接单时：办结「待接单」节点 + **同时给同一维修工发「维修中」节点** | 维修工始终持有活跃待办；流程留痕完整 |
| B | 接单时不发任何动作，待办一直挂着，到报完工才办结 | 未采用（「待接单」节点在维修期间一直显示未办，语义不准） |

#### 方案 A 的实现落点

**分流点在 `api/notify_plan.go` 的 `case model.RepairActionTake`**（那里有 `*model.RepairOrder`，文案必须在此生成——`notifyOp` 里没有单子）：

```go
if s.flowCenterEnabled {
    // A 方案：办结「待接单」节点，再给同一维修工发「维修中」节点。
    ops = append(ops, s.dealOp(o, o.AssigneeEmpID, "dispatch", true))
    title, content := takeAckCopy(o)
    ops = append(ops, s.ensureOp(o, o.AssigneeEmpID, "take", title, content))
} else {
    ops = append(ops, s.readOp(o, o.AssigneeEmpID, "dispatch")) // 开关关闭：保持原行为
}
```

`opRead` 枚举**保留不删**：开关关闭时仍产生它；回滚后若有残留的 flowcenter 待办，`deliverRead` 也要能按该条记录的 channel 把它办结。

#### 为什么必须按「每条待办自己的 channel」分派

这是整个灰度切换的地基，写错会让一半待办永远办不掉，且故障是**静默的**（用户只看到「待办一直在那儿」）：

- **新建**待办走哪个通道 → 看**当前开关** `flowCenterEnabled`；
- **办结 / 删除**已有待办 → 看**那条记录自己的 `task.Channel`**。

因为开关打开后，「切换前已用 im-todo 发出的待办」（生产存量 6 条 + 灰度期间在途的）仍躺在用户手机里，必须继续用 im-todo 的 `action` 接口办结；新发的流程中心待办必须用 `done` 接口。任何「只看全局开关」的写法都会让其中一半永远办不掉。

## 6. 免登链路的变化（重要简化）

官方文档「链接跳转」一节：

> 当用户在待办列表……点击流程时，系统将跳转到相应的链接地址，并会携带标识用户身份信息的参数(ticket)。

**云之家会自动在跳转地址后追加 `?ticket=xxx`。**

这意味着：

| | 现状（im-todo） | 流程中心 |
|---|---|---|
| 免登方式 | 后端拼 `?yzj_token=`（第 2 层） | 云之家自动追加 `ticket`（**第 0 层**） |
| 会话权限 | **只读会话**（`readonly:true`） | **完整权限会话** |

**第 2 点影响很大**：现在维修工从网页端点开待办拿到的是只读会话，**他没法接单**。换成流程中心后，`ticket` 换的是完整会话，这个限制自动消失。

因此：
- `api/notify.go` 的 `deepLink()`（约 513 行）**不再需要拼 `yzj_token`**，直接返回 `portal_base_url + /#/repairs/{id}`
- 前端 `web/src/utils/yzj-login.ts` 的第 0 层直接生效，第 2 层可保留为兜底（兼容旧的 im-todo 待办）
- `deeplink-login` 接口**保留不删**（旧待办还要用）

> ⚠️ 待实测确认：需等第一条真实流程中心待办发出后，验证 `ticket` 是否确实被追加、能否换到完整会话。

### 8.1 ✅ 外部澄清（金蝶技术支持，2026-09-23）：`typeId` 无需向云之家注册

用户向金蝶技术确认，原话：

> **「不需要在云之家注册，typeId 是由第三方系统开发人员通过这个接口传进来，具体传什么让他们自己定义。」**

这与官方文档完全一致，**不存在任何云之家侧的人工申请 / 报备 / 审批环节**：

- `typeId` 由业务系统自定（官方原文：「可以是任意值」）；
- `init` 接口**本身就是创建动作**——它按 `appId` + `appName` 创建「智能审批模板分类」
  （该 appId 对应分类已存在则不创建），再按 `typeName` 创建模板；重复调用会对现有模板做更新。
  ⇒ **「注册」这件事就是我们自己调一次 `init`**，不是去求云之家开权限。

> ⚠️ 但「无需注册」**不等于**「无需 `init`」。官方「集成过程」第 1 条原文：
> **「业务系统首次接入统一流程中心前一定要先执行初始化。」**

### 8.2 ⚠️ 三个容易踩的点（重读官方文档后补，2026-09-23）

#### ① 成功码：**不要看 `errorCode`，只看 `success`**（2026-09-23 实测更正）

官方文档里 **9 个接口的返回示例全部**是：

```json
{"success": true, "errorCode": 0, "error": null, "data": null}
```

这与 im-todo 通道**恰好相反**。im-todo 的规则是：

| 通道 | 同步成功 | 异步受理 |
|---|---|---|
| im-todo（`generatetodo`/`action`） | `errorCode=200` | `errorCode=0` + `data="{}"` |
| 统一流程中心 | **`errorCode` 不固定**（见下方实测） | —（无异步模式） |

> ⚠️ **实测更正（2026-09-23，探针 `cmd/zzflowprobe`）**：官方示例只出现了 `0`，
> 但**同一通道内 `errorCode` 并不恒定**：
>
> | 接口 | 实测 `errorCode` | `success` |
> |---|---|---|
> | `todo/send`（连发 3 次） | `0` | `true` |
> | `todo/done` | `0` | `true` |
> | `instance/finish` | `0` | `true` |
> | **`instance/delete`** | **`200`** | `true` |
>
> ⇒ **`errorCode` 既不能当成功判据、也不能当失败判据**。流程中心唯一可靠的判据是 **`success` 字段**。
> 官方示例全给 `0` 属于**示例偏差**，不是协议约束——**别把示例当规格**。

- 代码层因此是安全的：`OK()` 判的正是 `success`（`integration/yunzhijia/todo.go:128`），
  `flowcenter_test.go:153/197/250/333` 的桩数据 `errorCode:0` 断言 `OK()==true` 也仍然成立。
- **风险在读日志 / 写文档的人**：本项目在 im-todo 通道总结过「看到 `errorCode=0` 就说明 `sync` 没生效」，
  这条判据**只适用于 im-todo**；套到流程中心日志上会得出**完全相反**的结论（把成功读成失败）。
  根源是 `FlowResult = TodoResult`（两个通道共用同一个返回信封类型，却有两套成功码约定）
  ——类型复用带来的认知陷阱，解读日志前必须先确认通道。

#### ② `webUrl` / `mobileUrl` 不填 ⇒ 模板在**两端的「发起界面」都不可见**

官方原文：

| 参数 | 原文 |
|---|---|
| `mobileUrl` | 「不填则表示该模板不支持从移动端发起且**该模板在移动端不可见**」 |
| `webUrl` | 「不填则表示该模板不支持从 web 端发起且**该模板在网页端不可见**」 |

本项目 P0 把两者**都留空**（`flowcenter_web_url: ""` / `flowcenter_mobile_url: ""`）⇒
模板在两端发起界面均不可见。**这对维修单是符合预期的**（维修单只能从 FAMS 发起，
不该出现在智能审批的发起列表里），但必须写清楚，否则将来有人会误判成「模板没建成功」。

> ⚠️ 别与 `buid` 的「看不见」混淆：`buid` 填无效值影响的是**模板管理界面**（后台）；
> 我们不填 `buid` ⇒ 模板属**根组织**，**模板管理界面可见**。上线手册「智能审批后台能看到该模板」
> 这条验证点因此仍然成立。

#### ③ 别把「统一发起」和「原生流程集成」混为一谈

官方原文（文档末尾「统一发起」一节）：

> 「注意，配置统一发起**只是给业务系统提供一个统一的发起入口**……但所有审批数据仍旧在业务系统。
> **统一流程中心『我发起的』『待办』『待阅』里面并不能看到这些数据**，如果需要在这些地方看到
> 业务系统的数据，请按照**统一流程中心-原生流程集成**的方式进行**接口级别的集成**。」

| 模式 | 实现方式 | 数据出现在「我的待办 / 我发起的」？ |
|---|---|---|
| 统一发起 | 智能审批后台配置 appId + web/mobile 发起地址 | ❌ **不会** |
| **原生流程集成** | 接口级：`init` + `send` + `done` + `finish` | ✅ **会** ← **本项目采用这个** |

> 可以获得当前操作的用户身份信息」——正是本项目第 0 层免登用的那个 ticket

### 📌 设计原则：待办的生命周期由业务动作驱动，不由时间驱动（2026-09-23 确立）

| 维度 | 要求 |
|---|---|
| 待办何时消失 | 只在**处理人执行了业务动作**（办结 / 删除）后消失 |
| 超时 | **不启用**。`SendFlowTodoRequest.TTL` 保持 nil（`omitempty` → 请求体根本不带该字段），`TTLType` 留空 |
| 因此 | 待办会一直挂在「流程中心 → 我的待办」里，直到被处理——这正是流程中心相对 im-todo 的核心价值 |

**后续任何人不得擅自打开 `ttl`**：超时属于「由时间驱动待办消失」，与本原则直接冲突，需重新拍板。

#### 新发现①：待办列表按 `flowId` **聚合**，一个实例只有一条

实测（同一 `flowId` 发 3 次，覆盖 2 个不同 `activityId`）：「我的待办」里**始终只有 1 条**，
且标题/正文 = **最近一次 `send` 的内容**：

| 操作序列 | 界面显示 |
|---|---|
| `send`(node1, biz1) | 1 条：「待处理」 |
| `send`(node1, biz2，同节点) | 仍是 1 条：「待处理（第 2 条）」← 顶替 |
| `send`(node2, biz3，异节点) | 仍是 1 条：「节点2（第 3 条）」← 顶替 |

⇒ **聚合键是 `flowId`，不是 `activityId`**（异节点也没多出一条）。

**对 FAMS 的含义（正面）**：`FlowID = job.sourceID`（维修单 ID，`api/notify_flowcenter.go:143`），
所以**一个维修单在该员工待办列表里只占一行**，标题随流转自动更新（待接单 → 维修中 → …）。
不会像 im-todo 那样按节点堆成多条——这正是期望效果。

**对实现的两点影响**：
1. 「关旧节点」的必要性从「界面整洁」降级为「**实例状态正确性**」——界面本来就会顶替，
   但旧节点的 `todo/done` 仍应照常调用（接口按 `bizId` 工作，我们已实测其在被顶掉后仍成功）。
2. ⚠️ **不能靠「数待办条数」来验证流转是否正确**：一个维修单永远只显示 1 条，
   验证必须看**标题（节点名）**而不是条数。上线手册的自检步骤已据此修正。

#### 新发现②：`errorCode` 不可作成功判据

见 §8.2①。同一通道内 `send`/`done`/`finish` 返 `0`、`instance/delete` 返 `200`，`success` 均为 `true`。

#### 新发现③：`shouldDeleteForReactivate` 的原始理由已被推翻（**代码暂不动**）

`api/notify_flowcenter.go:333` 的注释原先写的理由是「flowcenter 下只删 active 的，
否则**同一人手上会同时挂两条**」。实测表明：在「我的待办」视图下**不可能同时挂两条**
（按 `flowId` 聚合），该理由不成立。

但**结论保持不变**（只删 active、保留 dealt），理由更正为：

1. 未办结的旧节点会让实例停在未完结状态，流程语义不干净；
2. 云之家的其他视图 / 角标（首页待办数、已办列表）是否仍会显示该未办结节点 —— ⏳ 未实测。

⇒ **本项只更正理由与注释，行为一行不改**。待有真实流转数据后再重新论证。
（代码注释已同步更正，见 `api/notify_flowcenter.go`。）

| 限制 | 触发条件 | 后果 | 为何 P0 接受 |
|---|---|---|---|
| 办结失败后旧节点 `bizId` 被覆盖 | `todo/done` 调用失败（云之家报错）→ 记录 `state=failed` → 随后 `deliverEnsure` 因 `state != active/dealt` 不走删除分支，直接 upsert 覆盖 `biz_id` | 旧节点在云之家侧可能仍存在，但本地已找不到它的 `bizId`，该条待办无法再被办结 | 属「外部接口失败」异常路径；有界重试 3 次 + `last_error` 落库 + 失败有日志。彻底解决需给唯一键加节点维度，改动面大，收益不成比例 |

### 已实现的兼容守卫

**混合单的 `instance/finish` 守卫**：一张单若待办**全部由 im-todo 发出**、之后开关才打开，则 confirm 时其 `flowId` 在云之家并不存在。`deliverFinishFlow` 开头用 `hasFlowCenterTask(repairID)` 查该单是否存在 `channel='flowcenter'` 的记录，不存在则跳过结案并记 info 日志。

为什么必须加：`retryFinishFlowInstance` 有 3 次退避重试，每张这类单 confirm 时会白白打 3 次 API + 3 条错误日志。
