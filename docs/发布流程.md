# 版本管理与发布流程

> 从 v1.0.0 起启用。本文说明**两个仓库怎么配合**、**版本号怎么定**、**一次发版怎么走**。

---

## 一、两个仓库

| 仓库 | 可见性 | 用途 | 本地 remote |
|---|---|---|---|
| `huangyongjie0924/fams-kingdee-dev` | **private** | **日常开发目标**。`git push` 默认推这里 | `origin` |
| `huangyongjie0924/fams-kingdee` | public | 对外展示。**按需**才推 | `public` |

```
git push                      # → 私有库（origin），日常就这样
git push public main --tags   # → 公开库，只在需要对外时手动执行
```

两个仓库**同源同历史**，公开库是私有库在某一点的快照。只要私有库的历史不被改写，
公开库就能 fast-forward，不存在「两套历史要合并」的问题。

> ⚠️ **但这条有个前提：私有库的历史没有被 force-push 改写过。**
> 一旦改写（哪怕只是 amend 一个提交），`public/main` 就不再是 `main` 的祖先，
> `git push public main` 会被拒绝，只能 `--force` —— 而那次 force 会**静默丢掉**
> 只存在于公开库的提交。
>
> 更要紧的是：**已经被推上公开库的提交，改写私有库救不了它。**
> 公开库里的历史一旦发出去就收不回来，所以「先私有、后公开」这个分工
> **只能在首次推送公开库之前保护你**。把「推公开库」当成不可逆操作对待。

### 为什么这样分

- 日常提交里有大量中间状态（重构到一半、文档还没定稿、探针脚本），不适合对外
- 公开库只在「想给人看」的时候推，推之前统一做一遍脱敏检查
- 私有库内容与公开库**完全一致**，不做两套内容——避免「私有库能跑、公开库跑不起来」

> ⚠️ **但「内容一致」不等于「可以无脑推」**。私有库里如果临时写了内网地址、真实姓名、
> 生产域名，推到公开库前必须先扫。见第四节。

## 二、版本号

采用 **SemVer**：`v主版本.次版本.修订号`

| 位 | 什么时候加 |
|---|---|
| 主版本 | 不兼容的改动（表结构破坏性变更、接口语义反转、需要停机迁移） |
| 次版本 | 向下兼容的新功能（新模块、新接口、新页面） |
| 修订号 | 向下兼容的缺陷修复 |

现状：**`v1.0.0`**（首个正式版）。历史提交在 v1.0.0 之前，未打标签。

### 标签打在哪个提交上

**标签必须打在生产实际运行的那个提交上。** 否则「版本号」就失去意义——
出了问题无法从版本号反查到代码。

判断方法：比对 Release 里记录的二进制 SHA256 与生产机上的 `/opt/asset-mgr/asset-mgr`。

> ⚠️ 但要清楚这条**只能证明「二进制一致」，不能证明「这个提交产出了它」**。
> SHA256 是脚本自己算、自己写进 Release 正文的，属于**自证**——
> 发现不了「上传的二进制其实编自别的源码」。
>
> 真正的来源证据是二进制**内嵌的构建信息**（`vcs.revision` / `vcs.modified`）。
> 见第五节，Release 正文里也会一并记录这两项。

## 三、发一次版

```bash
# 0. 工作区干净、本地与私有库同步（脚本会自己检查，不满足直接拒绝）
git status

# 1. 写发布说明（必须有，会作为 Release 正文）
#    路径约定：release-notes/v<版本>.md
vim release-notes/v1.0.1.md

# 2. 提交发布说明
git add release-notes/v1.0.1.md && git commit -m "docs: v1.0.1 发布说明"

# 3. 发版（构建前端 → 交叉编译 → 打标签 → 推送 → 创建 Release 并上传二进制）
python scripts/release.py v1.0.1 --notes release-notes/v1.0.1.md
```

脚本会做这些事，任何一步失败都会**中止并报错**：

1. **前置检查**：版本号格式、工作区干净、在 `main` 上、与 `origin/main` 同步、
   标签未被占用、`--repo` 与 `origin` 指向**同一个仓库**
2. **构建**：`cd web && npm run build` → 用**统一配方**编 linux/amd64（见下）
3. **校验产物**：确认二进制内嵌的前端产物就是**本次**构建的那批；
   确认构建信息里 `vcs.modified=false`、且 `vcs.revision` == 当前 HEAD
4. **推送分支**：`git push origin main`
5. **打标签并推送**：`git tag -a <版本>` → `git push origin <版本>`
6. **创建 GitHub Release**，附 `asset-mgr-linux-amd64`，并把本次产物的
   SHA256 / 大小 / 构建提交 / `vcs.revision` / `vcs.modified` / go 版本自动追加到 Release 正文

> **第 3 步**防的是「构建失败但产物照出」：前端构建如果失败、而磁盘上还留着上一次的 `dist`，
> `go build` 会拿旧 dist 编出一个「有产物、能启动、大小正常」的二进制，看起来完全没问题。
> 本项目实际踩到过（构建命令串在 `| tail` 里，退出码被吞掉）。
>
> **第 4 步不能省**：只推标签的话，标签与 Release 会指向一个**不在 `origin/main` 祖先链上**的
> 提交，远端 main 停在后面——「这个版本发布了」和「这个版本的代码在仓库里」就对不上了。

结束后脚本打印 SHA256，部署完拿它和服务器上的二进制比对即可确认「跑的是这版」。

### 统一构建配方

```bash
GOOS=linux GOARCH=amd64 CGO_ENABLED=0 go build -trimpath -ldflags="-s -w" -o deploy/asset-mgr .
```

| 参数 | 为什么 |
|---|---|
| `-trimpath` | 不把本机绝对路径编进去，换台机器/换个目录才可能复现出同一份产物 |
| `-ldflags="-s -w"` | 去掉符号表与 DWARF，体积小 **24%**（17.8MB → 13.4MB）；实测**不影响** `go version -m` |
| `CGO_ENABLED=0` | 显式关掉。目标机 CentOS 7，DB 驱动是纯 Go，没有引入 libc 依赖的理由 |

> ⚠️ **`README.md` 里的手工命令与 `scripts/release.py` 必须逐字一致，改配方时两边一起改。**
>
> 本项目吃过这个亏：曾经同时存在**三个二进制、三套参数**——线上实际跑的（带 `-s -w`、
> 无 `-trimpath`，sha256 `0b1b8817…`）、v1.0.0 Release 附件（无任何 flag，`4c8ad097…`）、
> 本地编的（`d101a438…`）——**互相都对不上，而且 Release 里那个附件其实从未被部署过**。
> 没有任何地方会发现这件事。配方不统一，`release.py` 算出来的 SHA256 就只能证明
> 「这个文件是这次构建出来的」，**证明不了它等于线上跑的那个**。

> 📌 脚本用 `env=` 参数传 `GOOS/GOARCH/CGO_ENABLED`，**不写成 `GOOS=linux go build` 这种命令前缀**。
> Windows 上 `shell=True` 走的是 `cmd.exe`，它不认 `VAR=value cmd`，会直接报
> `'GOOS' is not recognized`。这一点踩过：脚本最初就是这么写的，**导致构建步骤从未跑通过**，
> 而文档里还写着「任何一步失败都会中止并报错」。

### 只想检查不发布

```bash
python scripts/release.py v1.0.1 --notes release-notes/v1.0.1.md --dry-run
```

### 中断了怎么续

**直接重跑同一条命令**即可，脚本会按情况续上：

- 标签已存在且指向 HEAD → 跳过打标签，但**仍会推送标签**（幂等，已推过时 git 输出 `Everything up-to-date`）
- Release 已存在 → **复用它**，先删掉同名旧附件再重新上传

所以「标签推成功、但附件上传失败」这种也能靠重跑恢复，不需要手工收拾。

## 四、推到公开库之前

公开库是对外可见的，推之前扫一遍。**必须两条都跑**——`git grep` 只看**已跟踪**文件，
新建但还没 `git add` 的文件它看不见：

```bash
# ① 已跟踪文件（全历史，不只 HEAD）
#    用分支名而不是 --all：--all 会把 refs/original、远端缓存等一并扫进来，噪音大
git grep -nIE "<内网网段>|<口令片段>|<账号名>|<生产域名>" $(git rev-list origin/main) -- .

# ② 工作区全部文件（含未跟踪）
grep -rnIE "<同上>" --exclude-dir=.git --exclude-dir=node_modules --exclude-dir=dist .

# ③ 要判断「有没有命中」，别把 grep 串进管道 —— head 无论有没有输入都返回 0，
#    会把 git grep 的退出码吞掉，让分支判断永远走「有命中」那一边
OUT=$(git grep -lIE "<模式>" $(git rev-list origin/main) -- .)
[ -z "$OUT" ] && echo "干净" || echo "$OUT"
```

> 📌 这里**故意不写具体模式**。把要防的内容当示例抄进仓库，等于又泄漏一次；
> 而且这份文档会立刻被自己的扫描规则命中。实际模式按上面的四类自己填。

命中就要先处理。

### ⚠️ 改历史 ≠ 删掉内容（本项目实证，请务必读）

**只改工作区再提交一个新提交是不够的**——敏感内容如果在历史里，那个提交永远在。

但**改写历史也不够**。本项目实测：一个含口令片段的提交用
`git commit --amend` + `git push --force-with-lease` 改写后，本地确实不可达了
（`git branch --contains` 空、逐提交遍历 `origin/main` 零命中），
但 **GitHub 上仍能按 SHA 直接读到**：

```bash
curl -s -o /dev/null -w "%{http_code}\n" \
  -H "Authorization: Bearer $TOKEN" \
  https://api.github.com/repos/<owner>/<repo>/commits/<被改写的SHA>
# → 200，而且返回的 files[].patch 里就是那几行原文
```

**结论**：`rebase` / `amend` / `filter-branch` 只改 **ref**，不删 **对象**。
被 force-push 掉的提交变成「不可达对象」，但 GitHub 仍按 SHA 提供，且 API 会连
patch 正文一起返回。所以「我改写了历史」**不能**作为「已经清干净」的依据。

正确的处置顺序：

| 情形 | 处置 |
|---|---|
| **还没推送** | `rebase` 停在引入点就地脱敏再重放 —— **这是有效的**，对象只在本地 |
| **已推到私有库** | 改历史 **+ 视同已泄漏**：轮换相关口令/密钥；或**删库重建**（唯一能彻底清掉的办法） |
| **已推到公开库** | 同上，且更严重 —— **当成已公开**，必须轮换凭据 |

### 唯一能彻底清掉的办法：删库重建

```bash
# 需要 token 有 delete_repo scope（只有 repo scope 会 403）
curl -s -X DELETE -H "Authorization: Bearer $TOKEN" \
  https://api.github.com/repos/<owner>/<repo>
# 然后重新建库、重新推送 —— 本地历史完整，几条命令即可恢复
```

代价很小（本地有全部历史、Release 也能重建），效果彻底（对象随仓库一起删除）。
**前提是你的 token 有 `delete_repo` scope**；没有的话在网页
`Settings → Danger Zone → Delete this repository` 点一下同样可以。

> 本项目踩过两次：生产库 IP 曾写进 `docs/维修模块P0测试报告.md` 并被推到**公开库**
> （处理与验证见 `000bd9d`，那次幸运地在推送公开库之前就发现了）；
> 后来写这份文档时又把口令片段当扫描示例抄了进去，改写了历史，
> 但**对象至今仍能按 SHA 读到**。

### 不该进仓库的东西

`.gitignore` 已排除，但提交前仍值得确认：

| 文件 | 内容 |
|---|---|
| `config.yaml` / `deploy/config.yaml` | 数据库密码、JWT 密钥 |
| `.env` / `deploy/.env` | 星瀚与云之家凭据 |
| `cert/` / `*.key` / `*.pem` | 自签证书（含部署机地址） |
| `orgreset-backup/` | 组织主数据原始数据 |
| `uploads/` | 员工上传的附件 |

## 五、部署后怎么确认跑的是这版

按可靠性从高到低：

| 方法 | 命令 | 说明 |
|---|---|---|
| **内嵌构建信息** | `go version -m /opt/asset-mgr/asset-mgr` | 读出 `vcs.revision`（= 源码提交）与 `vcs.modified`。**这是唯一的来源证据** |
| 二进制比对 | `sha256sum /opt/asset-mgr/asset-mgr` | 与 Release 正文里的 SHA256 比。位相同即同一产物，但**只是同一性检查，不是来源证明** |
| 静态产物 | `curl -s http://<host>:8080/ \| grep -o 'assets/[A-Za-z0-9_-]*\.js'` | 文件名是内容哈希，只有新构建才有 |
| 服务状态 | `systemctl is-active asset-mgr` | 只能证明「服务活着」，**证明不了是新版** |

> `go version -m` 需要服务器上有 go 工具链；没有的话可以把二进制拉回本地读，
> 或直接看 Release 正文里记录的 `vcs.revision` / `vcs.modified`。

> ⚠️ 别拿 `/api/*` 的 401 当证据。鉴权中间件包在路由外层，**不存在的接口路径也返回 401**。
> 同理若前端有 SPA fallback，未知路径返回 200 也不代表文件存在。
> 判断前一定要拿一个**确定不存在**的路径做反例对照。

> 📌 本版二进制**未内嵌应用版本号**（启动日志与接口都不显示版本），但内嵌了 Go 的
> **构建信息**：`go version -m <binary>` 能直接读出 `vcs.revision`（源码提交）与 `vcs.modified`。
> 所以「跑的是哪个提交」是能查的，而且比 SHA256 更有意义——SHA256 只说明
> 「和 Release 里那个文件是同一个」，不说明它编自哪份源码。
>
> 想让**应用自身**也能报版本，可以后续加：编译时
> `-ldflags "-X main.buildVersion=$(git describe --tags)"` + 新增 `GET /api/version`，
> 那样一条 `curl /api/version` 就够了。

## 六、当前仓库状态速查

```bash
git remote -v                 # origin=私有库, public=公开库
git tag -l                    # 已发布的版本
git log --oneline -10         # 最近提交
git status -sb                # 与私有库的同步状态
git fetch public && git log --oneline public/main..main
                              # 私有库领先公开库多少（即还没对外发布的量）
                              # ⚠️ 必须先 fetch —— public/main 只是本地缓存，
                              #    不 fetch 就是过期值（发版脚本只 fetch origin）
```

## 七、重新发布一个历史版本

**什么时候用**：某个版本的 Release 附件丢了或损坏，需要用**同一个提交**重新产出并上传。
（本次重建私有库后重发 v1.0.0 就是这个场景。）

**核心约束：标签指向哪个提交，产物就必须编自哪个提交。** 否则「版本号 → 代码」的追溯就断了。
所以**不能**直接在当前 HEAD 上重编再上传——那样 `vcs.revision` 会等于当前 HEAD，与标签不符。

```bash
# 1. 先看标签指向哪个提交
git rev-parse v1.0.0^{commit}

# 2. 检出到那个提交（进入 detached HEAD）
#    web/dist 与 deploy/ 都在 .gitignore 里，checkout 不会动它们 —— 这正是能省掉
#    npm install 的原因。前提：该提交之后前端源码没有变化（用下面这条确认）
git diff --name-only 33a2e0d..main -- web/src web/package.json
git checkout 33a2e0d

# 3. 用统一配方构建
GOOS=linux GOARCH=amd64 CGO_ENABLED=0 \
  go build -trimpath -ldflags="-s -w" -o deploy/asset-mgr .

# 4. 核对：revision 必须等于第 1 步那个提交，modified 必须是 false
go version -m deploy/asset-mgr | grep -E "vcs.revision|vcs.modified"

# 5. 立刻回到 main（别忘）
git checkout main
```

然后把二进制上传到该版本的 Release，并把**真实的** SHA256 / `vcs.revision` 更新进 Release 正文：

```bash
# 取 release id 与已有附件 id
curl -s -H "Authorization: Bearer $TOKEN" \
  https://api.github.com/repos/<owner>/<repo>/releases/tags/v1.0.0
# 删旧附件（若有）
curl -s -X DELETE -H "Authorization: Bearer $TOKEN" \
  https://api.github.com/repos/<owner>/<repo>/releases/assets/<asset_id>
# 传新附件
curl -s -X POST -H "Authorization: Bearer $TOKEN" -H "Content-Type: application/octet-stream" \
  --data-binary @deploy/asset-mgr \
  "https://uploads.github.com/repos/<owner>/<repo>/releases/<release_id>/assets?name=asset-mgr-linux-amd64"
```

> ⚠️ **第 2 步的前提要真验证**。若该提交之后前端源码**有**变化，`web/dist` 是当前 HEAD
> 编出来的，拿它去配旧的后端代码是错的。此时要另开一个 `git worktree`，
> 在里面 `npm ci && npm run build` 重新构建前端。
>
> ⚠️ 第 4 步若 `vcs.modified=true`，说明工作区有未提交改动，**不要上传**。
>
> ⚠️ 这类操作**不要用 `scripts/release.py`**：它的前置检查要求标签打在 HEAD 上，
> 会强制把标签挪到当前提交，反而破坏「标签↔产物同源」。这是有意为之的约束，
> 不是缺陷——历史版本的重发本来就是少数场景，手工做更可控。
