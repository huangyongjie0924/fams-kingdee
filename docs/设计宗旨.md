## 一、宗旨原文

> 我们设计的系统应该是服务到每一位员工，提升工作便捷和高效。

**一字不改**，作为本项目的最高设计准则。下面所有内容都是对这句话的落地拆解与约束展开。

---

## 二、定位转变：从「台账工具」到「员工服务平台」

这句话本质上是一次**系统定位的转变**，不是一次功能追加。转变意味着：

- **使用者变了**：从「少数资产管理员」变成「每一位员工」。用户基数、使用频次、容错要求全部不同——管理员会为效率容忍复杂，员工只会为「值不值得」决定用不用。
- **入口变了**：从「PC 后台登录」变成「手机扫码 / 云之家工作台」。员工不会为了报个修专门登录一个系统。
- **价值主张变了**：从「台账准不准」变成「员工用不用、快不快」。台账准确是**底线**，不是**目标**；目标是让每一位员工感受到便捷与高效。

### 前后对照表

| 维度 | 过去（资产管理员的台账工具） | 现在（服务每一位员工的资产服务平台） |
|---|---|---|
| **入口** | PC 浏览器，管理员登录后台 | 手机扫码 / 云之家工作台，员工零门槛进入 |
| **使用者** | 资产管理员（少数人） | 全体员工（每一个人） |
| **第一屏内容** | 全量资产列表 + 管理工具栏（导入 / 导出 / 打标签 / 批量改状态） | 「我的资产」「我的报修」等**与我相关**的事 |
| **动作发起方** | 管理员（自上而下维护台账） | 员工（自下而上发起报修 / 领用等诉求） |
| **信息流向** | 单向：星瀚 → 台账 → 报表（以人录入为主） | 双向：员工提交 → 系统流转 → 回写履历 / 资产卡 |
| **评价标准** | 台账准不准（数据完整、与 ERP 对齐） | 员工用不用、快不快（便捷、高效、闭环） |

> 转变的**边界**：系统仍然要服务好资产管理员——「服务每一位员工」是**扩展**服务对象，不是**替换**。管理员的专业能力（批量导入、财务回填、同步治理）必须保留，且不应被员工体验的需求牺牲。

## 三、五条设计原则（含适用边界）

以下 5 条原则把宗旨变成可判定、可裁决的规则。**每条都明确「约束的是谁」**——否则一条不适用于所有场景的原则，会因为「在某个场景不成立」而被整体忽略。

### 原则 1 · 零学习成本

> 新员工无需培训、无需文档即可完成核心动作。

| 项 | 内容 |
|---|---|
| **可验收判据** | 一名从未用过本系统的员工，在不看任何说明、不经任何培训的前提下，能在 **60 秒内**完成一次报修（或其它核心动作） |
| **约束谁** | **所有面向员工的模块**（报修、领用、盘点录入、我的资产……） |
| **边界（不适用 / 放宽）** | 面向**管理员**的批量 / 高级操作（Excel 批量导入、列配置、权限管理、同步治理）——这些用户是专业岗、有培训、追求的是**效率上限与能力**，不以「60 秒上手」为约束 |
| **划界标准** | 以「目标用户是否需要被培训」划界：面向员工 → 强制；面向管理员 → 不强制，但仍要求功能可发现 |

### 原则 2 · 员工只做他必须做的事

> 系统替员工填，员工只填「只有他知道」的信息。

| 项 | 内容 |
|---|---|
| **可验收判据** | 员工提交的单据中，**手工填写**字段 ≤ **3 个**；其余字段必须由系统从已有数据（资产卡 / 主数据 / 登录态）带出 |
| **约束谁** | **所有需要员工输入**的模块 |
| **边界（不适用 / 放宽）** | 管理员录入主数据、批量回填财务字段等场景——这些场景本就以「专业、精确」为先，字段多且必须人工确认 |
| **划界标准** | 以「该字段能否由系统从已有数据推导」判定：能推导的，就不该问用户 |

### 原则 3 · 动作可预期

> 同一动作，在任何端、任何角色下，规则与反馈一致。

| 项 | 内容 |
|---|---|
| **可验收判据** | 手机与 PC、员工与管理员，对同一动作的校验规则与结果提示**完全一致**；提交后**立即**返回可追踪的标识（单号）与当前状态 |
| **约束谁** | **全部模块**（员工端与管理端都适用）——一致性是普适要求 |
| **边界** | 无例外。跨端、跨角色不得出现两套校验规则；状态名必须用业务白话（已受理 / 维修中 / 已完工），不得暴露内部枚举值 |

### 原则 4 · 信息只在源头录一次

> 不让信息在系统间漂移，也不让用户重复劳动。

| 项 | 内容 |
|---|---|
| **可验收判据** | 资产 / 使用人 / 部门 / 供应商等只从**权威源头**（星瀚托管主数据、资产卡）读取，新模块**不维护第二份**；产生的业务记录回写到相关台账（如资产卡履历），形成闭环 |
| **约束谁** | **全部模块**，含二期单据流 |
| **边界** | 主数据以星瀚为准；能引用就不冗余。**唯一例外**：为展示性能或留痕而做的**快照**（如 `count_item` 快照资产字段）允许存在，但快照是只读的历史定格，不得被当作可编辑的第二份数据源 |

### 原则 5 · 每个人都看得见与自己有关的事

> 闭环可追踪，不靠人追问。

| 项 | 内容 |
|---|---|
| **可验收判据** | 每个角色默认只看到「与自己相关」的数据；任何状态变更留痕（谁、何时、从什么到什么）；用户能**自助**查询自己发起事项的进度 |
| **约束谁** | **全部模块** |
| **边界** | 可见范围按角色收窄（员工看自己 / 主管看本部门 / 管理员看全部），但「默认按与我相关过滤」对所有角色都成立；不得出现「只有管理员能查、员工只能打电话问」 |

## 四、设计评审检查清单

任何新模块（不只是维修）在设计评审时**逐条勾选**。任一条不通过，须给出理由或调整设计。

### 原则 1 · 零学习成本

- [ ] 本模块的入口是否**唯一**，且无需培训 / 文档即可找到并进入？
- [ ] 新用户能否在不看说明的情况下完成核心动作？目标时长是否 ≤ 60 秒？
- [ ] 是否引入了多级菜单、专业术语，或强制的前置选择（如「先选公司再选部门再选资产」）？
- [ ] 面向员工的部分是否**移动端优先**（扫码 / 手机可用）？

### 原则 2 · 只做必须做的事

- [ ] 本模块是否要求用户手工填写了**本该系统带出**的信息？
- [ ] 员工手工填写字段是否 ≤ 3 个？每个是否都**不可由系统推导**？
- [ ] 是否让用户填写了身份信息（姓名 / 工号 / 部门），而登录态里已有？

### 原则 3 · 动作可预期

- [ ] 同一动作在手机端与 PC 端、不同角色下，**校验规则与结果提示是否一致**？
- [ ] 提交后是否立即返回可追踪的标识（单号）与当前状态？
- [ ] 状态名是否使用**业务白话**，而非内部代码 / 枚举值？

### 原则 4 · 信息只录一次

- [ ] 本模块是否维护了与现有主数据（资产卡 / 员工 / 部门 / 公司）**重复的第二份数据**？
- [ ] 是否**复用源头数据**，而不是让用户重新录入？
- [ ] 产生的业务记录是否**回写**到资产卡履历 / 相关台账，形成闭环？

### 原则 5 · 人人可见与自己相关的事

- [ ] 每个角色是否默认只看到「**与自己相关**」的数据，而非全量？
- [ ] 状态变更是否**留痕**（谁、何时、从什么到什么）？
- [ ] 用户能否**自助**查询自己发起事项的进度，而无需联系管理员？

### 跨切面（与现有系统的约定）

- [ ] 是否与「**每日 00:00 星瀚同步**」冲突？（托管字段会被覆盖——尤其 `asset_card.status`，见 `docs/维修流程模块需求分析.md` §3.5 风险 R1）
- [ ] 新增权限位是否在**前后端两份映射**中同步新增？（`model.rolePermissions` 与 `web/src/stores/auth.ts`）
- [ ] 是否遵循软删除约定（查询带 `deleted_at IS NULL`）与 `0` = 「未设置」哨兵值？

## 五、反例区：被本宗旨否决的设计

以下设计**已被否决**，后续任何人重新提出时，请先对照本节理由。

| # | 被否决的设计 | 违反的原则 / 决策 | 理由 |
|---|---|---|---|
| 1 | **通用工作流引擎 / 可配置审批流设计器** | 与「领域固化、不做元数据驱动」的既定决策冲突（见 `docs/项目介绍.md` 关键设计决策表） | 那套复杂度是为「服务几万家租户」才必要的；本项目只服务一个集团，引入工作流引擎是过度设计。流程要**固化成代码**，不做可视化配置 |
| 2 | **在维修模块里重建一张资产表** | 原则 4 | 资产信息以资产卡为唯一源头，重建第二份必然与星瀚同步漂移 |
| 3 | **让员工手工选资产 / 手填资产编码** | 原则 1、2 | 员工应扫码即带出资产；要求手填编码既违反零学习成本，也是重复劳动 |
| 4 | **把管理端能力直接暴露给员工端** | 原则 1、5 | 员工端不应出现批量导入 / 导出 / 批量改状态等管理工具栏；员工看到的是「与我相关」，不是「全量可管」 |
| 5 | **报修前先让员工选资产分类** | 原则 4 | 分类已在资产卡上，让员工再选一次是重复录入且容易填错 |
| 6 | **员工端与管理端各写一套校验规则** | 原则 3 | 两套规则必然随时间分叉，同一动作在不同端结果不一致 |
| 7 | **直接依赖 `asset_card.status` 表达业务状态，却不处理同步覆盖** | 原则 4 | 每日 00:00 星瀚同步会把本地置的「维修中」重置回「在用」（证据见 `docs/维修流程模块需求分析.md` §3.5 风险 R1）；状态真相必须存在业务单据里，或对同步加保护 |
| 8 | **为「服务员工」而砍掉管理员既有专业能力** | §二 转变边界 | 「服务每一位员工」是扩展服务对象，不是替换；批量导入、财务回填、同步治理等能力必须保留 |
