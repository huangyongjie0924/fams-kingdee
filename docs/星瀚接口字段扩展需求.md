# 星瀚资产卡接口字段扩展需求

> 提出方：固定资产台账系统（asset-mgr）
> 目标接口：`POST https://<your-kingdee-host>/ierp/kapi/v2/gcgs/fa/fa_asset_card/Select_AssetCard`
> 状态：待星瀚侧确认与排期
> 更新：2026-09-17（按「财务信息在星瀚是明细数据」这一口径重写）

## 一、结论（一句话）

星瀚侧资产原值 / 累计折旧 / 净值 / 含税金额 / 税额都存放在**财务信息明细子表**上，
该接口也确实返回了明细子表 `finentry`，但**只投影了 2 列（原值、净值），且这 2 列全库恒为 0**。

因此需要星瀚侧：**补齐 `finentry` 的投影列，并修正已有 2 列的取值**，
让明细数据真正落到接口返回里。台账侧无需改代码，值修好即自动对齐。

## 二、接口返回结构实测

对全量资产卡做了原始响应 dump（**227 行**，`totalCount=227`，命令见第五节），
不经过任何反序列化直接看 JSON 原文，结论如下。

### 2.1 `finentry` 是唯一承载财务信息的结构，但只有 2 列

返回体每行共 **48 个字段**，其中**只有 `finentry` 一个嵌套结构**，其余 47 个全是平铺标量。
`finentry` 内部实测只有 2 个键：

| 键名 | 出现次数 | 非零/非空次数 | 样例字面量 |
|---|---|---|---|
| `fin_originalval` | 200 | **0** | `0.0000000000` |
| `fin_networth` | 200 | **0** | `0.0000000000` |

即：**明细子表被返回了，但只投影出 2 列，且这 2 列没有任何真实数据。**
累计折旧、含税金额、税额在明细里**连键都没有**。

> 旁证：主表 47 个平铺字段里没有任何金额字段可用 —— `price`（含税金额候选）
> 227 行**全部**为 `0.000000`。也就是说金额数据**只能**从明细子表出来，
> 主表这条路本身就不存在。

### 2.2 227 行只对应 200 个资产编码 —— 存在同编码重复行

| 项目 | 数值 |
|---|---|
| 返回总行数 | 227 |
| 去重后的资产编码数 | **200** |
| 重复出现的编码数 | **27**（每个恰好 2 行） |
| 有 `finentry` 的行 | 200 |
| `finentry` 为 `null` 的行 | **27** |

27 组重复行的规律非常整齐：

- 两行 **`createtime` / `modifytime` 完全相同**，`billno` / `number` / 名称 / 类别 / 数量全部相同
- 差异只有三处：**`id`（不同）**、**`finentry`（一行有值、一行 `null`）**、
  以及其中 5 个编码的 **`bizstatus`（一行 `READY`、一行 `ADD`）**
- 带 `finentry` 的那行**永远是 `id` 较小**的那一行（27/27）
- `bizstatus` 组合分布：`READY + READY` 22 组，`READY + ADD` 5 组

以本次举例的资产编码 `12020302000003` 为例（两行原文摘录）：

```
id=2514569622389276672  bizstatus=READY  finentry=[{"fin_originalval":0.0000000000,"fin_networth":0.0000000000}]
id=2514570401640649728  bizstatus=ADD    finentry=null
```

**推测（需贵方确认）**：这种「同编码两行、id 不同、一行有明细一行没有」的形态，
很像是接口取数 SQL 把**资产卡主表与财务明细表做了 JOIN / UNION**，
而 join 条件或明细列投影没有配对。如果确实如此，那 2.1 里「列在但值为 0」
大概率就是**投影的列名没有对上明细表实际列名**（取到了默认值 0），
而不是明细表里真的没有数据。

> 对台账侧的影响：**无**。台账按 `asset_code` 落库，重复行会收敛成同一张卡
> （已核实本地 202 张卡、0 个重复编码）。但这会让 `totalCount` 不等于真实卡片数，
> 对任何消费方都是个坑，请一并说明重复行的业务含义。

### 2.3 期望值与实际值对照

以贵方给出的资产为例：

| 项目 | 星瀚界面显示 | 接口实际返回 |

## 三、具体需求

### 需求 1：修正 `fin_originalval`、`fin_networth` 的取值（必须）

这两列**已经投影出来了**，只是值恒为 0。请让它们返回明细子表上的真实数字。

> **对台账侧的影响：无需改代码。** 台账已按这两个键名做映射，只要值修对，
> 下一次同步就会自动覆盖，两边立刻对齐。

### 需求 2：补齐明细子表的投影列（必须）

请在 `finentry` 里补出以下列，并**告知实际使用的键名**（台账侧按你方回填的键名映射）：

| 需要的业务字段 | 现状 | 建议命名（仅供参考，以你方为准） |
|---|---|---|
| 累计折旧 | 明细里没有此列 | `fin_accumdep` / `fin_accumdepreciation` |
| 含税金额 | 明细里没有此列 | `fin_amountwithtax` / `fin_taxamount` |
| 税额 | 明细里没有此列 | `fin_tax` / `fin_taxamt` |

### 需求 3：明确明细子表的取值口径（待确认）

`finentry` 是数组，但**取值口径没有文档**。请确认：

- 明细是**按会计期间**存的（每期一行）吗？如果是，接口返回的是**当前期间**还是**全部期间**？
- 是否涉及**币别 / 组织 / 账簿**维度？台账只取本位币、本组织的口径，请在返回里明确。
- 一张卡可能返回**多条**明细吗？如果会，台账按什么规则取
  （第一条 / 期间最大的那条）？**请务必在回复中说明**，否则台账只能暂取 `finentry[0]`。

### 需求 4：说明同编码重复行的成因（待确认）

见 2.2：227 行对应 200 个编码，27 个编码被返回两行，差异在 `id` / `finentry` / `bizstatus`。
请确认这是**接口 SQL 的问题**（则应去重），还是**业务上确实存在两条记录**（则应说明区分规则，
并告知台账应取哪一条）。这直接决定需求 1、2 完成后台账能否拿到**正确那一行**的金额。

### 需求 5：净值是否由星瀚提供（待确认）

台账侧目前按 `净值 = 原值 − 累计折旧` 自行计算，与星瀚界面口径一致
（`359265.08 − 44908.14 = 314356.94` ✅）。

如果星瀚能直接给出净值，我们更希望**以星瀚返回值为准**（避免口径差异）。
请确认：`fin_networth` 修好后返回的就是最终净值，还是需要台账自行相减？

## 四、精度与格式要求

- **金额类**（原值 / 累计折旧 / 净值 / 含税金额 / 税额）：按元返回，保留 2 位小数，
  例如 `359265.08`、`44908.14`、`314356.94`
- 请保持**数值类型**（不要返回字符串），并保留小数位字面量
  （现状 `assetamount` 返回的是 `194.5200000000` 这种 10 位小数字面量，很好，
  台账侧按 `DECIMAL` 处理不会丢精度）
- 空值请返回 `0` 或 `null` 并保持一致，**不要混用**
  （现状明细行内是 `0.0000000000`、整个 `finentry` 又可能是 `null`，两种都要兼容）

## 五、复现方式（供你方验证）

```bash
# 1. 取 token
curl -s -X POST "https://<your-kingdee-host>/ierp/kapi/oauth2/getToken" \
  -H 'Content-Type: application/json' \
  -d '{"client_id":"<client_id>","client_secret":"<secret>","username":"<user>","accountId":"<account_id>","nonce":"<16位hex>","timestamp":"<YYYY-MM-DD HH:MM:SS>","language":"zh_CN"}'

# 2. 查询资产卡（注意 assetname / billno 必须非空，但实测不参与过滤）
curl -s -X POST "https://<your-kingdee-host>/ierp/kapi/v2/gcgs/fa/fa_asset_card/Select_AssetCard" \
  -H 'Content-Type: application/json' -H "accessToken: <token>" \
  -H "Idempotency-Key: <16位hex>" \
  -d '{"data":{"assetname":"1","billno":"1","filter":""},"pageNo":1,"pageSize":200}'

# 3. 直接看原始字面量（不要用程序反序列化后再打印，精度信息会丢）
#    预期看到： "finentry":[{"fin_originalval":0.0000000000,"fin_networth":0.0000000000}]
#    以及部分行为： "finentry":null

# 4. 分页取全量（totalCount=227，但去重后只有 200 个资产编码）
#    换 pageNo=2 再拉一次，对比两页的 number 字段即可复现重复行
```

> 复现要点：**必须直接看原始 JSON 字面量**（`curl` / `grep`），
> 不要反序列化成浮点再打印，否则 `0.0000000000` 与精度信息会被吃掉，
> 也就看不出「列在但值为 0」这个关键现象。

## 六、补充说明

- 该接口是当前租户**唯一开放**的资产卡 OpenAPI。已扫过 4 个路径基 × 19 个操作名共 76 个组合，
  除 `Select_AssetCard` 外**全部**返回 `404 Cannot found OpenAPI(or disabled)`，
  因此**无法通过换接口绕过**，只能在现有接口上补明细投影列。
- `data.filter` 参数实测**不生效**（传过滤条件仍返回全量），
  所以台账的增量同步每次实际拉的是全量（结果幂等正确，仅不省流量）。
  如需真正支持增量，也请一并评估。
- 需求 1、2 完成前，台账侧的处理方式是：**由台账人员按星瀚界面人工填写原值 / 累计折旧**
  （支持卡片表单逐个填写，也支持 Excel 批量导入），净值自动计算。
  同步不会覆盖人工填写的金额。这是临时方案，长期仍希望以接口为准。
