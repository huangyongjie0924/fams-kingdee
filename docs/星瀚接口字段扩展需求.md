## 三、已接入的字段

### 3.1 明细子表 `finentry` 的键清单

`finentry` 是数组，每张卡最多 1 条。39 个键里，台账实际取用 5 个：

| 子字段 | 语义 | 覆盖率 | 说明 |
|---|---|---|---|
| `originalfincard_originalval` | 资产原值 | 200/200 | 最小 999.08，无 0 值 |
| `originalfincard_accumdepre` | 累计折旧 | 200/200 | |
| `originalfincard_networth` | 净值 | 200/200 | 与「原值 − 累计折旧」**200/200 完全一致** |
| `originalfincard_preusingamount` | 预计使用期数（月） | 200/200 | 24~600 的整数 → 台账「财务使用期限」 |
| `originalfincard_preresidualval` | 预计残值（金额） | 194/200 | 用于反算残值率，见 3.3 |

**勾稽关系已全部验证**（200/200）：`networth == originalval − accumdepre`。
另外 `originalfincard_netamount` 与 `networth` 逐行完全相同、`originalfincard_originalamount`
有值（22 行）时恒等于 `originalval` —— 这两列是冗余列，未接入。

恒为空或恒零、暂未接入的键（13 个）：`fin_depremethod_*`、`fin_depreuse_*`（折旧方法/用途）、
`originalfincard_decval`（减值）、`originalfincard_monthorigvalchg`、`originalfincard_monthworkload`、
`originalfincard_originaldata`、`originalfincard_sourcetype*`。

**旧的 `fin_originalval` / `fin_networth` 两个键仍然保留但恒为 0** —— 是没接上数据的冗余列，
不要读它们（这正是 19:18 那次扫描误判「接口不提供金额」的原因）。

### 3.2 落库语义：财务信息整组以「星瀚这次有没有给明细」为准

- 明细带了（`finentry` 非 null）：以星瀚为准，覆盖台账
- 明细没带（那 27 行重复行）：**整组跳过，一个财务字段都不碰**

金额字段另加「大于 0 才覆盖」的闸门，避免把星瀚确实为 0 的值（如 6 张卡的预计残值为 0）
把本地值抹成 0。

### 3.3 残值率是反算的

星瀚只给**预计残值金额**，不给比率。不能直接相除就完事 —— 残值金额保留 2 位小数，
除出来的比率是 `4.999729%` ~ `5.00034%` 这种脏值。库列是 `DECIMAL(6,3)`，
四舍五入到 3 位后才收敛成干净的 `5.000` / `3.000`。

全库实测：172 张 5%、22 张 3%、6 张残值为 0（跳过，保留本地值）。

> 如果星瀚能直接提供**残值率**字段，希望能补上，比反算可靠。

### 3.4 踩过的坑：类别默认值把星瀚真值盖回去了

`syncer` 在解析明细**之前**会用资产类别的默认值预填「财务使用期限 / 残值率」
（房屋类默认 240 期 / 5%）。于是那 27 行 `finentry` 为 null 的重复行**带着非零的假默认值**，
正好骗过「大于 0 才覆盖」的闸门，把前一行刚从星瀚同步下来的真值（107 期 / 3%）又盖回去。

**表现**：全量同步后 22 张卡的残值率停在 5%（星瀚是 3%）、4 张卡的使用期限停在 240（星瀚是 99/107）。

**修复**：引入 `FinEntryPresent` 标记，合并时以「这次有没有明细」为整组开关，
不再靠逐个字段的值去猜。已加单元测试守住（`store/sync_test.go`）。

> 这个坑值得记一笔：**「大于 0 才覆盖」这种值域约定，在存在默认值填充时会失效。**

### 3.5 含税金额 / 税额：`incometax` 是进项税额

台账「财务信息」页签的另外两个金额也接上了。判断依据是**算术证据**，不是字段名：

| 子字段 | 覆盖率 | 实测规律 |
|---|---|---|
| `originalfincard_incometax` | 22/200 | 恒等于 `原值 × 13%`（22/22 精确成立） |
| —— | —— | `原值 + 税额` **恰好是整数**（21/22）：`6299.00` / `7575.00` / `5000.00` / `9499.00` / `68000.00` / `19500.00` … |

**结论**：

- `incometax` 的字面意思是「所得税」，但 13% 是增值税率，而且
  `原值 + 税额` 正好等于发票含税价 —— 所以它是**进项税额**，台账映射到「税额」。
- `原值` 是**不含税**金额，`含税金额 = 原值 + 税额`。
  （对照：`原值 × 1.13` 只能对上 17/22，而 `原值 + 税额` 对上 21/22，
  唯一那条差 0.01 是星瀚源数据本身的原值就差了 1 分。）

**为什么只写 22 张**：其余 178 张星瀚没提供税额（不是 0，是没填）。
这种情况下**不能**把「含税金额 = 原值」写进去 —— 那 178 张的原值未必是含税口径
（同为办公设备/电子设备的两批卡，一批带税额、一批不带，说明是录入差异而非类别差异）。
所以含税金额只在**能确认税额**时才落库，其余保持人工维护，前端也保持可编辑。

> 如果星瀚能对全部资产提供税额（或直接给一个「含税金额」字段），请告知，这边改成直接取用。

### 3.6 入账日期：明细里有一个独立信号（尚未接入）

`originalfincard_finaccountdate`（财务入账日期）200/200 有值，
且与主表 `realaccountdate`（已被台账用作「购入日期」）**在 147/200 张上不同**：

```
990605   主表 realaccountdate = 2017-09-15   （购入）
         明细 finaccountdate   = 2019-12-01   （财务入账）
```

也就是说这是两个不同的日期，可以填台账「财务信息」页签上的**入账时间**，
入账期间取其 `YYYY-MM`。**目前没有接入**——这一项不在原始需求里，等确认后再做。

### 3.7 两个容易误用的字段：`originalamount` / `netamount`

明细里还有两个金额字段，**名字看起来像「含税金额」，实际不是**，接入时特别容易踩：

| 子字段 | 覆盖率 | 逐行验算结果 |
|---|---|---|
| `originalfincard_originalamount` | 22/200 | 值**恒等于** `originalval`（原值）；与 `原值 + 税额` 相符的行数 **0** |
| `originalfincard_netamount` | 200/200 | 值**恒等于** `networth`（净值），200/200 |

所以：

- `originalamount` **不是**含税原值。它只在 22 张卡上有值，且那 22 张的值就等于原值本身
  （推测是「原币金额」对「本位币金额」，人民币业务下两者必然相等）。
- `netamount` **不是**含税净值，就是净值的副本。

**含税金额只能靠 `原值 + 税额` 推导**（见 3.5）——星瀚侧目前没有直接给这个数。

> 记录这一条的原因：这两个字段的覆盖率（22/200）和 `incometax` **完全一致**，
> 光看覆盖率很容易以为"星瀚对那 22 张同时给了含税金额"，进而误用。
> 判断口径只能靠**逐行验算**，既不能靠字段名，也不能靠覆盖率。
> （这条结论就是靠 `cmd/kdscan` 的指纹对比顺带发现的——见第八章。）

## 七、精度与格式

- 金额类按元返回，原始字面量是 6 位小数（如 `359265.080000`），台账按 `DECIMAL(14,2)` 落库
- 台账侧统一用 `json.Number` 接收，不做中间 `float64` 转换，避免丢精度
- 空值现状不统一：明细行内是 `0.0000000000`、整个 `finentry` 可能是 `null`，两种都要兼容

## 八、复现方式

```bash
# 1. 取 token
curl -s -X POST "https://<your-kingdee-host>/ierp/kapi/oauth2/getToken" \
  -H 'Content-Type: application/json' \
  -d '{"client_id":"<client_id>","client_secret":"<secret>","username":"<user>","accountId":"<account_id>","nonce":"<16位hex>","timestamp":"<YYYY-MM-DD HH:MM:SS>","language":"zh_CN"}'

# 2. 查询资产卡（assetname / billno 必须非空，但实测不参与过滤）
curl -s -X POST "https://<your-kingdee-host>/ierp/kapi/v2/gcgs/fa/fa_asset_card/Select_AssetCard" \
  -H 'Content-Type: application/json' -H "accessToken: <token>" \
  -H "Idempotency-Key: <16位hex>" \
  -d '{"data":{"assetname":"1","billno":"1","filter":""},"pageNo":1,"pageSize":200}'

# 3. 直接看原始字面量（不要用程序反序列化后再打印，精度信息会丢）
#    预期看到： "originalfincard_originalval":359265.080000
#    以及：     "fin_originalval":0.0000000000   ← 旧列，仍然是 0

# 4. 分页取全量（totalCount=227，去重后只有 200 个资产编码）
#    换 pageNo=2 再拉一次，对比两页的 number 字段即可复现重复行
```

> 复现要点：**必须直接看原始 JSON 字面量**（`curl` / `grep`），不要反序列化成浮点再打印，
> 否则 `0.0000000000` 与精度信息会被吃掉，也就看不出「列在但值为 0」这个关键现象。

台账侧还有一条常驻诊断命令，怀疑字段出问题时先跑它，比手写 curl 省事：

```bash
# 拉全量、列出所有字段与取值分布、展开嵌套明细、统计同编码重复行，
# 并和上次扫描的字段指纹逐字段对比
go run ./cmd/kdscan -config config.yaml

# 人员接口（-target personnel | all）
go run ./cmd/kdscan -config config.yaml -target personnel

# 确认变化无误后，把本次结果存为新基线
go run ./cmd/kdscan -config config.yaml -update

# 需要留原始报文做证据时加 -raw（注意写 Windows 路径，Go 不认 Git Bash 的 /tmp）
go run ./cmd/kdscan -config config.yaml -raw C:/tmp/kd
```

**指纹对比是这条命令里最要紧的部分**：它把「接口静默变更」从"靠人记住上次什么样"
变成了"一行命令就能看见"。基线存在 `docs/kingdee-fields-baseline.json`，
只记「字段在不在、有没有非零值、服务端生效的过滤条件」，**不记具体值**
（具体值天天变，记了只会淹没 diff）。

为什么必须记「有没有非零值」而不只记字段名：那次变更里，
旧的两个键（`fin_originalval` / `fin_networth`）**从头到尾都在**，只是永远为 0。
只比字段名的做法会得出"什么都没变"——这正是当时的误判。
实测把基线伪造成 19:18 的状态再扫一次，它报出了 **21 个 `+ 新增*有值`** 和
**16 个 `+ 新增`（恒 0）**，把「新增且有数据」和「新增但仍是空列」准确分开了。

### 8.1 资产卡接口也有服务端过滤条件


这条过滤条件**写在星瀚侧的接口配置里，不是请求参数**：请求体里传 `filter`
（空串 / `[null]` / `[(billstatus='C')]` / `[(1=1)]`）回显完全不变、行数恒为 227。

对我们来说结果恰好是对的——227 行、200 个编码，和基线完全一致，
说明我们同步的一直就是这个过滤后的集合（`billstatus='C'` 即已审核）。
但**它此前从未被记录过**，所以「接口到底返回的是不是全量」这件事一直没有依据。
现在指纹会记下它，口径一变就会报警。

### 8.2 过滤字段不必在投影里

资产卡的过滤字段 `org` **不在**它的 48 个投影字段里（投影里只有 `headusedept_*`，
没有 `org`），但过滤照常生效。所以排查「接口返回 0 行」时，
**不要**把原因归到"过滤字段没投影"上——过滤走的是实体模型字段路径，与投影列无关。

> 反过来说也成立：**投影里有这个键，不代表它有值**。
> 人员接口的 `orgstructure_number` 就在投影里，但 10633 条明细**有值 0 条**，
> 而它恰好是过滤条件引用的字段——这才是真正的 0 行原因之一。
