# 星瀚人员接口（query-personnel）字段探测

> 探测日期：2026-09-18
> 接口：`POST /v2/gcgs/base/bos_user/query-personnel`
> 复现命令：`go run ./cmd/kdscan -config config.yaml -target personnel`

## 一、结论摘要

1. **接口当前返回 0 行，不可用。** 星瀚侧给它加了一条**服务端过滤条件**，
   而该过滤条件在现有数据上匹配不到任何人。
2. **请求体无法影响这条过滤。** 试了 16 种参数名 + 14 种请求体形态 + 5 种参数位置，
   返回完全一致（`totalCount=0`、`filter` 回显不变）。过滤条件写在接口配置里，不是请求参数。
3. **同一天资产卡接口也被加了同款过滤**，但它能返回数据（227 行）。
   两个接口用的是同两个组织号 `1201` / `1202`——**资产卡拿得到、人员拿不到**。
4. **没有可绕开的替代路径。** 枚举 130 条相邻/替代路径，只有 `query-personnel` 可用；
   `bos_user/query` 存在但本应用无权限；其余全部 `Cannot found OpenAPI(or disabled)`。
5. **调整前的字段清单已固化为基线** `docs/kingdee-personnel-baseline.json`
   （27 个顶层字段 + `entryentity` 4 个子字段 / 5038 行）。
   等接口恢复，一条 `kdscan` 就能看出字段有没有跟着变。

## 二、服务端过滤条件（本次「过滤调整」的核心）

响应里 `data.filter` 会**回显服务端实际生效的过滤条件**——这是唯一能看见它的地方，
它既不在请求体里，也不在返回数据里（0 行时连字段都没有）。

| 接口 | 生效过滤条件（响应回显） | totalCount |
|---|---|---|
| 人员 | `[(entryentity.orgstructure.number = '1202' OR entryentity.orgstructure.number = '1201')]` | **0** |
| 资产卡 | `[((org.number = '1202' OR org.number = '1201') AND billstatus = 'C')]` | 227 |

调整前人员接口的回显是 `[null]`（不过滤），对应 5038 行。

### 覆盖尝试（全部无效）

`data` 里的键**全部不生效**，且 schema 宽松——传未知键也不报错：

| 位置 | 试过的写法 | 结果 |
|---|---|---|
| `data.*` | `filter` / `filterstring` / `filters` / `condition` / `conditionstring` / `expression` / `where` / `query` / `criteria` / `sql` / `searchkey` / `keyword` / `filterstr` / `filterstrs` / `searchfilter` / `extracondition` | 回显恒不变，`totalCount=0` |
| `data.*` | `number` / `name` / `enable` / `status` / `org` / `selectfields` | 同上 |
| 顶层 | `filter`（`data` 之外） | 报 `请求参数没有 data 数据` |
| 空值形态 | `filter: ""` / `"[]"` / `"()"` / `[null]` / `[(1 = 1)]` | 回显恒不变 |
| 分页 | `pageSize=1000` / `pageNo=2` | 回显里的 `pageSize` / `pageNo` **会**跟着变（说明这两个是请求参数），但行数仍为 0 |

> `data` 必须存在，缺了报 `请求参数没有 data 数据`；但里面的内容不影响查询。

### 路径枚举（130 条）

| 结果 | 路径 |
|---|---|
| 可用 | `/v2/gcgs/base/bos_user/query-personnel` |
| **存在但无权限** | `/v2/gcgs/base/bos_user/query` → `该第三方应用-sjce没有此接口访问权限` |
| 不存在 | 其余 130 条（`query-user` / `query-person` / `query-employee` / `select` / `list` / `bos_employee/*` / `bos_org/*` / `bos_orgstructure/*` …） |

`bos_user/query` 返回的是**权限**错误而不是「接口不存在」——说明它确实存在，
只是本应用 `sjce` 没被授权。这是目前唯一看得见的替代入口。

## 三、0 行的根因分析

过滤条件里用的是 `entryentity.orgstructure.number = '1202' OR '1201'`。
`1201` / `1202` 是**4 位公司编码**，从资产卡数据可以看清编码层级：

```
资产编码   12010205000001  =  1201(公司) + 0205(资产类别) + 000001(序号)
使用部门   120108 / 120117 / 120221 …   =  1201 / 1202 + 2 位部门
```

即 `1201` / `1202` 是**公司**级编码，而人员任职的组织通常是**部门**级（6 位）。
若 `entryentity.orgstructure` 指向的是部门，等值匹配 `'1202'` 必然落空 → 0 行。

另一种可能是该字段路径在 `bos_user` 上取不到值。两种情况的处理方式相同：
**都需要星瀚侧确认过滤条件**。

注意：**「过滤字段不在投影里」不是原因**。资产卡的过滤字段 `org` 同样不在它的 48 个投影字段里
（只有 `headusedept_*`，没有 `org`），但过滤照常生效。过滤走的是实体模型字段路径，
与投影列无关。

> **对同步的影响**：将来同步岗位时若按明细逐条落库，`ID-004423` 一个人就会写进 165 行。
> 必须按「工号 + 岗位」去重，或只取 `isincharge=true` / `seq=1` 的那条。
> 这个坑现在记下来，比上线后从脏数据里反推便宜得多。

> 排查记录：`entryentity` 在第一行（`administrator`）是 `null`。
> 早期版本的 `kdscan` 按**第一行**判定字段类型，会把它记成 `scalar`，
> 于是整个嵌套结构被静默漏掉。已改为按**第一个非 null 值**判定类型。

## 五、与台账现有人员数据的匹配情况

台账 `employee` 表现有 65 人。用 `emp_no` 对齐星瀚 `number`（5036 个工号）：

| 指标 | 结果 |
|---|---|
| 匹配上 | **64 / 65** |
| 唯一未匹配 | `ID-007823` 吴九 —— 该工号在星瀚侧不存在 |
| 工号匹配后姓名不一致 | **0** —— 说明 `emp_no` 是可靠的业务键，可以直接作为 upsert 键 |
| 台账 `phone` 为空、星瀚有值 | **63 人** —— 人员同步能立刻回填这 63 个手机号 |
| 台账 `dept_id = 0` | 62 人 |
| 台账 `company_id = 0` | 64 人 |

两个结论：

1. **`emp_no` 可以放心当业务键**：64 条匹配的姓名 100% 一致，没有歧义。
2. **部门/公司是台账最缺的字段（62~64 人为空），而接口恰好不提供**。
   所以人员同步能带来的增量目前只有 `phone`（以及 `name`/`active` 的校对），
   要把人员挂到部门上，必须等星瀚补投影（见下节第 3 条）。

## 六、需要星瀚侧配合的事项

1. **确认人员接口的过滤条件**：`entryentity.orgstructure.number = '1202' OR '1201'`
   是否为本意。若是，请改成能匹配到数据的组织层级（如部门编码或 `like '1201%'`）；
   若否，请移除。
2. **或为本应用 `sjce` 开通 `bos_user/query` 权限**，作为不受该过滤条件影响的替代入口。
3. **人员接口的投影需要补组织/部门字段**（如 `entryentity.orgstructure_*`）。
   当前 27 个字段里没有任何组织信息，人员无法归属到部门——
   台账 `employee.dept_id` / `company_id` 因此无法从接口获得（现有 62~64 人为 0）。
4. **`entryentity` 的重复明细建议清理**：952 人的任职明细存在重复，最极端的
   `ID-004423` 有 165 条完全相同的「副总经理」。

## 七、复现方式

```bash
# 扫描人员接口并与基线对比（当前会报「过滤条件变更」并以退出码 1 结束）
go run ./cmd/kdscan -config config.yaml -target personnel

# 两个接口一起扫
go run ./cmd/kdscan -config config.yaml -target all

# 落盘原始响应（注意路径要用 C:/ 形式，curl / go 都是 Windows 程序，
# 传 /c/tmp 会被解析成 C:\c\tmp 而静默落盘失败）
go run ./cmd/kdscan -config config.yaml -target personnel -raw C:/tmp/pn
```

`kdscan` 的字段指纹现在也记录**服务端生效的过滤条件**——这次调整之所以一开始看不见，
就是因为旧版指纹没记它：只看到「行数 5038 → 0」说不清原因，过滤条件才说得清。
