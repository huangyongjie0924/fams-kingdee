# 星瀚人员接口（query-personnel）字段探测

> 探测日期：2026-09-18
> 接口：`POST /v2/gcgs/base/bos_user/query-personnel`
> 官方文档：人员接口·电器板块（用户提供的 API 文档截图，2026-09-18 12:12）
> 复现命令：`go run ./cmd/kdscan -config config.yaml -target personnel`

## 一、结论摘要

1. **接口当前返回 0 行，不可用。** 星瀚侧给它配了一条**服务端过滤条件**，
   该条件在现有数据上匹配不到任何人。
2. **请求体无法影响这条过滤。** 官方文档的请求体参数只有
   `createtime` / `pageNo` / `pageSize` 三个，**根本没有 filter 参数**；
   `filter` 是文档里明确定义的**返回参数**（说明：「操作执行的过滤条件」）。
3. **给了 `createtime` 也没用。** 填 `2000-01-01 00:00:00`（相当于"要全量"）仍是 0 行，
   说明卡住的是过滤条件，不是时间窗。
4. **同一天资产卡接口也被加了同款过滤**，但它能返回数据（227 行）。
   两个接口用的是同两个组织号 `1201` / `1202`——**资产卡拿得到、人员拿不到**。
5. **没有可绕开的替代路径。** 枚举 130 条相邻/替代路径，只有 `query-personnel` 可用；
   `bos_user/query` 存在但本应用无权限；其余全部 `Cannot found OpenAPI(or disabled)`。
6. **调整前的字段清单已固化为基线** `docs/kingdee-personnel-baseline.json`
   （27 个顶层字段 + `entryentity` 4 个子字段 / 5038 行）。
   等接口恢复，一条 `kdscan` 就能看出字段有没有跟着变。
7. **文档写的类型和实测不符**（4 个 ID 字段 + `totalCount`），
   按文档定义 struct 会让整个反序列化失败——详见第五节。

## 二、官方文档要点

### 2.1 请求体参数（只有三个）

| 参数 | 类型 | 必填 | 说明 | 示例 |
|---|---|---|---|---|
| `createtime` | DateTime | 否 | 创建时间 | `"2026-09-18 11:44:26"` |
| `pageSize` | Integer | **是** | 分页参数，分页数量 | 10 |
| `pageNo` | Integer | 否 | 分页参数，查询页码 | 1 |

请求结构示例：

```json
{
  "data": {
    "createtime": "2026-09-18 11:44:26"
  }
}
```

**这是增量同步接口**：`createtime` 是时间水位，取该时间之后的数据。

`createtime` 确实是真参数——实测传空串或 `abc` 会报类型错误：

```
参数【createtime】的类型为 DateTime，而传入值不能转换为该类型。
```

但**填 `2000-01-01 00:00:00` 仍是 0 行**：

| `data.createtime` | totalCount | 服务端过滤回显 |
|---|---|---|
| `2026-09-18 11:44:26`（文档示例） | 0 | org 过滤，不变 |
| `2000-01-01 00:00:00` | 0 | org 过滤，不变 |
| `2026-09-18`（仅日期，也接受） | 0 | org 过滤，不变 |
| 不传 | 0 | org 过滤，不变 |
| `""` / `abc` | — | 报 DateTime 类型错误 |

### 2.3 文档证实了两件事

1. **`filter` 是返回参数，不是请求参数。** 文档把它列在「返回参数」下，层级 2（`data` 的子字段），
   说明写着「操作执行的过滤条件」。这解释了为什么传什么都无效——
   **它本来就只是回显**。
2. **`entryentity` 的文档名称是「部门分录」**，但它的 4 个子字段里
   **只有职位、负责人、行号、id，没有部门本身**。
   也就是说接口把 `entryentity` 定义成"部门分录"，却不返回是哪个部门。
   而服务端过滤条件引用的恰恰是 `entryentity.orgstructure.number` ——
   一个**既不在文档里、也不在返回里**的字段。

## 三、服务端过滤条件（本次「过滤调整」的核心）

响应里 `data.filter` 会**回显服务端实际生效的过滤条件**——这是唯一能看见它的地方。

| 接口 | 生效过滤条件（响应回显） | totalCount |
|---|---|---|
| 人员 | `[(entryentity.orgstructure.number = '1202' OR entryentity.orgstructure.number = '1201')]` | **0** |
| 资产卡 | `[((org.number = '1202' OR org.number = '1201') AND billstatus = 'C')]` | 227 |

调整前人员接口的回显是 `[null]`（不过滤），对应 5038 行。

### 覆盖尝试（全部无效）

| 位置 | 试过的写法 | 结果 |
|---|---|---|
| `data.*` | `filter` / `filterstring` / `filters` / `condition` / `conditionstring` / `expression` / `where` / `query` / `criteria` / `sql` / `searchkey` / `keyword` / `filterstr` / `filterstrs` / `searchfilter` / `extracondition` | 回显恒不变，`totalCount=0` |
| `data.*` | `number` / `name` / `enable` / `status` / `org` / `selectfields` | 同上 |
| 顶层 | `filter`（`data` 之外） | 报 `请求参数没有 data 数据` |
| 空值形态 | `filter: ""` / `"[]"` / `"()"` / `[null]` / `[(1 = 1)]` | 回显恒不变 |

> 因为它看起来像"记录的创建时间"（输出字段），而不像查询条件。
> 它是从**官方文档**里才看到的。**先要文档，再动手试。**

### 路径枚举（130 条）

## 四、0 行的根因分析

过滤条件里用的是 `entryentity.orgstructure.number = '1202' OR '1201'`。
`1201` / `1202` 是**4 位公司编码**，从资产卡数据可以看清编码层级：

```
资产编码   12010205000001  =  1201(公司) + 0205(资产类别) + 000001(序号)
使用部门   120108 / 120117 / 120221 …   =  1201 / 1202 + 2 位部门
```

即 `1201` / `1202` 是**公司**级编码，而人员任职的组织通常是**部门**级（6 位）。
若 `entryentity.orgstructure` 指向的是部门，等值匹配 `'1202'` 必然落空 → 0 行。

另一种可能是该字段路径在 `bos_user` 上取不到值。两种情况的处理方式相同：
**都需要星瀚侧确认过滤条件**。

注意：**「过滤字段不在投影里」不是原因**。资产卡的过滤字段 `org` 同样不在它的 48 个投影字段里
（只有 `headusedept_*`，没有 `org`），但过滤照常生效。过滤走的是实体模型字段路径，
与投影列无关。

## 五、⚠ 文档类型 vs 实测类型不一致

**按文档定义 Go struct 会让整个反序列化失败**——不是部分失败，是整个响应解不出来。

| 字段 | 文档 | 实测（全 5038 行） | 后果 |
|---|---|---|---|
| `id` | Long | **String**（`"1"`） | `ID int64` → `cannot unmarshal string into int64` |
| `gcgs_employmenttype1_p_id` | Long | **String** | 同上 |
| `ns_namestyle_id` | Long | **String** | 同上 |
| `entryentity.id` | Long | **String** | 同上 |
| `totalCount` | String | **Integer**（`5038`） | `TotalCount string` → 同样解不出 |
| `name` | String | String + **1 行 null** | `Name string` 收到 `null` 是安全的（Go 会留空） |
| `type` | String | String + **6 行 null** | 同上 |

另外 `entryentity.seq` 文档写 Integer、实测确实是 `int`；`isforbidden` / `isincharge`
文档写 Boolean、实测确实是 `bool`——这两个是文档与实测一致的。

> **规则**：字段类型以**实测**为准，文档只用来确认"有没有这个字段、语义是什么"。
> 实测手段就是 `kdscan` 的类型分布输出。

> 必须按「工号 + 职位」去重，或只取 `isincharge=true` / `seq=1` 的那条。
> 这个坑现在记下来，比上线后从脏数据里反推便宜得多。

## 七、与台账现有人员数据的匹配情况

台账 `employee` 表现有 65 人。用 `emp_no` 对齐星瀚 `number`（5036 个工号）：

| 指标 | 结果 |
|---|---|
| 匹配上 | **64 / 65** |
| 唯一未匹配 | `ID-007823` 吴九 —— 该工号在星瀚侧不存在 |
| 工号匹配后姓名不一致 | **0** —— 说明 `emp_no` 是可靠的业务键，可以直接作为 upsert 键 |
| 台账 `phone` 为空、星瀚有值 | **63 人** —— 人员同步能立刻回填这 63 个手机号 |
| 台账 `dept_id = 0` | 62 人 |
| 台账 `company_id = 0` | 64 人 |

两个结论：

1. **`emp_no` 可以放心当业务键**：64 条匹配的姓名 100% 一致，没有歧义。
2. **部门/公司是台账最缺的字段（62~64 人为空），而接口恰好不提供**。
   所以人员同步能带来的增量目前只有 `phone`（以及 `name`/`active` 的校对），
   要把人员挂到部门上，必须等星瀚补投影（见下节第 3 条）。

## 八、需要星瀚侧配合的事项

1. **确认人员接口配置里的过滤条件**：
   `entryentity.orgstructure.number = '1202' OR entryentity.orgstructure.number = '1201'`
   是否为本意。若是，请改成能匹配到数据的组织层级（如部门编码或 `like '1201%'`）；
   若否，请移除。
2. **或为本应用 `sjce` 开通 `bos_user/query` 权限**，作为不受该过滤条件影响的替代入口。
   这条更容易推动——只是加授权，不用动配置。
3. **`entryentity` 需要补部门字段**。文档把它定义为「部门分录」，
   但只返回职位/负责人/行号/id，**没有部门本身**；
   而过滤条件引用的 `entryentity.orgstructure.number` 更是既不在文档、也不在返回里。
   请把 `entryentity.orgstructure_*` 加进返回投影——
   否则人员无法归属到部门，台账 `dept_id` / `company_id`（现有 62~64 人为 0）永远补不上。
4. **`entryentity` 的重复明细建议清理**：952 人的分录存在重复，最极端的
   `ID-004423` 有 165 条完全相同的「副总经理」。
5. **文档的类型标注需要更正**：`id` / `gcgs_employmenttype1_p_id` / `ns_namestyle_id` /
   `entryentity.id` 文档写 Long、实测是 String；`totalCount` 文档写 String、实测是 Integer。

## 九、复现方式

```bash
# 扫描人员接口并与基线对比（当前会报「过滤条件变更」并以退出码 1 结束）
go run ./cmd/kdscan -config config.yaml -target personnel

# 两个接口一起扫
go run ./cmd/kdscan -config config.yaml -target all

# 落盘原始响应（注意路径要用 C:/ 形式，curl / go 都是 Windows 程序，
# 传 /c/tmp 会被解析成 C:\c\tmp 而静默落盘失败）
go run ./cmd/kdscan -config config.yaml -target personnel -raw C:/tmp/pn
```

`kdscan` 的字段指纹现在也记录**服务端生效的过滤条件**——这次调整之所以一开始看不见，
就是因为旧版指纹没记它：只看到「行数 5038 → 0」说不清原因，过滤条件才说得清。
