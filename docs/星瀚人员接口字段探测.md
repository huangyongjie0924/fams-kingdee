## 一、结论摘要

1. **接口已恢复，当前返回 5038 行**（过滤条件回退为 `[null]`）。
2. **0 行的根因已从"推断"升级为"实测铁证"**（详见第四节）：

## 四、0 行的根因（已实测确认，两个缺陷叠加）

过滤条件里用的是 `entryentity.orgstructure.number = '1202' OR '1201'`。
`1201` / `1202` 是**4 位公司编码**，从资产卡数据可以看清编码层级：

```
资产编码   12010205000001  =  1201(公司) + 0205(资产类别) + 000001(序号)
使用部门   120108 / 120117 / 120221 …   =  1201 / 1202 + 2 位部门
```

13:20 接口恢复后，用全量数据（5038 行 / 10633 条 `entryentity` 明细）逐条核对，
根因不再是推断：

### 缺陷一：拿 L4 公司编码做等值匹配，而人员全挂在 L5 以下

| 人员 `dpt_number` 所在层级 | 明细条数 | 占比 |
|---|---|---|
| L1 / L2 / L3 | 5 / 2 / 24 | 0.3% |
| **L4** | **431** | **4.1%** |
| **L5** | **3017** | **28.4%** |
| **L6** | **4277** | **40.2%** |
| **L7** | **2095** | **19.7%** |
| L8 / L9 | 763 / 19 | 7.4% |

`1201` / `1202` 是 **L4** 节点，而它们**被挂载的次数都是 0**：

```
1201 被挂载 0 次   某电器股份有限公司 (L4)
1202 被挂载 0 次   某家电销售股份有限公司 (L4)
12   被挂载 0 次   某电器股份有限公司（合并） (L3)
```

**88.3% 的挂载点在 L5–L7，没有任何人挂在 L4 的公司节点上**——等值匹配必然 0 行。

### 缺陷二：过滤条件引用的字段在投影里恒为空

`orgstructure_number` 出现在投影里，但 10633 条明细里**有值 0 条**（全是空串）。
`orgstructure_name` 同样恒空，只有 `orgstructure_id` / `orgstructure_fullname` 有值。
**而过滤条件偏偏用的是 `number`。**

> 注：**「过滤字段不在投影里」本身不是原因**。资产卡的过滤字段 `org`
> 同样不在它的 48 个投影字段里（只有 `headusedept_*`，没有 `org`），但过滤照常生效。
> 过滤走的是实体模型字段路径，与投影列无关。
> 这里的问题是**该实体字段在 `bos_user` 上就是空值**——两种缺陷的修法不同，
> 但结果都是 0 行。

### 建议的修法（按推荐度排序）

| # | 方案 | 实测覆盖 | 评价 |
|---|---|---|---|
| 1 | 给 `orgstructure_number` 补值，过滤条件改**前缀匹配** | 全量 | 最稳，需星瀚改投影 |
| 2 | 过滤条件改用 `entryentity.dpt_number like '1201%'` | 136 明细 / **131 人** | **当前投影就能用，无需星瀚改动** |
| 3 | 过滤条件改用 `longnumber like 'GCGS!GCGSHB!12!%'` | 全量 | 语义最准，但 `longnumber` 不在投影里 |
| 4 | 开通 `bos_user/query` 权限，绕开这个受限接口 | — | 最省事，只是加授权 |

方案 2 实测：`dpt_number like '1201%'` → 136 条 / 131 人；
`like '1202%'` → 117 条 / 113 人；合并去重 → **131 人**。
台账关心的 65 个资产使用人中 **62 人可命中**。
小缺口：`1200151`（业务支持中心二组）这类"跨支"编码不以 `1201` 开头会漏掉。

## 五、⚠ 文档类型 vs 实测类型不一致

**按文档定义 Go struct 会让整个反序列化失败**——不是部分失败，是整个响应解不出来。

| 字段 | 文档 | 实测（全 5038 行） | 后果 |
|---|---|---|---|
| `id` | Long | **String**（`"1"`） | `ID int64` → `cannot unmarshal string into int64` |
| `gcgs_employmenttype1_p_id` | Long | **String** | 同上 |
| `ns_namestyle_id` | Long | **String** | 同上 |
| `entryentity.id` | Long | **String** | 同上 |
| `totalCount` | String | **Integer**（`5038`） | `TotalCount string` → 同样解不出 |
| `name` | String | String + **1 行 null** | `Name string` 收到 `null` 是安全的（Go 会留空） |
| `type` | String | String + **6 行 null** | 同上 |

另外 `entryentity.seq` 文档写 Integer、实测确实是 `int`；`isforbidden` / `isincharge`
文档写 Boolean、实测确实是 `bool`——这两个是文档与实测一致的。

> **规则**：字段类型以**实测**为准，文档只用来确认"有没有这个字段、语义是什么"。
> 实测手段就是 `kdscan` 的类型分布输出。

```json
[0] seq=1  dpt_number=120108  dpt_name=品牌资产管理部
    orgstructure_fullname=…_某电器股份有限公司_品牌资产管理部      ← 挂 1201
[1] seq=2  dpt_number=120210  dpt_name=品牌资产管理部
    orgstructure_fullname=…_某家电销售股份有限公司_品牌资产管理部    ← 挂 1202
```

**`seq` 是明细行号，不是主职优先级**——取值范围实测到 **165**，
所以「取 `seq` 最小」既不是主职，也不唯一。
实测用「`seq` 最小」还原资产卡使用人的部门，只有 **146/227（64%）** 一致。

**没有任何字段能标明"当前主部门"。** 因此：

> **人员部门归属必须按多值处理，不能单值化。**
> 台账要补部门/公司，应当用**资产卡自身的 `headusedept_number`**，
> 而不是「使用人 → 人员接口」反推（详见
> `docs/星瀚部门接口字段探测.md` 第五节 5.3）。

### 6.3 ⚠ `entryentity` 里有大量重复明细

10633 条明细里，按「职位 + 是否负责人」去重后只剩 **5007 条——53% 是重复的**：

| 现象 | 数据 |
|---|---|
| 有明细的人 | 4759 |
| 其中明细存在重复的人 | **952**（占 20%） |
| 明细条数 > 50 的人 | 16 |
| 明细条数分布 | 1 条 3715 人 / 2~3 条 717 人 / 4~10 条 190 人 / 11~50 条 121 人 / 50+ 条 16 人 |
| 最极端 | `ID-004423` 孙七：**165 条全是「副总经理」**，`seq` 连号 1..165、`id` 也连号 |
| 职位种数最多的人 | `ID-000910` 周八：6 种 |

> **对同步的影响**：将来同步职位/部门时若按明细逐条落库，`ID-004423` 一个人就会写进 165 行。
> 必须按「工号 + 职位 + 部门」去重，或只取 `isincharge=true` 的那条。
> 这个坑现在记下来，比上线后从脏数据里反推便宜得多。

> 排查记录：`entryentity` 在第一行（`administrator`）是 `null`。
> 早期版本的 `kdscan` 按**第一行**判定字段类型，会把它记成 `scalar`，
> 于是整个嵌套结构被静默漏掉。已改为按**第一个非 null 值**判定类型。

## 七、与台账现有人员数据的匹配情况

台账 `employee` 表现有 65 人。用 `emp_no` 对齐星瀚 `number`（5036 个工号）：

| 指标 | 结果 |
|---|---|
| 匹配上 | **64 / 65** |
| 唯一未匹配 | `ID-007823` 吴九 —— 该工号在星瀚侧不存在 |
| 工号匹配后姓名不一致 | **0** —— 说明 `emp_no` 是可靠的业务键，可以直接作为 upsert 键 |
| 台账 `phone` 为空、星瀚有值 | **63 人** —— 人员同步能立刻回填这 63 个手机号 |
| 台账 `dept_id = 0` | 62 人 |
| 台账 `company_id = 0` | 64 人 |

三个结论：

1. **`emp_no` 可以放心当业务键**：64 条匹配的姓名 100% 一致，没有歧义。
2. **`phone` 是最快能回填的字段**：63 人立刻有值。
3. **部门/公司仍不能靠人员接口单值还原**（62~64 人为空）。
   `dpt_*` 已经能挂到组织树（94.5% 的人至少一个部门），
   但 `entryentity` 是多法人并行挂载、无主职标志，
   **一个工号会给出多个部门**（1016 人如此）。
   所以台账补部门归属应当走
   **资产卡 `headusedept_number` → 组织树**（227/227 可靠），
   详见 `docs/星瀚部门接口字段探测.md` 第五节。

## 八、需要星瀚侧配合的事项

> 13:20 复扫后，原第 3 条（补部门投影）**已部分兑现**——`dpt_*` 与
> `orgstructure_id/fullname` 都已补上。剩余事项如下。

1. **修正过滤条件（最高优先级）**：原配置
   `entryentity.orgstructure.number = '1202' OR … = '1201'` 有**两个独立缺陷**——
   ① 用 L4 公司编码做等值匹配，而 `1201`/`1202` 被挂载 **0 次**；
   ② 引用的 `orgstructure_number` 在投影里**恒为空**。
   建议二选一：
   - 给 `orgstructure_number` 补值，并改为**前缀匹配**；
   - 或改用 `entryentity.dpt_number like '1201%'`（**当前投影即可用，实测覆盖 131 人**）。
2. **或为本应用 `sjce` 开通 `bos_user/query` 权限**，作为不受过滤条件影响的替代入口。
   这条最容易推动——只是加授权，不用动配置。
3. ⚠ **`orgstructure_name` / `orgstructure_number` 仍是空值**。
   投影里加了这两个键，但 10633 条明细**有值 0 条**。
   要么补值，要么从投影里去掉（留着会让人以为能用来做过滤）。
4. **`entryentity` 缺少「主职」标志**。现在是多法人主体并行挂载，
   `seq` 只是明细行号（1~165），无法判断哪条是当前主部门。
   建议增加 `ismain` / `isprimary` 之类的标志位，否则人员部门归属只能按多值处理。
5. **`entryentity` 的重复明细建议清理**：952 人的分录存在重复，最极端的
   `ID-004423` 有 165 条完全相同的「副总经理」。
6. **文档需要同步更新**：
   - 类型标注：`id` / `gcgs_employmenttype1_p_id` / `ns_namestyle_id` /
     `entryentity.id` 文档写 Long、实测是 String；`totalCount` 文档写 String、实测是 Integer。
   - 字段清单：文档仍是 27 顶层 + `entryentity` 4 子字段，
     **落后于接口**（实测已是 27 + 11）。

## 九、复现方式

```bash
# 扫描人员接口并与基线对比
go run ./cmd/kdscan -config config.yaml -target personnel

# 三个接口一起扫（资产卡 / 人员 / 部门）
go run ./cmd/kdscan -config config.yaml -target all

# 落盘原始响应（注意路径要用 C:/ 形式，curl / go 都是 Windows 程序，
# 传 /c/tmp 会被解析成 C:\c\tmp 而静默落盘失败）
go run ./cmd/kdscan -config config.yaml -target personnel -raw C:/tmp/pn

# 确认变化无误后更新基线
go run ./cmd/kdscan -config config.yaml -target personnel -update
```

`kdscan` 的字段指纹现在也记录**服务端生效的过滤条件**——这次调整之所以一开始看不见，
就是因为旧版指纹没记它：只看到「行数 5038 → 0」说不清原因，过滤条件才说得清。
