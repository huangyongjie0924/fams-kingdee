# 多角色改造方案（一人可多角色）

> 状态：实施中（2026-09-24）
> 需求来源：用户明确「**不是一个单指派多个维护人员，是一个用户可多个角色同时存在**」。
> 同时包含角色改名：`viewer` → `employee`（员工）、`repair_tech` → `maintainer`（维护人员）。

---

## 0. 需求边界（不要扩大）

| # | 需求 | 落点 |
|---|------|------|
| 1 | 【只读】改名为【员工】 | `viewer` → `employee`，中文名「员工」 |
| 2 | 【维修工】改名为【维护人员】 | `repair_tech` → `maintainer`，中文名「维护人员」 |
| 3 | 角色可以多选 | **一个账号可同时持有多个角色**（不是一张单指派多人！） |
| 4 | 完工确认由发起人确认 | **当前实现已符合**（`handleConfirmRepair` 允许报修人；前端 `canConfirm` 亦然）。本方案不改语义，只做改名连带修订。 |

> ⚠️ 需求 3 的历史误读：曾按「一张维修单指派多个维护人员」设计，被用户两次否决。
> 本方案里「多选」= **账号多角色**，`repair_order.assignee_emp_id` 仍是单值，不要动。

## 1. 存储方案

**新增列，不改老列。**

```sql
ALTER TABLE sys_user ADD COLUMN roles varchar(128) NOT NULL DEFAULT '' AFTER role;
UPDATE sys_user SET roles = role WHERE roles = '' OR roles IS NULL;
```

- `roles`：逗号分隔、**无空格**、去重、按 `model.Roles` 声明顺序排序。**这是唯一事实来源。**
- `role`：**保留**，写入时恒等于 `roles` 的第一个角色（主角色）。存在两个理由：
  1. 旧 token / 旧前端仍读 `role`；
  2. **回滚安全**——把二进制换回旧版本，旧版本读到的仍是主角色，不会变成「无权限」。
- Go 侧 `EffectiveRoles()` 在 `Roles` 为空时回落到 `[]string{Role}`，所以**存量行不迁移也能正确工作**；
  上面的 `UPDATE` 是让 `roles` 列成为完整事实来源（`FIND_IN_SET` 查询依赖它），不是正确性前提。
- ⚠️ 无空格是硬约定：`api/notify_plan.go` 用 `FIND_IN_SET` 查资产管理员，带空格就查不到。

## 2. 语义约定（api 层与前端必须一致）

- **权限 = 并集**：任一角色持有该权限即放行。`model.CanAny(roles, perm)`。
- **数据可见范围 = 并集**：逐角色算出 scope 后合并；任一角色「不限」则整体不限。
  > 「不限」即全集，是并集的自然结果，**不给它开特例**——否则「A 不限 + B 受限」的行为无法解释。
- **资产可见范围三维**（`model.AssetScope`）：自己在用的（`SelfEmpID`）/ 管辖部门的（`DeptIDs`）/
  有未结单维修单的（`RepairingCardIDs`，**只由 employee 产生、不限报修人**，见 §4.5）。三维取**并集**。
- **`admin` 恒有全部权限**（与单角色版 `Can` 一致）。
- **不要直接比 `u.Role`**：多角色账号下它只是第一个角色。判断权限用 `CanAny(u.EffectiveRoles(), perm)`，
  判断角色用 `HasRole(u.EffectiveRoles(), role)`。

## 3. `model/model.go` 已提供的接口（本方案的地基，已由 lead 落地并编译通过）

```go
type User struct {
    Role  string   `json:"role"`            // 主角色 = Roles[0]
    Roles []string `json:"roles,omitempty"` // 全部角色；空则回落 [Role]
    ...
}

func NormalizeRoles(in []string) []string     // trim/去重/剔非法/按 Roles 顺序排序
func ParseRoles(s string) []string            // 解析 roles 列（逗号分隔）
func FormatRoles(roles []string) string       // 序列化（逗号分隔、无空格）
func (u *User) EffectiveRoles() []string      // 实际生效角色集合，保证非空（除非 Role 也空）
func HasRole(roles []string, role string) bool
func CanAny(roles []string, perm string) bool
func Can(role, perm string) bool              // 保留，单角色调用点/测试继续用
```

`model.Roles` 顺序 = `[admin, asset_manager, counter, dept_head, maintainer, employee]`（同时是前端展示顺序）。

## 4. 文件分工与逐点改法

### 4.1 数据与鉴权层（engineer-store）

**`store/user.go`** —— 所有 SQL 显式列名，加 `roles` 列：
- `Authenticate` / `ListUsers` / `UserByEmployee` / `GetUser`：SELECT 里加 `roles`，
  Scan 到一个 `string` 再 `u.Roles = model.ParseRoles(rolesStr)`。
- `EnsureAdmin` / `CreateSSOUser`：INSERT 时把 `roles` 一起写（= 主角色）。
- `CreateUser` / `UpdateUser`：签名从 `role string` 改为 `roles []string`，
  内部 `model.FormatRoles(roles)` 写 `roles` 列、`model.NormalizeRoles(roles)[0]` 写 `role` 列。
  **两个列必须同一条 SQL 里一起写**，否则主角色与角色集合会漂移。
- `CountEnabledAdmins`：`WHERE role = ?` → `WHERE FIND_IN_SET(?, roles) > 0 AND enabled = 1`
  （多角色下「主角色不是 admin 但持有 admin」也要算进来）。
- ⚠️ 不要用 `SELECT *`（全仓约定）。

**`api/user.go`**
- `userReq` 加 `Roles []string \`json:"roles"\``；`Role string` 保留（兼容旧前端）。
  解析：`roles := req.Roles; if len(roles) == 0 && req.Role != "" { roles = []string{req.Role} }`，
  然后 `roles = model.NormalizeRoles(roles)`。
- `validRole` → 保留给单值路径；新增 `validRoles(roles []string) bool`（归一化后为空即非法）。
- `roleBindingErr(role string, ...)` → `roleBindingErr(roles []string, employeeID, deptID int64) string`，
  语义改为「**任一**角色需要绑定就要求绑定」：
  - 含 `dept_head` 且 `deptID == 0` → 「部门负责人必须选择管辖的部门」
  - 含 `employee` / `counter` / `maintainer` 且 `employeeID == 0` → 按角色给具体文案
    （员工/盘点员/维护人员各自的文案见现文件 48/53/56 行，改名即可）
- `handleCreateUser` / `handleUpdateUser`：改成走 `validRoles` + 新 `roleBindingErr` + 新 store 签名。

  - `me.ID == id && (!HasRole(roles, RoleAdmin) || !req.Enabled)` → 挡（不能给自己摘掉 admin）

    → 走 `requireOtherAdmin()`
- `handleDeleteUser` 里 `target.Role == model.RoleAdmin` → `model.HasRole(target.EffectiveRoles(), model.RoleAdmin)`

**`api/auth.go`**
- `claims` 加 `Roles []string \`json:"rls,omitempty"\``。
- `issueToken` / `issueScopedToken` 都填 `Roles: u.EffectiveRoles()`（保留 `Role: u.Role` 不动）。
- 中间件里 `model.User{...}` 构造处加 `Roles: c.Roles`。
  **旧 token 没有 `rls` 字段**，`EffectiveRoles()` 会自动回落到 `[c.Role]`，无需兼容分支。

**`api/server.go`**

- `requireAnyPerm`：同样换成 `CanAny(userFrom(r).EffectiveRoles(), p)`（保持「命中任一权限即放行」）

**`api/sso.go`** —— `model.RoleViewer` → `model.RoleEmployee`（:78、:83），
日志 `role=%q` 改为 `roles=%q` 并打 `user.EffectiveRoles()`。

### 4.5 员工资产可见范围第三维：有未结单维修单的资产（2026-09-24 追加）

用户拍板：员工（`employee`）的资产可见范围 = **自己在用的资产 ∪ 有未结单维修单的资产**。

- **口径**：`model.AssetScope` 新增第三字段 `RepairingCardIDs []int64`（`model/model.go`）。
  非空表示可见「当前有**未到终态**维修单的资产」——待受理 / 已受理 / 待审批 / 已派工 / 维修中 /
  待确认 都算未结单（`status NOT IN (done, rejected, cancelled)`，即 `model.RepairTerminalStatuses`）。
- **不限报修人（关键）**：这是**全公司**口径，不是「我报修的」。任何人的报修单只要未结单，
  其资产就对该员工可见。理由：员工报修入口（`/api/assets?repairable=1`、`/api/assets/by-code`、
  扫码）**全部**经过 `assetScope` 门控（`api/labels.go` → `denyOutOfScope`），员工根本没法对
  看不见的资产报修，故「只看我报修的」等价于现状、是个空改动。用户明确选了「所有未结单的资产」。
- **只作用于 `employee`**：只有 `api/scope.go` 的 `RoleEmployee` 分支填这一维。
  `maintainer` / `dept_head` / `counter` / `admin` / `asset_manager` 一律不变
  （维护人员维持「看全量台账」）。
- **并集**：与 `SelfEmpID` / `DeptIDs` 取并集——`Restricted()` 与 `Allows()` 均加这一维；
  列表侧的 SQL 由 `store/card.go` 的 `scopeConds` 同口径产出（三维 → `(A OR B OR C)`，
  零值 / 单维度的产出与改动前**逐字节一致**）。
- **取数**：`store/repair.go` 新增 `ListOpenRepairCardIDs()`：
  `SELECT DISTINCT card_id FROM repair_order WHERE card_id > 0 AND status NOT IN (?,?,?)`。
  `card_id > 0` 是必须的（0 是「未设置」哨兵值）。未加额外索引，依赖 `idx_repair_card`；
  `repair_order` 只增不删，但**未结单**数量受运营现实约束（不是全表历史）。
- **首页「我的资产」卡片**：`store/dashboard.go` 的 `AssetTotalByHolder` 在 scope 之上**再 AND**
  `c.user_emp_id = ?`，故第三维被 AND 掉——卡片统计的仍是「我在用的资产」，这是**有意的**
  （标签就是「我的资产」），不要「顺手」改成并集。
- **反向验证**：临时禁用第三维（`scopeConds` 的 repairing part / `Allows` 的循环），
  `model` / `store` / `api` 三层新增用例全部变红，恢复后全绿。
