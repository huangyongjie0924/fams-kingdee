## 2. 白名单的设计依据

判定标准是**「这张单是否还挂着未兑现的外部承诺」**（云之家侧待办 + 资产卡状态），
**不是**「流转结束没结束」。按这个标准逐个状态过一遍：

| 状态 | 可删？ | 理由 |
| --- | --- | --- |
| `pending` 待受理 | ✅ | 从未被受理，云之家侧只有一条给受理人的待办，删除时由 `OnRepairDeleted` 清理 |
| `cancelled` 已撤单 | ✅ | **本轮新增**。已是终态，撤单时已跑过同一套整单清理（`deliverDeleteAll`），删除只是再确认一次 |
| `accepted` 已受理 | ❌ | 云之家侧已把待办推给了受理人，删掉本地行会让那条待办指向 404 深链 |
| `dispatched` 已派工 | ❌ | 同上，待办在维护人员手上 |
| `repairing` 维修中 | ❌ | 在办 + 写过着 `asset_card.biz_status` |
| `confirming` 待确认 | ❌ | 在办 |
| `done` 已完工 | ❌ | 终态，但删除会抹掉已完成业务的审计痕迹 |
| `rejected` 已驳回 | ❌ | 同上（**特意保留在拒绝集里，钉死「终态 ≠ 可删」**） |
| `scrapping` 报废评估 | ❌ | P1/P2 未启用 |

### 2.1 「已撤单可删」的安全前提（必须成立，否则不能放行）

**`cancelled` 的单从未写过 `asset_card.biz_status`。**

`biz_status` 全仓只有一个写入者 —— `store.applyBizStatusTx`，且只在
**进出 `repairing`** 时才写（进 → `'维修中'`，出 → `''`）。
而 `repairTransitions` 里 `cancel` 只允许三个来源：

```go
model.RepairActionCancel: {
    model.RepairPending:    model.RepairCancelled,
    model.RepairAccepted:   model.RepairCancelled,
    model.RepairDispatched: model.RepairCancelled,
},
```

**没有 `repairing → cancelled`。** 所以一张 `cancelled` 的单，其资产卡的
`biz_status` 一定是空的 ⇒ 删除它不需要回滚资产卡状态，与 `pending` 完全同理。

> ⚠️ **这条前提是白名单的承重墙**：若将来放开「维修中撤单」，
> `cancelled` 就可能带着非空的 `biz_status`，删除逻辑必须一并处理。
> 测试里有一条断言专门守它（见 §4）。

### 2.2 云之家侧的清理

`handleDeleteRepairs` 的挂载点三 `OnRepairDeleted` → `deliverDeleteAll`，
与「撤单」用的是**同一套整单清理**（删流程实例 + 删该 sourceId 下所有 im-todo）。
唯一区别是不产生任何新建待办（单据已不存在，再推待办只会把用户送到 404 深链）。

  若 2020 不在白名单，报错会指向 2020；实际报的是 2021 ⇒ **2020（已撤单）通过了白名单校验**，
