## 2. 三个承重墙设计决策

### 2.1 为什么必须独立建表，绝不能把 IT 属性加到 `asset_card`

`asset_card` 是**星瀚托管表**：每天 00:00 的同步会按 `kingdeeOwnedColumns` 白名单
**覆盖本地值**。全表只有一个本地列 `biz_status` 逃过同步，而它已被维修单据状态机独占
（唯一写入者是 `store.applyBizStatusTx`）。

⇒ 任何 IT 属性只要落在 `asset_card` 上，第二天凌晨就会被星瀚的值覆盖成空。
故新建 `it_equipment` 表，用 `card_id` 与资产卡做**可空外键**。

### 2.2 `card_id` 可空 + 唯一键，同时满足两个互斥需求

需求同时要求「一卡最多一条 IT 记录」和「任意多条资产卡上没有的设备」，这两个约束
只能靠 **MySQL 唯一索引对 NULL 不去重、对 0 去重** 这条特性同时满足：

```sql
card_id BIGINT DEFAULT NULL,
UNIQUE KEY uk_it_card (card_id)
```

- 有卡设备：`card_id = <卡ID>`，第二条同卡记录撞唯一键 ⇒ 一卡一记录。
- 无卡设备：`card_id = NULL`，任意多条共存 ⇒ 不撞键。

⚠️ **若改成 `NOT NULL DEFAULT 0`，第二台无卡设备会撞唯一键报
`Duplicate entry '0' for key 'uk_it_card'`** —— 这是本轮最容易踩的坑。

Go 侧 `0 ↔ NULL` 的双向转换**只落两处**（单一真相，防止漏改一边）：

- 读：`itSelect` 的 `COALESCE(c.card_id, 0)`
- 写：`itValueExpr("card_id")` 返回 `NULLIF(?, 0)`

### 2.3 `itScope` 从 `assetScope` 派生，而不是另写一个 switch

```go
func itScopeOf(sc model.AssetScope) model.ITScope
```

理由：两个模块的可见范围若各写一份 switch，随时间必然分叉。代价是 employee 账号会
多跑一次 `ListOpenRepairCardIDs`（`assetScope` 的第三维），结果被**刻意丢弃** ——
`RepairingCardIDs` 属维修模块语义，照搬到 IT 台账会让员工看到**别人名下**设备的 IT 配置。

## 3. 权限模型与 fail-open 风险（本轮的核心风险点）

`api/scope.go` 的 `assetScope` 是一个**逐角色累加**的 switch，`default` 分支返回
**零值 scope = 「不限」**。这意味着：

> ⚠️ **新增角色忘登记的默认后果是看到全量数据**（fail-open），而且从界面上完全看不出来。

（对照：函数入口对「角色集合为空」是 fail-closed 403。同一个函数里两种相反的默认值，
正是危险所在。）

因此本轮在 `assetScope` 与 `repairScope` **各补一个显式 `case model.RoleITAdmin:`**
并写明理由，让「IT 管理员能看全量资产台账」这件事在 diff 里可见、可被测试钉住。

权限矩阵：

| 角色 | `it.manage` | 资产台账 | 维修单 | IT 台账可见范围 |
| --- | --- | --- | --- | --- |
| `admin` | ✅ | 不限 | 不限 | 不限 |
| `asset_manager` | ❌ | 不限 | 不限 | 不限 |
| `counter` | ❌ | 不限 | 不限 | 不限 |
| `maintainer` | ❌ | 不限 | 不限 | 不限 |
| `dept_head` | ❌ | 管辖部门 | 管辖部门 | 管辖部门 |
| `employee` | ❌ | 本人在用 + 未结单维修 | 自己相关 | 本人在用（**丢掉维修维**） |
| **`it_admin`（新增）** | ✅ | **不限** | 不限 | 不限 |

`it_admin` **刻意不给 `asset.manage`**：他需要能检索全库资产才能挑设备做关联，
但不需要能改资产卡。代价是他同时能看到全量资产的金额与财务字段（原值/净值/折旧），
这是**明确接受的取舍，不是遗漏**（已写进 `api/scope.go` 的注释）。

## 5. 数据库迁移（本轮与任务 C/D 的关键区别）

任务 C/D 是**纯逻辑换版**（「无数据库迁移、无配置变更 ⇒ 回滚是二进制一步」）。
本轮**含迁移**，但迁移方式是「**启动时自动建表**」：

```go
// store/mysql.go —— schema 是固定切片，store.New() 启动时逐条执行
`CREATE TABLE IF NOT EXISTS it_equipment ( ... ) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4`
```

⇒ 老库只需换二进制，**无需手工 SQL、无需停机窗口**。这条声明已单独验证（见 §6.3）。

### 5.1 新表结构

```sql
CREATE TABLE IF NOT EXISTS it_equipment (
  id BIGINT AUTO_INCREMENT PRIMARY KEY,
  card_id BIGINT DEFAULT NULL,          -- ⚠️ 可空是承重墙（见 §2.2）
  asset_code VARCHAR(64) NOT NULL DEFAULT '',
  device_type VARCHAR(32) NOT NULL DEFAULT '',
  user_emp_id BIGINT NOT NULL DEFAULT 0, -- ⚠️ 刻意不加唯一约束：一人多机是正常业务
  dept_id BIGINT NOT NULL DEFAULT 0,
  location VARCHAR(128) NOT NULL DEFAULT '',
  purpose VARCHAR(32) NOT NULL DEFAULT '',
  status VARCHAR(16) NOT NULL DEFAULT '在用',
  is_xinchuang TINYINT(1) NOT NULL DEFAULT 0,
  brand_model VARCHAR(128) NOT NULL DEFAULT '',
  cpu VARCHAR(128) NOT NULL DEFAULT '',
  memory_gb INT NOT NULL DEFAULT 0,
  disk VARCHAR(128) NOT NULL DEFAULT '',
  os_version VARCHAR(64) NOT NULL DEFAULT '',
  remark VARCHAR(500) NOT NULL DEFAULT '',
  created_by VARCHAR(64) NOT NULL DEFAULT '',
  created_at DATETIME DEFAULT CURRENT_TIMESTAMP,
  updated_at DATETIME DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
  UNIQUE KEY uk_it_card (card_id),
  KEY idx_it_user (user_emp_id),
  KEY idx_it_dept (dept_id),
  KEY idx_it_status (status),
  KEY idx_it_code (asset_code)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4
```

### 6.4 守卫测试「能红」验证（两轮，均已还原源码）

守卫测试的价值在于**它会在真的漏配时变红**。为此做了两次注入漂移：

| 注入 | 预期 | 实际 |
| --- | --- | --- |
| 清空 `auth.ts` 的 `it_admin: ["it.manage"]` | `TestFrontendRoleTablesInSync` 红 | ✅ 报「角色 "it_admin" 的权限数量不一致：后端 [it.manage]，前端 []」 |
| 两处 `case model.RoleITAdmin:` 改成不可命中的字面量 | `TestScopeHandlesEveryRoleExplicitly` + `TestScopeITAdminExplicitInBothScopes` 红 | ✅ 两条都报错 |

> ⚠️ 第一次尝试是**直接把 `case model.RoleITAdmin:` 改名** → 编译失败
> （`undefined: model.RoleITAdminREMOVED`）。改名无法验证守卫，必须换成
> **能编译但永不命中**的字符串字面量（`case "it_admin_removed":`）才等效于「漏配」。

还原核对：`grep -c "case model.RoleITAdmin:" api/scope.go` = **2**；
`grep -c 'it_admin: \["it.manage"\]' web/src/stores/auth.ts` = **1**。

### 6.5 为什么守卫测试必须「扫源码」而不是断言行为

行为测试**无法区分**「显式写了 `case`」与「落 `default`」—— 两种写法返回的 scope
一模一样。所以 `TestScopeHandlesEveryRoleExplicitly` 是**读 `scope.go` 源码**，
断言「`model.Roles` 里每个角色要么有显式 `case`，要么在承认名单里」。

同理，前后端权限表一致性守卫是**解析** `auth.ts` 的 `rolePermissions` 对象
（正则 `(?s)role\s*:\s*\[(.*?)\]`）并逐项集合比对 `model.rolePermissions`，
而不是字符串包含。漂移的两个方向都会被点名：

- 前端多给 → 「按钮可见但点击 403」
- 前端少给 → 「后端允许但界面没入口」

## 8. 回滚（二进制一步，表保留）

```bash
cd /opt/asset-mgr && mv asset-mgr.bak-<TS> asset-mgr && systemctl restart asset-mgr
```

**两个必须知道的注意点：**

1. **`it_equipment` 表留在库里**。旧二进制从不查它 ⇒ 留着无害；若回滚前已写过 IT 数据，
   数据**不会丢**（只是旧版本看不到）。故本轮回滚**不需要 SQL**。
2. ⚠️ **旧二进制的 `NormalizeRoles` 会把 `it_admin` 当非法值过滤掉**：

   ```go
   for _, r := range Roles {   // 旧版本的 Roles 里没有 it_admin
       if set[r] { out = append(out, r) }
   }
   ```

   ⇒ **单独持有 `it_admin` 的账号回滚后 `EffectiveRoles()` 变空** ⇒ `assetScope`
   入口 fail-closed ⇒ 403，即**登录后看不到任何数据**（而**不是**看到全量）。

   这是**安全的降级方向**，但回滚前需确认是否有账号单独持有该角色；若有，
   要么回滚后临时给它补一个别的角色，要么接受它暂时不可用。

## 9. 已知限制 / 遗留

- **未在生产库真实落一条 IT 设备记录**：验收停在「本地真库 + 真 HTTP 往返」与
  「老库自动建表」这两步。功能可用性已由 §6.1/§6.2/§6.3 共同证明；如需 100% 端到端，
  可由用户授权后在生产建一条（可删，非破坏性）。
- **导入要求「资产编码必填」而页面表单允许留空**：导入是批量、可重复的动作，
  `asset_code` 是唯一匹配键；编码可空的话同一份文件导两次就会**静默复制**每台无卡设备
  —— 静默重复是导入最危险的失败方式。页面表单是一次一条，不受此限。
- **创建接口不按 `asset_code` 判重**（只按 `card_id`），故页面上可以建出两条同编码记录；
  此时再导入该编码会被拦（「IT 台账里有 N 条同编码记录，无法判定更新哪一条」）。
  这是刻意的：页面允许「先录后改」，导入必须无歧义。
- **`C:/tmp/mysql-fams-e2e` 与 `C:/tmp/mysql-fams-it` 两个测试 datadir 未真正清理**：
  `safe-delete` 守卫拦下了 `shutil.rmtree`（`[SAFE_DELETE_BULK_CONFIRM_REQUIRED]
  {"count":193,"threshold":50}`），属非阻塞提示。需要清理请授权。
- **前端仍无回归护栏**：`it_probe.py` / `it_e2e.py` 是一次性脚本，未进仓。
  建议把「导出 → 原样导回 → 断言 created=0」这条链做成可重复的冒烟脚本。
