全站界面设计方案

把已经落地的「工业简约」语言从登录页扩展到全部 26 个视图，并把按模块堆叠的导航重组为按任务组织。方案定位是演进，不是推翻——保留现有信息密度、双端分叉与数据结构，只统一视觉语言、收敛导航层级、补齐移动端。

四个核心结论

  • 登录页与内页是两个产品。登录页是石墨黑 + 信号黄 + 2px 硬边；内页是 Element Plus 默认蓝 #409eff + 8px 圆角 + 默认阴影。用户一进系统就感到「换了个人做的」。
  • 导航按「系统有什么」组织，不按「我要做什么」。12 项平铺、无分组，维修三入口（我的报修 / 我的维修 / 维修管理）命名相近、靠权限位隐式区分，用户需要先知道自己是什么角色才能找到入口。
  • 列表页把 12 个控件平等地铺在一行。主操作「新建资产」被「批量」压在第二位，没有主次；批量操作常驻占位，而它是低频动作。
  • 移动端只有汉堡抽屉。扫码是移动端最高频的动作，却要「点汉堡 → 找扫码」两步；且没有底部标签栏，单手够不到顶部。

改完的形态

01 统一语言

一套 token 贯穿全站：石墨黑结构色、信号黄交互色、钢灰中性阶、2px 硬边、发丝线替代阴影。Element Plus 通过 --el-* 变量整体对齐，不改任何页面结构。

02 任务导航

侧栏重组为「日常 / 维修 / 盘点 / 数据 / 系统」五组；维修入口收敛为 2 项，其余视图在页面内用分段切换承载。路由一行不改，深链全部保留。

03 移动优先

补底部标签栏（工作台 / 资产 / 扫码 / 维修），扫码从抽屉里提到一级；报修走右下悬浮按钮。云之家免登的只读会话不显示标签栏。

投入产出比最高的第一步：新增一个 web/src/styles/tokens.css（约 120 行），覆盖 Element Plus 的主题变量。这一步不碰任何页面组件，却能让 26 个视图同时从「默认蓝」变成「工业简约」，是全案性价比最高的一刀。

1.2 导航按模块组织，且靠权限位隐式表达角色

SideMenu.vue 共 12 个一级项，全部平铺、无分组、仅两层。维修相关的三项尤其容易混淆：

菜单文案权限位实际去向用户需要先知道什么
我的报修repair.report/repairs/mine「我提交的单」
我的维修repair.handle/repairs?mine=1「派给我处理的单」
维修管理repair.dispatch/repairs「全量维修单」

三者语义分别是「我提交的 / 我处理的 / 全部」，但文案只差一个字。用户必须先知道自己持有哪些角色，才能推断该点哪个——这是典型的把实现细节暴露给用户。

值得注意的是，Home.vue 里已经有一段正确处理这件事的逻辑 repairEntry computed：按权限优先级决定入口标题与去向。它证明了正确做法，但只在工作台生效，侧栏没跟上。

典型症状：Main.vue:77 品牌标题 15px，Home.vue 页面标题 22px，列表页标题 20px——同一层级的元素在不同页面尺寸不同。用户感知到的不是「丰富」，而是「不整齐」。

1.4 列表工具栏 12 个控件平铺，无主次

asset/List.vue 工具栏从左到右依次是：批量 · 新建 · 编辑 · 调整状态▾ · 删除 · 打印标签 · 导出 · 扫码 · 弹性空隙 · 搜索框 · 高级搜索 · 列配置。

  • 主操作「新建」排在第 2 位，被低频的「批量」压在前面。
  • 「批量 / 编辑 / 删除」是模式性动作，却在未选中任何行时也常驻，点了才提示「请先选择」。
  • 搜索框被挤在右侧、宽度受限，而检索是最高频动作。

这违反 Hick 定律：选项越多、决策越慢；也违反「主操作应当唯一且显眼」的通行做法。

1.5 移动端没有一级导航

Main.vue:23 移动端只有一个汉堡按钮打开 el-drawer。问题有三：

  • 两步才到扫码。SideMenu.vue:11 的扫码项 v-if="isMobile"——说明产品已经意识到移动端才需要扫码，却把它藏在抽屉里。
  • 拇指够不到顶部。汉堡按钮在左上角，单手竖握时是屏幕最难点到的位置之一。
  • 没有「当前在哪」的持续提示。抽屉关闭后无任何导航状态可见。

1.6 深色侧栏的选中态缺失，品牌区与登录页断裂

  • SideMenu.vue:67 .menu{border-right:none}——Element 默认的选中态右侧指示条被去掉了，只靠背景色变化区分，弱。
  • Main.vue:4 品牌区是纯文字「固定资产台账」，没有任何标识；登录页已经接了集团 logo 铭牌，两侧不连贯。
  • 顶栏只有角色标签和用户下拉，没有面包屑或页面标题——进入 /master/category 这类深层页面后，顶栏无法回答「我在哪」。

1.7 哪些不该动（同样重要）

诊断不是「全盘否定」。以下经核实是好的设计，方案必须保留：

保留：信息密度

表格行高、字号密度适合企业台账场景。桌面端一屏能看到 12+ 行是正确的，不要为了「呼吸感」把它改成 6 行。

保留：双端有意分叉

List.vue 桌面用表格 + 分页、窄屏改用 .m-card 卡片列表，源码注释已说明「列配置对卡片没有意义」。分叉是对的，缺的是统一视觉语言。

保留：对比度达标

现有配色对比度优于 WCAG AA。改造中任何新配色都必须复测，不能为了「高级灰」把文字压到 4.5:1 以下。

保留：工作台结构

问候条 / 待我处理 / 概览卡 / 快捷入口四段结构清晰，repairEntry 逻辑正确。只需统一视觉，不动结构。

02设计原则

五条原则，后续每一个决策都可以回溯到其中一条。

原则 01

任务优先于模块

导航回答「我要做什么」，不回答「系统里有什么」。维修三入口收敛、盘点两项分组、基础数据折叠，都是这条原则的直接结果。

依据：Jakob 定律——用户把大部分时间花在别的系统上，期望本系统遵循同样的心理模型。

原则 02

一屏一个主按钮

每屏最多一个实心黑按钮。其余动作降级为描边或纯文字，危险动作额外加确认。工具栏里常驻的「批量」改为选中后才浮出的操作条。

依据：Hick 定律——选项数量增加，决策时间对数上升。

原则 03

工业语汇，克制表达

沿用登录页：石墨黑 + 信号黄 + 2px 硬边 + 发丝线。去掉圆润的 8px 圆角与默认投影——工业感来自「精确」而非「装饰」。

这不是审美偏好：硬边与发丝线在高密度表格里比投影更少干扰，扫描效率更高。

原则 04

数据用等宽，标签用无衬线

资产编码、金额、日期、单据号一律等宽字体并右对齐。等宽让数字位对齐，用户能一眼看出量级差异；无衬线中文承担标签，保证可读性。

依据：表格数字对齐是财务/台账类界面的基础要求，也是「专业感」的主要来源之一。

原则 05

移动端是一等公民

高频动作（扫码、报修）必须一步直达且落在拇指区。底部标签栏固定 4 项，其余走抽屉。云之家免登的只读会话不显示标签栏。

依据：Fitts 定律——目标越小越远，命中越慢；底部是单手竖握的最优区域。

贯穿全案的硬约束

只改呈现，不改契约

本方案不改动任何路由 path 或 route name。云之家待办深链形如 #/repairs/2019 已经发到员工手机上，一旦改名全部失效。导航只改「怎么显示」，不改「去哪」。

3.2 维修入口收敛：一个入口，按角色定标题

把「我的报修 / 我的维修 / 维修管理」三项收敛为两项：一个创建动作，一个查看动作。查看动作的标题与去向由权限优先级决定。

权限条件（优先级从上到下）菜单标题去向页面内分段切换
repair.dispatch || repair.manage维修工单/repairs全部 · 待我处理 · 我提交的
repair.handle待我处理/repairs?mine=1待我处理 · 我提交的
repair.report（兜底）我的报修单/repairs/mine我提交的
这段逻辑已经写好了，不需要新写。Home.vue 的 repairEntry computed 已经实现了完全相同的优先级判断。落地时只需把它从 Home.vue 提到一个共享模块（如 composables/useRepairEntry.ts），侧栏与工作台共用同一份，避免两处漂移。

为什么是「收敛 + 页内切换」而不是「保留三项」

  • 多角色用户不再丢视图。一个账号同时持有 asset_manager 和 maintainer 时，旧方案按优先级只给一个入口，另一类视图被隐藏。改为页内分段切换后，三个视图都在同一个页面里可切换。
  • 导航项数与角色解耦。侧栏项数不再随权限组合变化，视觉稳定，用户换角色后不需要重新学习导航结构。
  • 符合用户心理模型。用户想的是「看维修单」一件事，而不是「我的维修」和「维修管理」两件事。

3.3 移动端底部标签栏

桌面端侧栏保持现状（固定 186–200px），移动端补一个 4 格底部标签栏，把最高频的动作提到拇指区。

三条必须遵守的实现约束

  • 只读会话不显示。auth.readonly（云之家深链免登）为真时，侧栏与抽屉都已经隐藏，标签栏必须同样隐藏，否则出现「能点但点了 403」。
  • 主内容区要留出底部空间。标签栏固定 52px + env(safe-area-inset-bottom)，.main 需相应增加 padding-bottom，否则列表最后一行被遮住。
  • 抽屉保留。标签栏只放 4 项高频，完整菜单仍在汉堡抽屉里——标签栏是补充不是替代，这样低权限账号也不会有空位。
注意 useIsMobile 的定义：(max-width: 767px), (max-height: 520px)。第二个条件是高度断点，用于兜住横屏手机。标签栏必须挂在同一个 isMobile 判断上，否则横屏手机竖屏切换时会出现「有侧栏又没标签栏」的中间态。

7.1 关键技术实现：Element Plus 变量覆盖

本项目已有成功先例——登录页的 .submit { --el-button-size: 48px } 就是局部覆盖 EP 变量。全站层面只需把覆盖点提到 :root：

:root {
  /* 结构色 —— 取代 Element 默认蓝 */
  --el-color-primary:        #14171b;
  --el-color-primary-light-3:#3d454f;
  --el-color-primary-light-5:#6b7480;
  --el-color-primary-light-7:#c3c9d0;
  --el-color-primary-light-8:#dde1e6;
  --el-color-primary-light-9:#eef1f4;
  --el-color-primary-dark-2: #000000;

  /* 语义色 —— 整体压暗，适配工业基调 */
  --el-color-success:#2f8f4e;  --el-color-warning:#c9781a;
  --el-color-danger: #c0392b;  --el-color-error:  #c0392b;
  --el-color-info:   #5c6470;

  /* 硬边与发丝线 */
  --el-border-radius-base:2px; --el-border-radius-small:2px;
  --el-border-radius-round:2px;
  --el-border-color:#dde1e6;   --el-border-color-light:#eef1f4;
  --el-border-color-lighter:#eef1f4;

  /* 文字层级 */
  --el-text-color-primary:#14171b;  --el-text-color-regular:#3d454f;
  --el-text-color-secondary:#6b7480; --el-text-color-placeholder:#8d959f;

  /* 投影只保留一档 */
  --el-box-shadow-light:0 1px 3px rgba(20,23,27,.06);
  --el-font-size-base:14px;
}
⚠️ 一个必须记住的 EP 陷阱：.el-button--large 的高度是硬编码的（--el-button-size:40px），不读 --el-component-size-large。所以只覆盖上面这些变量时，输入框会变高而按钮不会——登录页已经踩过这个坑。如果 P0 要统一表单控件高度，必须同时给按钮加 --el-button-size。

7.2 风险清单

风险说明应对
全站配色突变 P0 一次性影响 26 个视图，可能有页面依赖「primary = 蓝色」的隐含假设（如自定义的浅蓝底提示条）。 用已有能力做全站回归：把 CDP 截图脚本扩展为逐路由截图，改动前后各跑一遍逐页比对。
深色侧栏对比度回退 侧栏底色从 #2b3245 改为 #14171b 后，次级文字 #c8cddb 的对比度会变化，可能跌破 4.5:1。 必须复测。登录页改版时已建立方法：CDP 取 getComputedStyle 真实色、半透明前景先与背景合成再算比值。
权限表漂移 导航改造会碰到 auth.can() 的调用点。前端 rolePermissions 与后端 model.rolePermissions 必须逐项一致，历史上真实漂移过一次（asset_manager 多出 sync.manage，导致按钮可见但点击 403）。 本次改造不新增也不修改任何权限位，只调整 v-if 的呈现位置。改完核对一遍两个文件的权限表逐项相等。
只读会话露出写入口 云之家深链免登的会话 auth.readonly = true，侧栏与抽屉已隐藏。新增底部标签栏时若漏掉这个判断，会出现「点得下去但 403」。 标签栏、FAB、侧栏三处必须用同一个 !auth.readonly 条件。建议抽成一个 computed 统一引用。
深链失效 云之家待办里的链接形如 fams.example.com:8448/#/repairs/2019，已经推送到员工手机。路由一旦改名，历史待办全部打不开。 本方案零路由改动（见 3.4 映射表）。落地时必须逐条核对 path 与 route name 未变。
构建与部署 前端改动必须重新构建才生效（web/dist 被 go:embed 进二进制）；npm run build 会因批量删除守卫中止。 沿用已固化的流程：先把 web/dist 移出仓库再构建；构建后用首页 JS 文件名作为版本指纹验收；对生产环境直接截图做最终确认。
顺手「优化」业务约束 视觉改造时容易把 MANUAL_EXCLUDED_STATUSES（维修中/调拨中不可手动改状态）当成多余的禁用逻辑删掉。次日星瀚同步会抹掉本地改动，用户会认为系统丢数据。 P4/P5 改动列表页与详情页时，业务逻辑一行不动，只改呈现。

7.3 验收清单

每期上线后逐项确认，全部通过才算完成：

  • 首页引用的 JS 文件名已变化（版本指纹）
  • 对生产环境截图，页面真实渲染新设计（不是只看本地产物）
  • 全站对比度复测：所有正文 ≥ 4.5:1，大字号 ≥ 3:1
  • 各角色账号逐一登录，侧栏分组正确、无空组
  • 云之家免登的只读会话：无侧栏、无抽屉、无标签栏、无 FAB
  • 历史深链可打开：#/repairs/{id} 至少测一张真实单据
  • 窄屏与横屏（高 ≤520px）两种触发条件都验证标签栏与留白
  • 写操作按钮 loading 期间不可重复提交（报修、批量更新）
  • 浏览器控制台运行时异常 0 条
