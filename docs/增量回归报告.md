### 3.4 验证方法论（重要，避免以后被 401 骗过）

**「`/api/dashboard` 返回 401」不能作为「新路由已注册」的证据。** 鉴权中间件包在 `mux` **外层**（`api/auth.go` `Authenticate`），任何 `/api/*` 请求（**包括根本不存在的路径**）都会先被鉴权拦成 401，与路由是否注册无关：

```
GET /api/dashboard         -> 401   ← 未带 token，无法据此判断路由存在
GET /api/nonexistent-xyz   -> 401   ← 对照：不存在的路径同样 401，证明 401 与路由无关
```

**正确做法**：用**只有新构建才有的静态产物**判定上线，并配对照：

```
GET /assets/Home-DDoanYQi.js    -> 200   ← 需求 B 首页产物（旧构建不可能有）
GET /assets/Home-XXXXXXXX.js    -> 404   ← 对照：证明 200 不是「/assets/* 一律放行」
```

再叠加**编译期内嵌串**（`api/dashboard`、`该资产未设置资产类别`）与 **SHA256** 交叉印证。

## 5. 缺陷与观察

### 5.1 业务代码缺陷

**无（P0 / P1 / P2 = 0）。**

### 5.2 测试代码缺陷（2 处，已修 —— 均为「共享库 + 并行包」假红，非业务问题）

`go test ./...` 会**并行**跑各包，而这些用例连的是**同一套生产库**，跨包互相建/删探针卡，导致依赖「多次读一致」的断言偶发假红。两处均已加固为**并发容忍**：

1. **`store/repair_qa_store_test.go` · `TestQADataHygiene`**（我方用例）
   - 现象：并行跑 `./api/... ./store/...` 时，store 包的卫生扫描会扫到 api 包**尚在途**的 `QA-REPAIR-` 探针卡 → `probe_card=1` 假红（单跑 store 包则 PASS）。
   - 修复：所有「疑似残留」计数加 **90s 宽限期**（只统计创建于 90 秒前的行），真正的历史残留必落窗口之外；孤儿行不变量保持严格。

2. **`cmd/orgreset/main_test.go` · `TestInspectSplitsVisibleAndSoftDeletedCards`**（工程师用例）
   - 现象：先 `SELECT COUNT(*)`（总数）再 `inspect()`（分项），两次读落在不同快照 → 「可见 203 + 软删 0 ≠ 总数 204」假红（单跑该包则 PASS）。
   - 修复：改为取「`inspect` 前后总数不变」的**静止快照**再断言；持续并发写入则 `Skip` 而非误报。

- 验证：修复后 `go test ./...`（并行）**连续两次全绿**（7 包全 ok）。
- **改动仅限测试文件**（`_test.go`），未触碰任何业务代码。

### 5.3 非阻塞观察（供参考，不影响判定）

1. **dry-run 会推进 `sync_state`**：`syncer.Run` 即使 dry-run 也会写 `sync_run` 审计行并更新 `sync_state.last_run_id/last_success_at`（本次 id=253）。对业务无影响（`cursor_value` 未动、00:00 批次照常），但严格说 dry-run 应「零副作用」，建议后续把审计写入也纳入 dry-run 判定。**既有行为，非本次引入。**
2. **`asset_card` 202 vs 星瀚 227**：非数据丢失。`external_asset_map` 有 227 行但仅 **200 个不同 `card_id`**（同一卡因星瀚侧资产编码变更产生多条映射），加 2 张手工卡（`source=购入`）= 202。`asset_history` 创建记录恰为 202、软删 0，佐证无丢卡。
3. **admin 调 `GET /api/repairs?mine=1` → 403**：属**设计**。`admin` 无员工绑定（`employee_id=0`），`mine=1` 需绑定员工（`api/repair.go:174`「当前账号未绑定员工，无法查看我的单据」）；同理 `POST /api/repairs` 对无员工绑定的账号返回 403（`api/repair.go:110`）。**非缺陷。**
4. **真实卡 2（iPhone 13 Pro）当前 `status=维修中`**：`updated_at=2026-09-02`，**早于本次全部改动**，且 `biz_status` 为空（非单据驱动）——属**既有真实数据**，非测试残留，未触碰。
5. **旧 `sync_run_error` 38 行**：全部来自 `run_id=10`（9 月初 vendor 重复插入），**陈旧、非本次产生**；首页 `sync_failed` 待办计数即源于此，属既有数据现状。
