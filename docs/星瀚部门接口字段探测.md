# 星瀚部门接口（query-department / 行政组织）字段探测

> 探测日期：2026-09-18
> 接口：`POST /v2/gcgs/base/bos_adminorg/query-department`
> 复现命令：`go run ./cmd/kdscan -config config.yaml -target dept`
> 指纹基线：`docs/kingdee-dept-baseline.json`

## 一、结论摘要

1. **接口可用，返回全集团行政组织树 5203 个节点**（启用 5196 / 停用 7），
   层级 1~10 层，`number` 全局唯一无重复。
2. **它是本次排查里唯一能"往上追"的接口**：每个节点都带
   `structure[].viewparent_number`（父节点编码）与 `level`（层级），
   **整棵树可以完整还原**，不需要对方额外提供。
3. **资产卡的部门归属 227/227 全部可解析**：29 个使用部门全部命中组织树，
   追到公司后 `1201`（XXX公司）140 张、`1202`（YYY公司）87 张，**零未命中**。
4. ⚠ **「公司」在树里不固定层级**（L2~L8 都有），编码位数也不固定（2~12 位），
   753 个名字带「公司」的节点其实是**部门**。
   **唯一可靠判据是 `orgpattern_name = 公司`**，不能按层级或名称判断（见 4.1）。
5. **人员接口 0 行的铁证在这里**：过滤条件用 L4 公司编码 `1201`/`1202` 做**等值匹配**，
   但全量实测 **`1201`/`1202` 被挂载 0 次**，88.3% 的人员挂载点在 L5–L7。
   叠加第二个缺陷——过滤条件引用的 `orgstructure_number` 在投影里**恒为空**（见第六节）。
6. **`name` 不可作为业务键**：5203 个节点只有 1333 个唯一名称，555 个名称重复，
   `财务部` 一个名字挂了 **78 个**节点。任何按名称匹配的方案都会错。
7. **接口只给组织，不给成员**：没有任何字段能反查"这个部门有哪些人"。
8. ⚠ **「用资产卡使用人反推部门」这条路径已实测证伪**（仅 64% 一致）。
   原因是人员接口的 `entryentity` 是**多法人主体并行挂载**，
   且没有字段标明主职。**台账补部门归属只能用资产卡自身的 `headusedept_number`**（见 5.3）。

## 四、组织树与编码规律

树的根是 `GCGS`（ZZZ集团（集团）），**整棵树覆盖整个集团**，
不只是 XXX板块。XXX板块是其中 `12` 这一支：

```
GCGS          L1  ZZZ集团（集团）
└ GCGSHB      L2  ZZZ集团（合并）
  └ 12        L3  XXX公司（合并）
    ├ 1201    L4  XXX公司          ← 过滤条件里的 1201
    │ ├ 120101  L5  公司领导
    │ ├ 120102  L5  财务部
    │ │ ├ 12010201  L6  总账组
    │ │ └ 12010202  L6  财务组
    │ ├ 120108  L5  品牌资产管理部
    │ │ ├ 12010801  L6  商标管理组
    │ │ ├ 12010802  L6  园区管理组
    │ │ └ 12010803  L6  品牌授权组
    │ └ …（L5 共 48 个）
    └ 1202    L4  YYY公司        ← 过滤条件里的 1202
      ├ 120201 … 120224  L5
      └ …（L5 共 48 个）
```

**XXX板块子树（`12` 之下）共 90 个节点**：L3 ×1、L4 ×2、L5 ×48、L6 ×39。

**编码规律**：`number` 是逐级下钻的定长编码——
`1201`（公司，4 位）+ `08`（部门，2 位）= `120108`；再 + `01`（组）= `12010801`。
每深一层补 2 位。但**不要靠解析编码来还原层级**（集团别处的编码并不统一，
如 `07050100701060202`），**用 `level` + `viewparent_number` 更可靠**。

`longnumber` 是完整路径，例如 `120108` 的：

```
GCGS!GCGSHB!12!1201!120108
```

> 这条路径对修人员过滤条件最有用：用 `longnumber` 做前缀匹配
> （`like 'GCGS!GCGSHB!12!%'`）就能一次覆盖整个 XXX板块子树，
> 而不用逐个枚举 L4/L5/L6 的编码。
> ⚠ 但人员接口的投影里**没有** `orgstructure_longnumber`，见
> `docs/星瀚人员接口字段探测.md` 第八节的过滤条件修正建议。

### 4.1 ⚠ 「公司」在树里不固定层级 —— 只能用 `orgpattern_name` 判

这是最容易踩的坑：**不能靠层级判断一个节点是不是公司**。

`orgpattern_name`（组织形态）的完整分布：

| `orgpattern_number` | `patterntype` | `orgpattern_name` | 节点数 |
|---|---|---|---|
| `Orgform06` | 3 | 部门 | 4938 |
| `Orgform02` | **1** | **公司** | **204** |
| `Orgform01` | 3 | 集团 | 55 |
| `Orgform05` | 2 | 工厂 | 4 |
| `Orgform03` | 2 | 分公司 | 2 |

`orgpattern_name = 公司` 的 204 个节点，**层级从 L2 一直散到 L8**：

| level | 2 | 3 | 4 | 5 | 6 | 7 | 8 |
|---|---|---|---|---|---|---|---|
| 公司节点数 | 1 | 15 | **76** | **88** | 19 | 2 | 3 |

编码位数同样不固定：公司节点的 `number` 有 2 / 4 / 6 / 7 / 8 / 9 / 10 / 12 位。
（XXX板块这一支刚好是 4 位、L4，纯属巧合。）

三个"看着像公司"的判据**全都不可用**：

| 判据 | 反例 |
|---|---|
| 层级 = L4 | 1201/1202 是 L4，但 `0101` 在 L3、`0301` 在 L3、还有公司在 L5/L6 |
| 编码 4 位 | 公司编码有 2/4/6/8/10/12 位；4 位里也有部门 |
| 名称含「公司」 | **753 个名字带「公司」的节点 `orgpattern_name = 部门`**，如「XXX公司」`120128` |

**唯一可靠判据是 `orgpattern_name`（或等价的 `orgpattern_number = 'Orgform02'`）。**

用 `orgpattern_name` 沿 `longnumber` 上溯，**资产卡 227 行 100% 能找到唯一公司节点**：

```
120108 品牌资产管理部  L5  →  1201 XXX公司（公司）
120115 综合办公室      L5  →  1201 XXX公司（公司）
120213 综合办公室      L5  →  1202 YYY公司（公司）
12020701 空调组        L6  →  1202 YYY公司（公司）
```

结果：`1201` → **140 张**，`1202` → **87 张**，**零未命中**。

> 对比：如果按"上溯到 L4"来做，`120108`（L5）会正确落到 `1201`，
> 但一个挂在 L6 的部门、或挂在 L5 公司的部门，都会算错。
> **按 `orgpattern_name` 上溯才对。**

## 五、能解决什么

### 5.1 资产卡 → 公司归属（227/227，零未命中）

资产卡原本只有 `headusedept_number`（使用部门，L5/L6），拿不到公司。
有了组织树，往上追到 L4 即可：

| 使用部门 | 名称 | 层级 | 卡片数 | 追溯链路 |
|---|---|---|---|---|
| `120108` | 品牌资产管理部 | L5 | 75 | 120108 ← 1201 ← 12 ← GCGSHB ← GCGS |
| `120117` | 品质管理部 | L5 | 18 | 120117 ← 1201 ← … |
| `120115` | 综合办公室 | L5 | 14 | 120115 ← **1201** ← … |
| `120213` | 综合办公室 | L5 | 14 | 120213 ← **1202** ← … |
| `120215` | 信息数字化部 | L5 | 12 | 120215 ← **1202** ← … |
| `120221` | YYY公司 | L5 | 11 | 120221 ← 1202 ← … |
| `12020701` | 空调组 | L6 | 2 | 12020701 ← 120207 ← 1202 ← … |

**29 个使用部门全部命中，合计归属：`1201` → 140 张，`1202` → 87 张。**

注意 `120115` 与 `120213` 都叫「综合办公室」、`120215` 与 `120112` 都叫「信息数字化部」，
**靠名称根本分不出是哪个公司的**——必须靠编码 + 树。

### 5.2 台账部门/公司字段（部分可解）

台账 `employee` 65 人里，`dept_id = 0` 有 62 人、`company_id = 0` 有 64 人。
有 `dept_name` 的只有 3 人，逐个对照：

| 工号 | 姓名 | 台账 `dept_name` | 台账 `company_name` | 组织树里同名节点 |
|---|---|---|---|---|
| `000388` | 张三 | 信息数字化部 | XXX公司 | `120112`(→1201) / `120215`(→1202) |
| `000336` | 李四 | 综合办公室 | （空） | `120115`(→1201) / `120213`(→1202) |
| `002087` | 王五 | 财务部 | （空） | `120102`(→1201) / …共 78 个同名 |

**这 3 个名字在组织树里都不唯一**，光靠 `dept_name` 无法定位。
唯一线索是 `000388` 的 `company_name = "XXX公司"` —— 那正是组织 `1201` 的
**`simplename`**（5203 个节点里只有它填了简称），说明台账这一列存的是组织简称而不是全称。

### 5.3 ⚠ 已被证伪的路径：用资产卡的使用人反推部门

资产卡有 `headuseperson_number`（使用人），227 张卡涉及 **65 个使用人**，
与台账 65 人的 `emp_no` **重合 64 人**，而 65 人在人员接口**匹配率 100%**。
看起来是一条现成的路——**实测走不通**：

| 检验 | 结果 |
|---|---|
| 使用人 → 人员接口匹配 | 65/65（100%） |
| 卡上部门 = 人员 `entryentity` 的**任一**部门 | 198 / 227（87%） |
| 卡上部门 = 人员 `seq` 最小的那个部门 | **146 / 227（64%）** ❌ |

原因有两层：

**① `entryentity` 是「多法人主体并行挂载」，不是历史调岗。**
同一个职位会在每个法人主体下各挂一条，`seq` 是**明细行号**，不是主职标志：

```json
// 000376 赵六，职位「园区主管」，2 条明细
[0] seq=1  dpt_number=120108  dpt_name=品牌资产管理部
    orgstructure_fullname=…_XXX公司_品牌资产管理部      ← 挂 1201
[1] seq=2  dpt_number=120210  dpt_name=品牌资产管理部
    orgstructure_fullname=…_YYY公司_品牌资产管理部    ← 挂 1202
```

`seq` 的取值范围实测到 **165**（`entryentity` 单行最多 165 条），
所以「取 seq 最小」既不是主职，也不唯一。**没有任何字段标明哪条是当前主部门。**

**② 台账那 3 个有 `dept_name` 的人，在人员接口里同样是多值。**

| 姓名 | 台账 `dept_name` | 人员接口给出的部门（全部） |
|---|---|---|
| 张三 | 信息数字化部 | `120112`(→1201) **和** `120215`(→1202) |
| 李四 | 综合办公室 | `120115`(→1201) **和** `120213`(→1202) |
| 王五 | 财务部 | `120101`、`120102`(→1201)、`120214`(→1202) |

台账的 `company_name = "XXX公司"` 恰好是 `1201` 的 **`simplename`**，
说明台账这边是能分清 1201 / 1202 的，反倒是人员接口分不清。

> **结论：台账补部门归属，必须用资产卡自身的 `headusedept_number` + 组织树
> （路径 A，227/227 可靠），不要用「使用人 → 人员接口」反推（路径 B，仅 64% 可靠）。**
> 人员接口的 `dpt_*` 适合用来建**人员档案**的部门归属，但**必须按多值处理**，
> 不能单值化——见 `docs/星瀚人员接口字段探测.md`。

## 六、人员接口 0 行的铁证（2026-09-18 已实测确认）

把三个接口放在一起，根因非常清楚。人员接口的过滤条件是：

```
entryentity.orgstructure.number = '1202' OR entryentity.orgstructure.number = '1201'
```

拿这份过滤条件，去比对人员接口**全量返回**（过滤已恢复为 `[null]`，5038 行）的
10633 条 `entryentity` 明细，得到两条独立的致命原因：

### 原因一：拿 L4 公司编码做等值匹配，而人员全挂在 L5 以下

| 人员 `dpt_number` 所在层级 | 明细条数 | 占比 |
|---|---|---|
| L1 | 5 | 0.0% |
| L2 | 2 | 0.0% |
| L3 | 24 | 0.2% |
| **L4** | **431** | **4.1%** |
| **L5** | **3017** | **28.4%** |
| **L6** | **4277** | **40.2%** |
| **L7** | **2095** | **19.7%** |
| L8 | 763 | 7.2% |
| L9 | 19 | 0.2% |

**88.3% 的挂载点集中在 L5–L7**。而 `1201` / `1202` 是 **L4** 节点：

```
1201 被挂载  0 次    XXX公司 (L4)
1202 被挂载  0 次    YYY公司 (L4)
12   被挂载  0 次    XXX公司（合并） (L3)
```

**没有任何一个人的 `entryentity` 挂在 `1201` 或 `1202` 上**——
等值匹配必然返回 0 行。这不是"可能"，是**算术上的必然**。

### 原因二：过滤条件引用的字段在投影里恒为空

过滤条件用的是 `entryentity.orgstructure.number`。该字段**确实出现在投影里**，
但 10633 条明细里**非零值为 0 条**：

| 字段 | 出现 | 有值 | 唯一值 |
|---|---|---|---|
| `orgstructure_id` | 10633 | 10633 | 2152 |
| `orgstructure_fullname` | 10633 | 10633 | 2152 |
| `orgstructure_name` | 10633 | **0** | 0 |
| `orgstructure_number` | 10633 | **0** | 0 |
| `dpt_id` | 10633 | 10633 | 2152 |
| `dpt_name` | 10633 | 10633 | 651 |
| `dpt_number` | 10633 | 10633 | 2152 |

星瀚把 `orgstructure_*` 加进了投影，却**只有 `id` 和 `fullname` 有值**，
`name` / `number` 是空串——**而过滤条件偏偏用的是 `number`**。

### 结论与建议

> **0 行是两个独立缺陷叠加的结果**：过滤条件用了错误的层级（L4 等值匹配），
> 又用了投影里取不到值的字段（`orgstructure.number` 恒空）。
> 只要其中任意一个成立，就永远是 0 行。

| # | 方案 | 实测覆盖 | 评价 |
|---|---|---|---|
| 1 | 给 `orgstructure_number` 补值，过滤条件改**前缀匹配** | 全量 | 最稳，但要星瀚改投影 |
| 2 | 过滤条件改用 `entryentity.dpt_number like '1201%'` | 136 明细 / **131 人** | **当前投影就能用，无需星瀚改动** |
| 3 | 过滤条件改用 `entryentity.orgstructure.longnumber like 'GCGS!GCGSHB!12!%'` | 全量 | 语义最准，但 `longnumber` 不在投影里 |
| 4 | 开通 `bos_user/query` 权限，绕开这个受限接口 | — | 最省事，只是加授权 |

> 方案 2 的实测数字：`dpt_number like '1201%'` → 136 条明细 / 131 人；
> `like '1202%'` → 117 条 / 113 人；两者合并去重 → **131 人**。
> 台账关心的 65 个资产使用人中，**62 人能被命中**。
> 注意方案 2 有个小缺口：`1200151`（业务支持中心二组）这类"跨支"编码
> 不以 `1201` 开头，会漏掉（这就是 142 → 136 那 6 条的差异）。

**同时仍需星瀚配合的两件事**：
1. **清理 `entryentity` 的重复明细**——10633 条里有大量同职位多主体重复挂载，
   且没有字段标明主职，导致无法单值化（详见第五节 5.3）。
2. **更正 API 文档的类型标注**（`id` 等标 Long 实为 String，见人员报告第五节）。

## 七、接口的能力边界

- **只给组织，不给成员**。没有任何字段能反查部门下有哪些人。
- **不给负责人**。`structure` 里没有 `isincharge` 之类的角色字段
  （人员接口的 `entryentity.isincharge` 才有，但那边没有组织）。
- **21 个视图混在 `structure` 里**，取树必须按 `view_id` 筛。
- `name` 重名严重（`财务部` ×78），**业务键只能用 `number` 或 `id`**。

## 八、复现方式

```bash
# 扫描部门接口并与基线对比
go run ./cmd/kdscan -config config.yaml -target dept

# 三个接口一起扫（资产卡 / 人员 / 部门）
go run ./cmd/kdscan -config config.yaml -target all

# 展开某个组织节点（-code 传组织编码）
go run ./cmd/kdscan -config config.yaml -target dept -code 120108
```

`filter = [structure.view.id = 1]`、5203 行 / 5203 个编码、29 个顶层字段 + `structure` 30 个子字段。
