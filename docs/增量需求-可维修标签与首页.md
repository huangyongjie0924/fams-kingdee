| 版本 | v1.0 |

| 上游依据 | `docs/设计宗旨.md`（19 条评审清单 + 8 条反例）、`docs/维修流程模块需求分析.md`、`docs/维修流程模块架构建议.md`（§1.5 `display_status`） |
| 语言 | 简体中文 |

> **一句话结论**：
> **需求 A** —— 在 `asset_category` 上加一个本地布尔列 `repairable`（同步只 INSERT 不 UPDATE，加列安全），**建议默认开启 3 个分类（机器设备 / 电子设备 / 办公设备）**，运输工具与「其他」待老板拍板；不可维修资产在三层（详情页 / 报修页 / 后端）拦截，且**「历史事实不被新规则否定」**——改标签只拦新提交，不动历史与进行中单据。
> **需求 B** —— 首页采用「**一个页面 + 按角色渲染区块**」，不按角色分页面；核心是「**待我处理**」；维修中统计一律走 `display_status`（`COALESCE(NULLIF(biz_status,''), status)`），**不用会被同步重置的裸 `status`**。

## 0. 背景与范围

老板看完已上线的维修模块后提出两个**增量**需求：

| # | 原话 | 本文件章节 |
|---|---|---|
| A | 「只针对设备类资产可维修提单，资产分类中比如电子设备、办公设置、机器设备。建议是在资产分类中加个标签识别是否可维修。」 | §一 |
| B | 「需要设计一个首页显示资产、流程的情况。」 | §二 |

**已核实的技术事实**（直接采用，不再重复验证）：

- `asset_category` 表结构：`id, name, code, parent_id, use_months, residual_rate, sort_index, created_at`。
- `asset_category` 是**本地主数据**，同步只 `INSERT` 新分类、**不 UPDATE** 已有行（`store/sync.go:105-111` `CreateMasterTx`，category 分支仅 `INSERT INTO asset_category (name, code)`）→ **加列安全，不会被同步覆盖**（与 `asset_card.status` 的情况完全不同）。
- 现有 10 条分类**扁平**（seed 无 `parent_id`，即全部为顶层）；资产卡通过 `category_id` 直接引用某个分类。
- `store/card.go` 的 `cardSelect` **已经** `LEFT JOIN asset_category cat`（L25）→ 派生字段零新增 JOIN。
- 目前**没有首页**，`web/src/router/index.ts` L10 `/` 直接 `redirect: "/assets"`。
- 现有 6 个角色：`admin / asset_manager / counter / dept_head / repair_tech / viewer`。

**硬约束**：本文档所有设计已逐条过 `docs/设计宗旨.md` 的 19 条评审清单（见 §三），并避开 8 条反例。

## 一、需求 A：分类「可维修」标签

### A.1 标签语义与归属

| 项 | 定义 |
|---|---|
| **语义** | 资产分类上的一个布尔属性：该分类下的资产**是否允许提交维修单**。`true` = 可维修，`false` = 不可维修 |
| **载体** | `asset_category.repairable`（`TINYINT(1) NOT NULL DEFAULT 0`）——台账**本地**列 |
| **同步影响** | **零**。同步对 category 只 INSERT 不 UPDATE；新同步进来的分类取列默认值 `0`（不可维修） |
| **默认值取向** | **`0`（不可维修）是安全默认**：拦下一单是可恢复的（管理员开启标签即可），放进一单不该报的会污染数据。宁可少开，不可多开 |
| **层级规则** | 分类扁平，**按资产自身的 `category_id` 判定，不做父子继承**。若将来引入嵌套分类，再单独定义继承规则（当前数据无此问题） |

> **维护提示**：新分类（含星瀚同步新建的）默认不可维修，需管理员手工开启。这是「安全默认」的代价，建议在首页给管理员一个轻提示（见 §二 B.4 P2-3）。

### A.2 初始值建议（哪些分类默认可维修）

老板原话举例：「电子设备、办公设置、机器设备」——「比如」说明不是穷举。逐条判断：

| id | 分类名 | 编码 | 建议初始值 | 依据 |
|---|---|---|---|---|
| 2 | **机器设备** | 0203 | ✅ **可维修** | 老板明确举例；典型设备类 |
| 3 | **电子设备** | 0205 | ✅ **可维修** | 老板明确举例；典型设备类 |
| 5 | **办公设备** | 0206 | ✅ **可维修** | 老板举例（原话「办公设置」应为「办公设备」） |
| 4 | **运输工具** | 0204 | ❓ **待拍板**（**建议 ✅**） | 汽车 / 叉车本质是设备、会坏需修，符合「设备类」；但其维修常走保险 / 4S / 年检，流程与内部报修不同。**产品建议纳入**，请老板确认 |
| 7 | **其他** | 0299 | ❓ **待拍板**（**建议 ❌**） | 兜底分类，语义不定，里面可能混有房屋 / 土地类。**建议默认关闭**，由管理员按需开启——避免「最小意外」 |
| 1 | 房屋及建筑物 | 0202 | ❌ 不可维修 | 构筑物，维修走物业 / 基建，非「设备维修」 |
| 8 | 建筑物 | 0101 | ❌ 不可维修 | 同上 |
| 10 | 房屋及建筑物 | 0302 | ❌ 不可维修 | 同上（重复类） |
| 6 | 土地资产 | 0201 | ❌ 不可维修 | 无实体 |
| 9 | 土地使用权 | 0102 | ❌ 不可维修 | 无实体 |

> **注（事实性，不影响上表结论）**：上表 `id` 为当前生产库快照。分类 `id` 是自增主键、**按插入顺序生成、与 `code` 数字序无关**（如 `id=1` 是 `0202`、`id=5` 是 `0206`），且**跨环境不稳定**。故 `id` 列**仅作示意**，任何实现一律**按 `code` 匹配、勿硬编码 `id`**。

**汇总**：
- **建议默认可维修（3 个）**：机器设备、电子设备、办公设备（老板明确举例，零争议）。
- **待老板拍板（2 个）**：运输工具（产品建议 ✅）、其他（产品建议 ❌）。
- **建议默认不可维修（5 个）**：房屋及建筑物 ×2、建筑物、土地资产、土地使用权。

| 项 | 结论 |
|---|---|
| **权限** | `master.manage`（现授予 `asset_manager`，`admin` 隐式）——与「资产分类」页现有编辑权限一致，**不新增权限位** |
| **位置** | `web/src/views/master/CategoryTree.vue`（资产分类管理页） |

### A.4 不可维修资产的报修入口表现（三层防线）

原则：**前端隐藏是体验，后端拒绝是底线**。三层都要有，缺一不可。

| 层 | 位置 | 表现 | 性质 |
|---|---|---|---|
| **① 详情页** | `web/src/views/asset/CardDetail.vue`（报修按钮 L47） | 条件从 `auth.can('repair.report')` 改为 `auth.can('repair.report') && card.repairable`；不可维修时**直接隐藏**按钮（不用禁用态，避免噪音） | 体验 |
| **② 扫码落地** | 扫码 → `#/assets?asset_code=X` → 打开 `CardDetail` 抽屉 | 同上——按钮不出现，员工看到的是资产详情，不会误点 | 体验 |
| **③ 报修页** | `web/src/views/repair/New.vue` | 若用户**直接访问**（书签 / 手输编码）且资产不可维修：显示 `el-alert`（type=warning）说明原因，**隐藏提交表单**；手动输入编码解析后同样判定 | 体验兜底 |
| **④ 后端** | `api/repair.go` `handleCreateRepair` | 拒绝并返回 **400**，文案（业务白话，符合原则 3）：<br/>「该资产所属类别「房屋及建筑物」不支持报修，如需维修请联系资产管理员」 | **底线（必须）** |

> **文案要求**：错误信息必须**带上分类名**（让员工明白「为什么不行」），且**给出去处**（联系管理员），不能只回「无权限」。

### A.5 边界情况：分类「可维修改为不可维修」时的规则

这是本需求最容易出错的点。明确规则如下（核心一句：**历史事实不能被新规则否定**）：

| 场景 | 规则 | 理由 |
|---|---|---|
| **历史维修单**（已完工 / 已驳回 / 已撤单） | **完全保留**，不受影响 | 它们记录的是「当时发生过的事实」，新规则不能追溯否定 |
| **进行中的维修单**（待受理 / 已受理 / 已派工 / 维修中 / 待确认） | **继续走完**，不因标签变更而中断或自动驳回 | 已经投入了受理 / 派工 / 维修成本；中断比走完更糟。管理员若确要终止，走既有的「取消」动作 |
| **新提交的报修单** | **拦截**（后端 400） | 规则只对新动作生效 |
| **反向变更**（不可维修 → 可维修） | 无特殊影响，立即允许新提交 | 放宽总是安全的 |
| **资产换分类**（`category_id` 变更） | 按**当前**分类判定；已有单据不受影响 | 判定依据始终是「提交那一刻的分类」，历史单已快照 `asset_name` 等，不回溯 |
| **分类被删除** | 现状 `deleteRef` 已禁止删除被资产引用的分类（`store/masterdata.go:98-115`），无需额外处理 | 复用既有护栏 |

## 二、需求 B：首页

### B.1 首页形态结论

**结论：一个页面 + 按角色渲染区块（不按角色分页面）。**

| 理由 | 说明 |
|---|---|
| **1. 符合「零学习成本」** | 路由唯一（`/` → `home`）。员工和管理员都只需记住「回首页」，不需要知道「我这个角色该进哪个首页」 |
| **2. 差异本质是「看多少行」，不是「看什么」** | 6 个角色的数据源高度重叠（资产统计 + 维修待办），差别只在可见范围。而可见范围**已经由 `assetScope` / `repairScope` 在服务端按角色收窄**（`api/scope.go`）——前端只需渲染服务端返回的同一份结构 |
| **3. 「待我处理」是同一张卡片、不同角色的不同查询** | 不是不同的页面结构。分页面会把 `scope` 逻辑在前端复制 6 份 |
| **4. 避免 6 个几乎相同的页面** | 按角色分首页 → 6 个高度重复的视图，违反「信息只录一次」的精神（这里是「视图只写一次」），且新增角色要加页面 |

**实现形态**：单个 `Home.vue`，内部用 `v-if="auth.can(...)"` / 角色判断控制区块显隐——与 `SideMenu.vue` 现有的「全部 `v-if="auth.can(...)"`」风格一致。

> **路由改动**：`router/index.ts` L10 `{ path: "", redirect: "/assets" }` → `{ path: "", name: "home", component: () => import("../views/Home.vue") }`；登录后跳转由 `beforeEach` 改为落 `home`。
> **服务端**：新增一个 `GET /api/dashboard`，按登录角色返回「待办 + 概览」两份数据（读接口不门控，范围在数据行上收窄——沿用既有约定）。

### B.2 「待我处理」——首页的核心

每个角色进来第一眼看到的应是「**有什么要我做的**」。按 6 个角色列出：

| 角色 | 「待我处理」清单 | 条数 | 数据来源 |
|---|---|---|---|
| **admin** | ① 待受理维修单 ② 已受理未派工 ③ 待确认（可代确认）④ 同步异常 / 失败批次 ⑤ 维修超时单 | **5** | `repair_order` + `sync_run` |
| **asset_manager** | ① 待受理 ② 已受理未派工 ③ 待确认 ④ 维修超时跟催 | **4** | `repair_order` |
| **repair_tech** | ① 派给我的待接单（`dispatched`）② 我名下维修中未完工（`repairing`） | **2** | `repair_order`（`assignee_emp_id=me`） |
| **dept_head** | ① 本部门（含下级）待受理 ② 本部门维修超时；③（P1）本部门待审批 | **2（P0）+1（P1）** | `repair_order`（`use_dept_id ∈ 子树`） |
| **counter** | ① 我的待盘点任务（`count_item` 指派给我且未录入）② 我的报修待确认 | **2** | `count_item` + `repair_order` |
| **viewer（员工）** | ① 我的报修待确认（等我确认）② 我的报修处理中（在流转、不需我动手，仅展示） | **2** | `repair_order`（`reporter_emp_id=me`） |

> **设计要点**：
> - 「待我处理」里的每一项都应是**可点击直达**的（点「待受理 3」→ 跳到维修管理列表并预筛 `status=pending`）。
> - 员工端**不出现**管理向待办（无「待受理」「待派工」）；维修工端不出现「我的报修」（他报修走员工视角，二者可并存但首页默认展示其角色主待办）。
> - 「超时」是 P1（依赖 P1-5 的时效规则）；P0 先不做超时项。

### B.3 展示哪些指标

| 分组 | 指标 | 说明 |
|---|---|---|
| **资产侧** | ① 资产总数 ② 分类分布（Top N）③ 状态分布 | 均按登录角色的可见范围统计（复用 `assetScope`） |
| **流程侧** | ④ 维修单各状态数量 ⑤ 待我处理（见 B.2）⑥ 近 30 天新增 / 完工趋势 | 按 `repairScope` 收窄 |

#### ⚠ 关键：「维修中」统计用哪个字段？

**结论：一律用 `display_status`（即 `COALESCE(NULLIF(biz_status,''), status)`），不用裸 `status`，也不单用 `biz_status`。**

| 字段 | 是什么 | 为什么首页不能用它单独统计 |
|---|---|---|
| `status` | 星瀚托管的生命周期状态 | **每日 00:00 会被同步重置**（`store/sync.go:217/322-324`；`useStatusMap` 把「正常使用」→「在用」，227/227 卡命中）→ 用它统计，维修中永远算不出来 |
| `biz_status` | 台账本地业务状态（`'维修中'`） | 只表达「本地业务占用」，不表达资产的生命周期全貌 → 只统计它，会漏掉「在用 / 闲置 / 报废」的分布 |
| **`display_status`** | **派生**：`biz_status` 非空取它，否则取 `status` | **唯一正确口径**。与列表 / 详情 / 筛选 / 导出一致（架构建议 §1.5 单点收敛） |

- 首页「状态分布」的 SQL 按 `GROUP BY COALESCE(NULLIF(biz_status,''), status)` 聚合（`asset_card` 仅约 227 行，全表聚合成本可忽略）。
- 维修单各状态数量按 `repair_order.status` 聚合（这是单据自己的状态，与卡片状态无关）。

### B.4 P0 / P1 / P2

| 优先级 | 内容 |
|---|---|
| **P0** | ① 首页框架 + 路由（`/` → `home`，登录后落首页）② 「待我处理」卡片（按 6 角色渲染，见 B.2）③ 资产总数 + 维修单状态数量（用 `display_status`）④ `GET /api/dashboard` 接口 |
| **P1** | ① 资产状态分布 / 分类分布（Top N）② 近 30 天趋势（新增 / 完工）③ 快捷入口（去报修 / 去盘点 / 去维修管理）④ 「超时」待办项（依赖 P1-5）⑤ 员工「我名下资产」区块（承接 P1-6「我的资产」） |
| **P2** | ① 部门维度对比 ② 维修成本概览（依赖 P1-4）③ 「有 N 个分类未设置可维修标签」的管理员提示（呼应 §A.1 维护提示） |

### B.5 明确不做（避免做成大而全的 BI 看板）

| 不做 | 理由 |
|---|---|
| 自定义图表 / 拖拽式看板配置 | 违反 `docs/项目介绍.md`《关键设计决策》「领域固化，不做元数据驱动」 |
| 多维下钻 / 任意维度透视 | 首页是「待办 + 概览」，不是分析工具；真要做分析应单开报表页 |
| 日期区间对比、同比环比 | 227 张卡、单集团规模，收益极低 |
| 报表设计器 / 导出配置 | 已有 `assets/export`；首页不做导出 |
| 实时刷新 / WebSocket 推送 | 无此量级需求；手动刷新足够 |
| 地图 / 大屏 | 超出「服务每一位员工」宗旨（那是给领导看的，不是给员工用的） |
